# 协作面与模拟身份

更新时间：2026-10-31。本文记录 HTTP 0.6.0／第九项迁移的首个协作切片。帖子、频道、写预算和实时信封保持 0.5.1。

## 已确认的产品决定

1. 通过校验的访问令牌在本地没有对应行时，插入 `issuer`＋`subject` 用户。不要求邀请。
2. 多个身份组同时适用时，只采用优先级最高的那一组的全部授权。较低组的授权不并入，也不单独撤销最高组里的某一项。
3. 正式身份供应商是自托管 ZITADEL。本切片运行模拟 issuer，发现文档和 JWKS 路径与 ZITADEL 相同，便于以后只替换 issuer、audience 和 JWKS 地址。
4. 账号以后走第一方注册／登录。本切片不接入微信或其他第三方登录。

优先级相同的组不能写入目录（`priority` 唯一）。纯函数在调用方绕过该约束时，保留组 ID 字典序较小的一组，结果稳定。

## 采用的既有做法

| 做法 | 来源 | 本切片怎么用 |
|---|---|---|
| JWT 访问令牌必须签名，`typ` 为 `at+jwt`，拒绝 `none`，资源服务器校验精确的 `iss`、`aud` 和 `exp`，并支持 RS256 | [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) | 沿用现有 `tokenauth` 校验器，不另写验签。 |
| 应用明确列出可接受算法，避免把 `alg` 改成 `none` 或把 RS256 换成 HS256 | [RFC 8725 §3.1–3.2](https://www.rfc-editor.org/rfc/rfc8725.html) | 允许名单为 RS256、ES256、EdDSA。JWKS 地址来自配置，不读取令牌里的 `jku`。 |
| 用 JWKS 缓存和未知 `kid` 时的限速刷新 | [ZITADEL JWKS 说明](https://zitadel.com/docs/apis/openidoauth/endpoints)、[keyfunc](https://github.com/MicahParks/keyfunc) | 继续使用已锁定的 keyfunc v3.8.0，刷新间隔一分钟。 |
| OIDC 发现位于 `/.well-known/openid-configuration`，ZITADEL 的 `jwks_uri` 为 `{issuer}/oauth/v2/keys` | [ZITADEL 端点](https://zitadel.com/docs/apis/openidoauth/endpoints)；2026-10-31 对照公开实例 `https://zitadel-libraries-l8boqa.zitadel.cloud/.well-known/openid-configuration` | 模拟进程发布同样的路径和发现字段。签名算法只列出实际发布的 RS256 与 ES256。 |
| 测试用 issuer 同时提供发现文档、JWKS 和签名方法 | [compliance-framework mock OIDC](https://github.com/compliance-framework/api/blob/v0.17.2/internal/service/sso/providers/testutil/mock_oidc_server.go) | `internal/mockidp` 用进程内密钥签名 `at+jwt`。`POST /mock/token` 只用于开发。`POST /oauth/v2/token` 返回 501，把该路径留给以后的 ZITADEL。 |
| 首次见到外部身份时建立本地账号，并且不按未验证的 email 合并 | [Keycloak First Broker Login](https://docs.redhat.com/en/documentation/red_hat_build_of_keycloak/26.2/html/server_administration_guide/identity_broker) 的 Create User If Unique | 只按已配置 issuer 的 `sub` 插入。不同 issuer 的相同 subject 保持两行。 |
| 组成员用 PUT 加入、DELETE 移除，重复调用保持同一结果 | [Discourse groups API](https://github.com/discourse/discourse_api/blob/main/lib/discourse_api/api/groups.rb) | `PUT`／`DELETE /v1/identity/groups/{group_id}/members/{user_id}`。 |
| 优先级策略取最高优先级角色的判定，而不是把所有角色的权限做并集 | [Uberfire PRIORITY](https://www.uberfireframework.org/docs/security/permissionResolution.html)；同一思路见 [Casbin priority](https://casbin.apache.org/docs/priority-model/)。NIST RBAC 和 Discord 默认是并集，本决定明确不采用并集 | `identity.Resolve` 返回唯一获胜组的授权。 |
| 职员只能管理严格低于自己最高角色的角色和成员；比较的是双方的最高角色，而不是名册上较低的那一个 | [Discord 角色层级](https://support.discord.com/hc/en-us/articles/214836687-Discord-Roles-and-Permissions)；[Discourse：版主不能授予管理员](https://meta.discourse.org/t/admin-versus-moderator/56750/4) | 赋予的角色，以及目标的有效优先级，都必须低于调用者的有效优先级。有效优先级与权限接口相同。 |
| 始终保留至少一名管理员，避免把站点留成无人可管理 | [Prosody protect_last_admin](https://hg.prosody.im/prosody-modules/rev/2623515d8507) | 移除或降级后，仍须有一名成员的获胜角色含 `manage_members`。目录组也计入这名管理者。 |

没有新增 Go 依赖。验签仍是 golang-jwt v5.3.1 与 keyfunc v3.8.0。

## 模拟 issuer

```text
go run ./cmd/mock-idp
```

| 变量 | 默认 |
|---|---|
| ODYSSEIA_MOCK_IDP_ADDR | 127.0.0.1:9443 |
| ODYSSEIA_MOCK_IDP_ISSUER | https://127.0.0.1:9443 |
| ODYSSEIA_MOCK_IDP_AUDIENCE | odysseia-api |
| ODYSSEIA_MOCK_IDP_TLS_CERT_FILE／KEY_FILE | 必填，TLS 1.3 |

API 侧：

```text
ODYSSEIA_AUTH_ISSUER=https://127.0.0.1:9443
ODYSSEIA_AUTH_JWKS_URL=https://127.0.0.1:9443/oauth/v2/keys
ODYSSEIA_AUTH_AUDIENCE=odysseia-api
```

证书主机名与 issuer 主机名一致。换到 ZITADEL 时替换这三个值，并改用 ZITADEL 的令牌端点签发 `at+jwt`。

监听地址 `ODYSSEIA_MOCK_IDP_ADDR` 必须是回环：`127.0.0.1`、`::1` 或主机名 `localhost`。`0.0.0.0`、空主机（`:9443`）和其他地址会拒绝启动。这与 OAuth 本地回环只绑定 loopback、不绑定通配地址的做法一致（[RFC 8252 §7.3](https://www.rfc-editor.org/rfc/rfc8252.html)、[go-pkgz/auth 的 localhost 绑定](https://github.com/go-pkgz/auth/commit/32d0c6e7ee3f3fda4d488d5bf4913d740e90bfdc)）。

`POST /mock/token` 再检查 `RemoteAddr`。不是回环就返回 403，不签发。请求体只有 `subject` 和可选的 `alg`：

```text
POST /mock/token
{"subject":"alice","alg":"RS256"}
```

`alg` 可省略，默认 RS256，也可为 ES256。audience 固定为进程的 `ODYSSEIA_MOCK_IDP_AUDIENCE`，请求里不能另写；多写字段会得到 400。响应含 `access_token`、`token_type=Bearer`、`expires_in=300`。令牌含 `client_id=odysseia-mock`。发现文档和 JWKS 仍可在本机读取，它们不签发令牌。

## 数据

第九项迁移新增：

- `identity_groups`：内置 `member`（优先级 100，read＋post）、`moderator`（200，另含 delete 与 manage_members）、`owner`（300，另含 manage_groups）。
- `user_groups`：用户与目录组的多对多关系。
- `forum_members.role_id`：每个论坛成员保存一个角色，默认 member。已有成员行使用该默认值，开帖与回复的成员检查不变。

第一个拥有 `manage_groups` 的人由维护身份写入 `user_groups`，例如把本地用户插入 owner 组 `00000000-0000-4000-8000-000000000003`。之后该用户可以调用分配接口。

运行身份在原有论坛授权之外还需要：

```sql
GRANT SELECT, INSERT ON odysseia.users TO odysseia_runtime;
GRANT SELECT ON odysseia.identity_groups TO odysseia_runtime;
GRANT SELECT, INSERT, DELETE ON odysseia.user_groups TO odysseia_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON odysseia.forum_members TO odysseia_runtime;
GRANT INSERT ON odysseia.forum_member_removals TO odysseia_runtime;
GRANT INSERT (method, payload) ON odysseia.realtime_outbox TO odysseia_runtime;
GRANT USAGE ON SEQUENCE odysseia.realtime_outbox_id_seq TO odysseia_runtime;
```

成员变更先 `SELECT … FOR UPDATE` 锁住 `forums` 行。PostgreSQL 要求该语句除 SELECT 外，还要有表上至少一列的 UPDATE 权限（[SELECT 的锁定子句](https://www.postgresql.org/docs/current/sql-select.html)）。现有运行身份已经有 `GRANT UPDATE(last_topic_position) ON odysseia.forums`，这一列就满足锁行。不要只授 forums 的 SELECT。users 的 UPDATE／DELETE 仍不授予运行身份。移除成员写入的 disconnect 使用上面的 outbox INSERT 和序列 USAGE。

## HTTPS 接口

契约在 OpenAPI `info.version` 0.6.0。

| 方法与路径 | 行为 |
|---|---|
| GET /v1/identity/groups | 任何已登录用户读取目录。 |
| PUT /v1/identity/groups/{group_id}/members/{user_id} | 分配目录组。调用者的最高目录组需要 `manage_groups`。重复分配返回 200。 |
| DELETE /v1/identity/groups/{group_id}/members/{user_id} | 移除目录组。已经不存在时 `removed` 为 false。 |
| GET /v1/forums/{forum_id}/members | 当前成员分页列表，`after` 是排他的用户 UUID。`role_id`、`role_name`、`priority` 只是该行保存的论坛角色，不是有效优先级。非成员得到 404。 |
| POST /v1/forums/{forum_id}/members | 加入成员。`role_id` 省略时用 member。需要 `manage_members`。新角色的优先级必须低于调用者在该论坛的有效优先级。已存在返回 409／`member_exists`。 |
| PUT /v1/forums/{forum_id}/members/{user_id}/role | 设置该论坛成员的单一角色。新角色和目标的有效优先级都必须低于调用者的有效优先级。有效优先级与 GET permissions 相同，取目录组和论坛角色中的最高者。若变更后没有任何成员的获胜角色仍含 `manage_members`，返回 409／`last_manager`。 |
| DELETE /v1/forums/{forum_id}/members/{user_id} | 删除成员，并在同一事务写入审计和 realtime disconnect。目标的有效优先级必须低于调用者的有效优先级。不能因此让论坛失去最后一名管理者。 |
| GET /v1/forums/{forum_id}/permissions | 返回调用者在该论坛的获胜角色和它的授权。 |

论坛内的适用角色＝该成员的 `role_id`，加上该用户的全部目录组。非成员即使拥有目录组也得到 404。

授权名称为 `read`、`post`、`delete`、`manage_members`、`manage_groups`。`manage_members` 与 `manage_groups` 会拒绝缺少授权的变更。调用者和目标都用该论坛内的有效优先级作比较：目录组与论坛上保存的角色放在一起，只取最高的一组。只能赋予优先级更低的角色，也不能改动或移除有效优先级不低于自己的成员。因此版主不能移出一名论坛角色仍是 member、目录组却是 owner 的用户。成员变更在论坛行锁内完成。若结果会使获胜角色含 `manage_members` 的成员变为零，返回 409／`last_manager`。`read`、`post`、`delete` 供界面决定是否展示发帖、删帖等入口。帖子和频道的现有写入仍只检查论坛成员关系。消息删除路由尚未提供。

维护命令 `remove-forum-member` 继续保留，供带操作号的重试使用。

## 实际能做和不能做的事

`provision-forum` 插入成员时不写 `role_id`，数据库默认是 member（优先级 100，含 read 和 post，不含 manage_members）。新论坛因此没有论坛角色上的管理者。某成员如果已经在目录组 moderator 或 owner 里，有效优先级仍会带上 `manage_members`，可以管理该论坛。

API 赋角色时要求新角色的优先级严格低于调用者的有效优先级。内置最高优先级是 owner 的 300，所以没有任何调用者能通过 API 把论坛角色设成 owner。论坛角色 moderator（200）只有有效优先级高于 200 的人能赋，内置目录里就是 owner（300）。论坛行上的 owner 角色只能由维护身份直接写 `forum_members.role_id`。

`DELETE` 先做 `last_manager`，再做有效优先级比较。唯一管理者移除自己时，管理者计数先变成 0，返回 409／`last_manager`，不会先走到 403。两名管理者之一移除自己时，另一人仍在，计数检查通过，随后因为目标有效优先级等于自己而返回 403／`permission_denied`。`PUT` 角色则先拒绝不低于自己的新角色（403），再做 `last_manager`（409），最后才比较目标的有效优先级（403）。

`GET /members` 的 `priority` 来自 `forum_members.role_id` 对应的组，不合并目录组。目录 owner 若论坛角色仍是 member，这一列显示 100。界面不能只用它决定能否移除；移除是否允许要看双方的有效优先级，即 `GET /permissions` 那种最高组。

## 验证

本环境实际跑通的是默认测试，超时按完整包留出余量：

```text
go test -count=1 -timeout=180s ./...
go vet ./...
go build ./...
```

它覆盖身份组优先级、回环监听拒绝、非回环签发 403、请求体不能改 audience、RS256／ES256、`none` 与 HS256 拒绝，以及成员 HTTP 状态。带 PostgreSQL 夹具时再用同一超时：

```text
pwsh -File deploy/postgres/test.ps1 -GoExecutable go
```

该夹具运行 `integration` 标签，包含用户引导、版主不能移出“论坛角色 member、目录组 owner”的用户，以及唯一管理者不能把自己移出论坛。没有 Docker 夹具时，`go test -tags integration -c ./internal/postgres` 只确认这些测试能编译。
