## 4. 模块与首个模型草案

以下是逻辑职责；不按每张表机械创建多层接口或预建空目录：

| 模块 | 拥有的规则 | 对外协作 |
|---|---|---|
| 身份 | 外部 issuer／subject 与本地用户映射、API 身份接入。 | 提供可信用户身份，不从请求正文接受作者身份。 |
| 访问控制 | 身份组、授予、权限规则和判定。 | 经清楚接口取得作品／会话事实，不复制第二套成员状态。 |
| 作品 | 卡、分类／标签、版本与资源关联、发现可见性。 | 提供作品状态与归属。 |
| 讨论／论坛 | 独立论坛、帖子／模式、主楼与一层子回复归属。 | 使用通用消息，作品模块通过关联接入，不反向依赖作品。 |
| 会话 | 固定频道、私聊群聊、成员与生命周期。 | 使用同一消息机制，拥有成员关系。 |
| 消息 | 正文、稳定 ID、引用、幂等、revision、历史与读进度。 | 接收可信作用域上下文，生成业务变更事件；不反向调用所有上层产品。 |
| 文件 | 上传状态、对象元数据、关联、受控下载和清理。 | 对象存储 SDK 留在适配边界，授权来自业务。 |

首个切片需要表达的概念：

| 概念 | 最少需要表达的内容 |
|---|---|
| 用户／论坛／帖子 | 稳定身份、独立论坛及测试成员、帖子所属论坛和创建时模式；作品后续通过关联接入。 |
| 消息 | 稳定消息 ID、作用域、创建顺序、可信作者、正文、revision、具体引用消息 ID。 |
| 讨论归属 | 回复所属帖子、归属哪个主楼；它与实际引用目标是两种关系，正文不双写。 |
| 幂等请求 | 用户＋作用域＋客户端请求 ID 的唯一性；重复请求复用结果，冲突内容明确报错。 |
| 事件 | 稳定事件 ID、schema version、作用域、消息 ID／revision 和变更位置，随业务数据同事务写入。 |
| 用户进度 | 已收到、已读、变更同步位置分别定义；不让普通读取顺手改变已读。 |

其中当前成员论坛、帖子、创建消息／幂等／待发布事件已有迁移与 OpenAPI，细节见切片文档；revision、编辑删除变更日志、读进度、完整权限及作品关联仍为后续草案，不以字段清单冒充已实现。

事件和恢复需提前固定以下边界：

- 消息创建顺序、编辑／删除变更位置、Centrifugo 临时 offset 是不同概念。
- 同一作用域的顺序分配与业务／事件写入在事务内协调；全局自增 ID 不自动证明提交顺序。
- 发送成功表示持久化结果，投递可能重试；消费者与客户端按事件 ID／revision 去重。
- 短期缓存恢复失败后从业务数据库补拉变更或重新加载当前状态；不能只按新消息 ID 补拉而漏掉编辑／删除。
- 实时订阅、历史和引用读取执行同一业务可见性边界，撤权验证包含已建立连接。

## 5. P2 的最小业务验收场景

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A01 | 发主楼、回主楼、再引用子回复 | 始终只有主楼＋一层子回复，引用仍准确指向具体消息；对应 D02／D03。 |
| A02 | 伪造作者／跨作用域资源 ID | 作者由可信身份确定，越权读写与订阅被拒绝，没有正文／摘要泄漏。 |
| A03 | 重试或并发提交同一请求 | 只产生一份业务写入与一份逻辑事件，重复投递可去重。 |
| A04 | 消息与 outbox 的事务回滚／提交 | 回滚两者均不存在；提交后发布暂时失败仍可恢复投递。 |
| A05 | 页间插入、同排序边界、跨会话游标 | 分页稳定；游标不能用于读取其他作用域，不产生错页或越权。 |
| A06 | 短断线与超出缓存窗口 | 分别验证 SDK 恢复与业务补拉／状态加载路径，不静默漏消息。 |
| A07 | 现有连接失去访问权 | 后续正文、引用、历史、事件访问按约定时效撤销。 |
| A08 | 前端接入 | 提供 OpenAPI、错误语义、事件示例、恢复步骤和合成测试身份。 |

本切片只以合成数据验证明确范围，不自动等同于完整论坛、完整 IM、附件授权或三万在线生产验收。

当前 A01–A08 的后端范围均已完成，详细逐项证据见 [P2 验收与交接](P2后端验收与交接-2026-10-29.md)。新增真实 65 秒消费中断、历史过期、七页 HTTPS 加载和 241 条实时重叠合并；健康双节点撤权以 3 秒本机预算回归。A08 提供完整接入包，并通过真实协议测试模拟客户端完整恢复流程；未声称同事的前端页面已经签收。生产共享缓存高可用、正式故障撤权时效、小时级积压、乱序注入和容量在 P6 验收，当前异步窗口及持续刷新连接的限制明确保留。

## 7. 每一步的代码审查要求

主流程平铺、错误提前返回、集合索引和批量查询；禁止把新规则散落到各 handler。错误在边界记录一次，查询不顺带改状态。

提交一个功能前回答：

1. 改这个功能会牵动哪些模块，是否都与它相关？
2. 更换数据库、身份服务、实时层或对象存储，是否能把变化留在相应适配处？
3. 移除模块时是否只需调整明确依赖和入口装配，其他模块仍能独立验证？

当前按配置、进程装配、HTTP、身份类型、令牌协议与 PostgreSQL 适配分工。HTTP 接收验签／查用户函数，不导入 JWT 或数据库包；identity 类型不依赖它们。更换数据库或身份供应商主要调整相应适配与入口装配，HTTP 和纯身份类型可独立验证；当前没有套空服务层或每表接口。新增业务规则时再建立实际需要的边界。

实时模块只签发身份连接凭据，不操作论坛或数据库；HTTP 的服务凭据代理复用现有授权读取，原 exp 随 Actor 传递。PostgreSQL 维护命令拥有成员／审计事务，供应商 publish／disconnect 载荷集中于事件适配；forum／message 模型不依赖实时 SDK。替换实时层调整相应协议适配及装配，移除维护命令或实时路由后身份、论坛仍可独立验证。
