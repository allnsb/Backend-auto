## 3. 作品、分类和资源

### W01：卡是独立作品（已确认）

卡有独立的作品页面。此前讨论和参考图包含作品介绍、作者、分类／标签、版本、资源文件和下载入口。

下载后的资源交给其他工具使用。当前不要求网站直接运行卡或提供其运行环境。

具体文件格式、单文件大小、存储总量、版本保留和下载配额待定，不能直接套用某个候选后端的默认限制。

### W02：分类用于组织内容（已确认）

用户举例：

```text
男性向
└─ 轻前端
   └─ 纯爱
      └─ 某张卡
```

这表示分类路径，不要求每一级都成为独立经营、独立审核、独立管理员体系的论坛／分站。

分类最大深度、作品能否属于多个分类、标签与分类的边界待定。以上示例不代表所有作品必须恰好经过三级分类。

### W03：每张卡包含介绍、聊天频道和论坛（已确认）

1. **介绍与下载**：了解作品、查看版本、获取文件。
2. **聊天频道**：围绕作品持续聊天，固定采用 DC 式即时消息流。
3. **论坛**：按帖子／议题组织正式讨论，支持贴吧式回复串和即时式讨论；两种形式的新回复都即时出现。

用户最新明确的关系是：**每张卡里面同时有类似 DC 的聊天频道和论坛；频道固定即时式，论坛的讨论形式可选。** 不是整张卡在“聊天”和“论坛”之间二选一。

```text
一张卡（作品空间）
├─ 介绍、作者、版本与资源下载
├─ 聊天频道
│  └─ 固定即时式：连续消息流＋消息引用
└─ 论坛：帖子／议题列表
   └─ 讨论形式可选
      ├─ 贴吧式：主楼层＋一层楼中楼＋消息引用
      └─ 即时式：帖内连续消息流＋消息引用
```

上图表达产品关系，不规定必须把每张卡实现成一个独立 Discord guild、租户或独立后端实例。论坛模式由发帖者创建每个帖子时选择；每张卡允许多少个聊天频道和论坛仍待定。

三个区域需要有清楚的入口，不能只保留其中一个。最终是否用标签页、分栏或其他布局，待界面设计确定；用户提供的两张早期示意图用于表达大致体验。

上述是作品空间内的要求。普通论坛可直接使用通用讨论能力，作品通过明确关联接入；普通帖子无需作品记录。

### W04：资源存放和访问（目标已确认，细节待定）

作品资源需要存放、获取和权限控制。公共作品文件与私聊／群聊附件具有不同的访问语境，选型时要分别检查。

对象存储产品、CDN、下载链接时效、附件类型、资源审核和备份策略尚未定型。

## 4. 讨论结构、实时性和引用：三件不同的事

### D01：论坛支持两种可选的讨论形式（已确认）

以下两种形式用于独立普通论坛及作品关联论坛。卡内聊天频道始终采用即时式，不参与这项二选一；作品内介绍、聊天频道、论坛三个区域仍同时存在。普通论坛不要求先创建作品。

| 形式 | 内容结构 | 实时性 | 回复关系 |
|---|---|---|---|
| 贴吧式回复串 | 讨论帖 → 主楼层 → 一层楼中楼 | 主楼层和楼中楼的新回复都即时出现 | 可以引用具体消息 |
| Discord 式即时讨论 | 同一会话内按时间连续排列消息 | 新消息即时出现 | 同样可以引用具体消息 |

这里的“正式讨论”不表示发帖后等待刷新。也不能再把所有正式讨论一律解释成没有楼中楼的平面消息流。

**选择规则（2026-10-28 已澄清）**：发帖者在创建单个帖子时选择贴吧式或即时式。这是当前明确要求，不再将选择者和选择粒度列为待定。

**期望增强**：最好还能让不同读者对同一个帖子各自选择贴吧式或聊天式视图。优先满足发帖时选模式；个人切换视图是否纳入首发、如何与帖子规则配合仍待定，不能将这一增强当成已完成或首发硬性要求。

发帖后能否更改帖子模式、谁有权更改及其对历史内容的影响仍待定。工程上建议区分帖子模式与个人显示偏好，并保持同一帖子内容的单一权威来源；这是设计建议，不等于已经选定具体字段或后端。

### D02：楼中楼只嵌套一层（已确认）

```text
讨论帖
├─ 主楼层 A
│  ├─ 子回复 A1
│  ├─ 子回复 A2，引用 A1
│  └─ 子回复 A3，引用 A2
└─ 主楼层 B
   └─ 子回复 B1
```

A2 回复 A1、A3 回复 A2，不会产生更深的视觉缩进；它们仍处于主楼层 A 下的同一层。

“属于哪个主楼层”和“实际引用哪条消息”是不同关系，后续实现必须能表达这一区别。具体字段、索引和数据库方案尚未指定。

### D03：回复采用 DC 式消息引用（已确认，最新纠正）

用户明确要求：**像 DC 一样引用消息，而不是只显示贴吧式“回复 @某人”。**

- 回复应指向具体原消息，而不只是某个用户。
- 卡内聊天频道，以及论坛中的贴吧式楼中楼和即时式讨论，都需要这种引用能力。
- 楼中楼结构可以像贴吧，但回复展示不照搬图片里的“回复 用户名：正文”。
- 引用不会自动创建新的嵌套层级。

以下是上一轮提出的交互草案，核心引用需求已明确，具体呈现和操作细节仍可调整：

> ↪ 原作者：被回复消息的内容摘要……  
> 当前作者：这条回复的正文。

草案包括显示原作者与原文摘要、点击引用定位原消息、必要时展开所属楼层。摘要长度、图片／文件引用样式、跳转动画等没有最终定稿。

### D04：引用、提及和通知分别处理（待定规则）

“引用某条消息”与“@某个人”不是同一个动作。用户要求引用不能被单纯 @ 替代，并未要求删除所有 @ 功能。

以下还未决定：引用是否默认提醒原作者、是否可关闭该提醒、能否同时引用和 @、是否支持多条或局部引用。

### D05：讨论的其他边界（待定）

- 排序、分页、楼中楼默认展开数量、热门楼加载方式。
- 帖子发布后能否修改模式，修改是否改变数据组织、默认交互及历史链接。
- 读者个人切换视图的首发优先级、适用范围和显示规则。
- 跨楼层、跨帖、跨会话引用是否允许。
- 原消息被编辑、删除、撤回或失去可见权限后，引用如何显示。
- 点赞、表情回应、置顶、锁帖、精华、订阅等功能的首发范围。

## 5. 即时聊天范围

### I01：需要完整聊天体验（已确认）

卡内聊天频道、私聊和群聊均在范围内。卡内聊天频道固定即时式，与该卡的论坛并存；论坛也有即时式讨论选项，不能因此把论坛和聊天频道合并成同一个区域。不能把“有 WebSocket 推送”或“有站内通知”直接当成满足完整 IM 体验。

此前整理还包含全站闲聊；其频道组织和是否首发需要复核。

### I02：复用优先（已确认）

希望复用现成 IM 后端及其能力，减少自行实现聊天协议、协议转换和重复事件转发。多套后台应能接入统一的账号和权限体验。

2026-10-26 用户最初明确选择 OpenIM 作为 IM 后端，随后认可 BBS-GO 地基路线并要求建立独立目录。论坛实时事件路径、权限同步与具体接口仍待验证；当时选型不表示已经部署、迁移或完成集成。

同日源码审查后，用户要求“深度搜索下别的代替”。因此重新比较 IM 引擎、协议服务器和社区聊天后端，OpenIM 不再作为本次替代调查的不可变前提。

在 2026-10-26 那轮调查中，用户进一步明确：当时要找的是 **OpenIM 本身的替代 IM 后端**，保留作品／论坛内容业务。当时优先比较频道、私聊群聊、历史和多端同步引擎，完整社区产品只作次级参考；该范围已被 2026-10-28 的整体重新选型要求更新。

2026-10-26 的阶段决定为“先换 OpenIM”，并对 MongooseIM 与 Tinode 选择“都试试”。当时保留 BBS-GO，固定两个候选版本开展隔离试验；这不等于完成业务接入或迁移。

2026-10-28 用户明确要求“不要被上下文污染”“从头开始选用方案”。因此上述技术选择不再是当前约束：论坛底座、IM 引擎、实时层及自定义内核路线一起重选。优先复用是产品工程偏好，不等于必须复用此前已拉取的某个完整项目。

同日后续用户表示“行吧那就我们自己搞?”。当前按自研业务内核方向继续细化，I02 的复用优先也适用于成熟实时组件和可适配的开源业务逻辑，不再预设必须采用完整 IM 后端。聊天产品业务仍须逐项实现或复用并验证；具体组件和首发清单尚未决定。

完整性评估需要检查历史消息、断线补拉、未读、多端同步、成员管理、消息编辑／删除、通知、附件等能力。这些是评估清单，**每项的首发优先级和具体行为尚未全部确认**。

没有明确要求语音通话、视频通话、屏幕共享、跨站联邦、机器人平台或强制 WebTransport；不能因为希望“像 DC”就自动纳入全部功能。

## 7. R18 开关与隐私

### V01：单站开关，替代独立分站（已确认）

- 不保留此前材料里的独立分站设计，改用类似 R18 的开关。
- 关闭时，相应作品在列表、搜索、推荐／发现等入口**完全不出现**，不是显示标题、占位卡片或模糊封面。
- 该规则不扩展为逐条筛选聊天中的文字、图片和视频；用户此前明确不处理这部分。

待定：关闭时通过旧链接直接访问作品的表现、作品元信息／引用预览的处理、默认开关状态、修改资格、标记与审核流程。上述待定项不能被现有分站文档的默认值自动填补。

### V02：服务端处理消息，传输、存储与备份加密（已确认）

用户选择的是：**服务端可以处理消息，但严格限制访问、保留期限和管理员权限**。2026-10-28 再次明确选择“保留服务端处理：HTTPS/WSS＋存储和备份加密，严格控制管理员访问”。

- 不把端到端加密设为当前强制条件。
- 客户端与公网服务之间必须使用加密传输：HTTP API／文件访问使用 HTTPS，WebSocket 使用 WSS；不使用明文 HTTP／WS 暴露用户通信。身份验证及数据访问控制同样必须落实。
- 存储与备份加密是明确要求，不能只做公网 TLS；含隐私数据的数据库、附件及其派生存储需要纳入覆盖范围。
- 私聊、群聊和附件不能因为有一个可访问链接就被默认认定为满足隐私要求。

工程边界见 [加密边界与版本策略](加密边界与版本策略-2026-10-28.md)：内部链路 TLS／证书验证、存储及备份覆盖、密钥隔离、日志脱敏和管理员审计。它是规划，不表示已经配置或验收；具体供应商、字段加密方式、各类内容的保留天数、用户删除与备份清除范围、管理员何时可以查看消息、审计细则及导出仍待定。

## 8. 性能、运维和选型评估

### N01：规模目标与验收指标分开（已确认目标，指标待定）

超过 3 万同时在线是当前目标。还没有确定同负载下的最终硬件配置、持续消息写入量、投递量、单个热门房间在线人数、活跃讨论数量和延迟 SLA。

2026-10-26 补充关注：用户提出单个帖子／线程希望能超过 DC 式 1,000 成员限制的可能性。选型需分别检查加入／关注成员、累计参与者与当前在线订阅者的规模，不能直接继承候选项目的 1,000 人默认上限作为产品要求。具体人数与负载尚未决定，也不代表已确认无限容量。

此前合伙开发者提供的 Fluxer 数据属于对照材料：3 万讨论帖、4,000 活跃线程、2,500 同时在线、全服每秒 100 条消息，P95 接近 0.5 秒。用户确认测的是 **Fluxer 本体**。这不是本项目已达成的数据，也不是用户已经接受的最终性能指标。

2026-10-30 整体优化继续深查同类实现并做原版回测。0.5.1 复用 pgx 合并单请求写批次，加入可配置写事务预算，固定总连接数的分池候选未采用；服务器与独立压力机有增加余量的可能，提升倍数未经生产测试。原版二进制回测存在明显波动，另有一轮 25 次目标实时投递缺口，原始失败保留并补诊断，不能记成已定位或已修复。最新取舍、全部缺口和范围见 [整体优化对照](整体优化与写预算对照-2026-10-30.md)。

2026-10-29 用户再次明确：容量评估要覆盖**多个帖子同时很热、每帖多人收发**，并持续区分贴吧式帖子、即时式帖子和固定即时频道。贴吧式也要测主楼／一层子回复／具体引用及实时接收；不能用单热点或仅 API 写入代替多热点与广播，也不能把实时组件的 channel 当成已实现的产品固定频道。未实现形态在对应阶段补业务与负载验收，不用改标签或只测相同底层协议冒充完成。代码变动继续同步注释、契约和文档。

2026-10-30 用户批准先完成 P3 并统一验证，确认固定频道首版继承论坛成员。0.5.0 已实现三种讨论形态并记录 960 个真实 WSS 客户端的三个 60 秒混合档；写入率、读取率和投递率分别核对。400/s 写入档完成不代表已测得全站极限，高档 23144 次容量拒绝全部保留；[P3 证据](P3讨论模式与固定频道-2026-10-30.md)不改变原三万以上同时在线目标或 Q08 待定的正式指标。

### N02：长期可维护和可复用（已确认方向）

- 优先比较维护活跃度、安全修复、版本升级、开放接口、插件／扩展机制和 SDK。
- 核对服务端、SDK、管理端和客户端各自的许可证及开源／商业功能边界；“仓库公开”不能替代核对。
- 2026-10-26 用户明确选择：深改后的代码是否公开**暂不决定，开源与闭源两条路线都比较**。不能预设接受 AGPL 的网络源码义务，也不能因此提前排除 AGPL 项目。
- 用户偏好现代、性能和安全表现好的技术栈；2026-10-28 进一步明确希望最新潮的技术栈和版本，随后明确选用 Go。数据库等配套仍待落实，不将现代性偏好解释为接受预发行生产部署。
- 讨论过 PHP 安全事件、Rust／Go／Java 等语言和 WebTransport，不等于已经排除所有某语言项目或锁定某个协议。
- 已明确接受并计划深度魔改；要评估数据模型可改性、接口与 SDK 可扩展性、权限扩展、测试覆盖、上游安全更新合并和版本迁移。减少无必要改动与愿意深改并不矛盾。
- 避免只为追求新技术增加单人无法长期维护的组件；深度分叉的维护代价应列出，不能据此擅自排除用户明确接受的深改路线。
- 2026-10-28 用户追问能否边写边借鉴其他产品的部分逻辑。复用范围不局限于完整成品或基础设施；可比较直接使用组件、移植业务模块及其测试、参考公开行为后实现。具体来源尚未选定，工程上需核对许可证、依赖、数据与授权假设，不能未经验证承诺固定比例的工期缩减。
- 按用户提供的架构原则保持单一职责、清楚接口和明确状态变更；业务尽量不依赖具体框架、数据库或 UI，避免循环依赖、过度拆分和空泛抽象。改动尽量局限于相关模块，并检查外部服务替换与模块移除的影响。

这些选型方向不能被简化为“语言更新就更安全”或“用了 Rust 就一定比其他后端快”。

### N03：自建与复用的验收边界（工程建议，标准待定）

用户追问自行实现后能否保证安全和性能。当前没有已验证的零漏洞或具体容量承诺；复用成熟代码也不能自动继承原产品的整体结论。

- 安全验证重点包括越权读取／写入、可信作者、私密历史、引用与附件访问、已有连接撤权、管理员访问范围与审计；按实际变更做回归、依赖检查和必要的独立审查。
- 性能验证应固定硬件、数据和写入／投递负载，覆盖热点扇出、慢客户端、断线重连和恢复，记录端到端 P95／P99、错误率、内存及积压情况。
- 具体验收阈值、首发功能和生产部署仍待确定。减少无意义的防御性编程不等于省略必要授权和数据约束。

自定义业务内核的 [工作量预算](../../research/backend-effort-budget-2026-10-28.md) 已记录一名熟练全职后端、日常 AI 辅助、前端另计等假设：完整基础范围初估 24–39 人周，含余量约 7–12 个月。该区间尚未按实际业务模块复用与开发速度校准，不是交付承诺，也不是用户已接受的排期；原型和删减内测的范围另见该文档。

### N04：简洁编码与复用规划（已确认要求，具体方案为建议）

2026-10-28 用户要求先看有哪些代码可以直接复用并做大致规划，同时明确“代码要优雅”，不要 if 与循环层层嵌套，也不要在各处堆补丁式逻辑。

- 主流程平铺，前置条件与错误提前返回；集合匹配使用预建索引，避免双重扫描和请求热路径的 N+1 查询／逐条网络调用。
- 权限、校验和状态变更放在明确的职责边界；避免同义判断、重复校验、吞错、静默回退和层层记录同一错误。
- 不用过长布尔表达式、递归、零碎函数或过度抽象隐藏复杂度；必要的判断与单次遍历保持直白。
- 代码实现、相关注释、契约与文档同步维护；不能只读注释推断代码行为，应实际检查实现、调用和数据约束，并用相应测试核实。文档区分当前能力、历史试验与待验收项。
- 2026-10-29 用户明确要求独立评估需求与实现手段的合理性，不为满足字面要求强行交付。区分产品目标、技术假设与验收指标；对收益不足、成本过高或互相冲突的方案说明依据并提出调整，性能优化使用同条件对照验证，不预先承诺收益。
- 用户进一步明确：完整功能的代码体量可能上万行；这不是要求压低行数。开发期间持续联网寻找可复用的组件、局部业务逻辑与测试，而不只做一次初始调研。每个功能动手前、遇到难点和引入／升级依赖时检查官方资料与活跃仓库，记录版本、许可、取舍和验证，搜索与实际交付同步推进。

初步候选、来源文件、许可证、适配边界和分阶段建议见 [后端复用清单与粗规划](../../research/backend-reuse-plan-2026-10-28.md)。该清单是工程建议与检查记录，不是依赖已引入、许可清点已完成、业务已实现或技术栈已确认的证明。

### N05：技术现代性与版本维护（偏好已确认，执行方式为建议）

用户明确希望采用最新潮的技术栈和版本，不因已有研究、目录或代码把项目固定在旧方案。Go 与 Rust／Axum／Tokio／SQLx 对照后，用户明确选择 Go，后续沿 Go 主栈落实配套；Rust 对照保留为历史材料。
