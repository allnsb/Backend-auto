# 多个热帖、贴吧式回复与真实 WSS 扇出

日期：2026-10-29（Asia/Taipei）。本报告保留 HTTP 0.4.2 的历史测量。本轮新增压测与验证，未修改生产写入算法、API 契约、迁移或依赖版本。

后续已采用缓存、Outbox 逻辑分区／通知，并修复每流等待上限；当前 0.4.3 结果与代价见 [后续报告](缓存分区与准入修复-2026-10-29.md)。本文原数字和当时候选状态不回写。

**结论：目前不能承诺“很多帖子都很热时也能轻松应付”。** 4 帖各 25 条／秒、各 128 人实时接收的三轮输入均完整成功；4 帖各 100 条／秒出现客户端需求缺口；16 帖各 25 条／秒在最终复核中已出现容量拒绝；16 帖各 100 条／秒三轮均大量拒绝，普通写入也受挤占。已提交消息的目标投递全部收到，不能把这个结果解释为全部计划输入成功。

原始聚合结果、三轮全部场景、预热、硬件和源码指纹见 [快照](性能基线/2026-10-29-multi-hot-fanout.json)。前轮 [单热点＋普通帖隔离](按流写入隔离与原因分析-2026-10-29.md)保留原测量范围，7.5–8.3ms 不代表多热点或广播容量。

## 算法和业务形态的实际状态

已完成的是三轮被采用的性能改进：小 CTE／pgx.Batch、全局有界写预算、按论坛／消息流局部准入。Keyset、强幂等、事务计数器和 Outbox／稳定事件 ID 继续沿用。用户／动作配额、LISTEN/NOTIFY、分区、UUIDv7、singleflight／缓存、读进度、变更日志与周期授权复查仍按各自证据和业务阶段评估，不能说“所有算法都改完”。完整 [采用状态](../../research/algorithm-selection-2026-10-29.md)与研究候选分开维护。

| 产品形态 | 当前实现与本轮覆盖 |
|---|---|
| 贴吧式帖子 threaded | P2 已实现；本轮实际提交主楼、引用主楼的子回复、引用子回复的子回复，并校验根楼和具体引用独立、一层结构、实时多人接收。 |
| 即时式帖子 | P3 尚未实现对应可创建模式和完整业务契约；本轮未冒充已测。 |
| 产品固定即时频道 | P3 尚未实现业务对象／入口和权限生命周期；底层 PUB/SUB channel 不等于这个产品功能，本轮未冒充已测。 |

P2 后端 A01–A08 已完成；当前是 P2 之后的性能专项，P3 尚未开始，P6 正式容量／上线验证仍未完成。贴吧式的新内容本来就实时，不能把“实时收发”等同于“即时式帖子”。

## 负载与测量方法

- 开发机 AMD Ryzen 7 6800H，8 核／16 逻辑处理器，物理内存报告 16312721408 字节（约 15.19GiB）。Go 1.27.3、GOMAXPROCS=16；API、负载生成器与 SDK 回调在同一个 Windows Go 进程，原生 Centrifugo 6.10.2 在同一台 Windows 机器；PostgreSQL 18.6 在 Docker Linux 临时内存存储。没有隔离客户端和服务端的 CPU 成本。
- 48 个贴吧式帖子、12384 条预置 1KiB 消息；1025 个不同的本地账号及 RS256 subject，真实 HTTPS／TLS 1.3、HTTP/2、可信 JWKS 验签、成员查询和原生 outbox 消费。测试仅使用合成数据，没有接真实 IdP。
- 4 个热帖各 128 个独立身份／WSS 连接，共 512；或 16 帖各 64 个，共 1024。顺序建立连接，建连不计入消息吞吐。热帖写者轮换同帖的这些身份，不能把一个用户的多条连接称为多人。
- 每帖固定计划 25／100 次写入每秒，32 个写工作者；普通 32 帖另保持历史读取 100／秒、32 个工作者，以及写入 25／秒、8 个工作者。每档预热 3 秒、计量发起窗口 12 秒，JSON 单列预热；不改成闭环吞吐来隐藏未发出需求。普通读取请求返回至多 50 条历史，本轮未叠加热帖翻页风暴。
- 写入按三种负载轮换：普通主楼、在原主楼下引用主楼、在同一主楼下引用子回复。每条正文 1KiB，分别保留 RootID 与 QuoteID；三种负载的实际提交数量在快照中单列。
- API 池 16、全局写事务预算 12、每计数器局部预算 2、总接纳 256。采样使用独立 1 连接统计探针及 1 连接只读聚合观察池，每 503ms 观察池／锁／outbox 与 Go 堆。观察也有成本，理论读取余量不是独占保留池。
- 原生服务沿用一个 outbox 分区、20ms 轮询、内存 broker、history size=2／TTL=60s，未为压测更改生产默认或取消鉴权。SDK 使用官方 v0.13.0，连接凭据可经真实 HTTPS 刷新；这些短场景的计量窗口中实际没有刷新、重连或订阅错误，不能宣称已测刷新／重连风暴或慢读者。

接收延迟从 **Go 客户端发起 HTTPS 写请求，到相应 WSS 的 SDK 回调开始**，两端用同一个 Go 单调时钟。它包含客户端／准入／事务／原生消费／WSS／SDK 调度，不是仅提交后推送耗时，也不包括浏览器绘制。

停止发起后先等已发出的 HTTP 请求完成（单请求时限 5 秒），核对数据库，再最多等 30 秒收敛 outbox 和客户端回调。delivery_drain_ms 只计最后这段等待，不是窗口后的全部时间；window_received 单列窗口内实际接收量，避免把尾部收敛吞吐算进窗口。

数据库按请求 UUID 核对作者、正文、根楼／引用与每流连续序号，并核对成功 HTTP 结果。WSS 逐订阅者校验同一事件 ID、消息序号与规范化内容；JSONB 会重排键，所以先解码为消息结构再校验摘要。目标投递数＝实际提交的热帖消息×对应实际订阅者，未发出和 503 不计作已提交。接收分位数与缺口一起报告，完整性字段不代表所有计划输入成功。

## 最终夹具结果

前两轮条件相同；之后修复测试清理中保留已结束场景接收映射的问题，并清掉报告不需要保留的逐消息关联表，负载和生产代码不变。第三轮用最终夹具复核。三轮均完整保留，不能将其波动全部归因于清理改动，也不能只挑前两轮更好的 16 帖结果。

下面为最终夹具的 12 秒计量窗口；普通写计划均为 300 次。拒绝均为容量 HTTP 503，未发出是在客户端工作者不足时发生，两者分开：

| 热帖数×每帖订阅者 | 每帖计划写／秒 | 热帖计划／成功／未发出／503 | 发起到接收 P95 | 普通写成功／未发出／503 |
|---|---:|---:|---:|---:|
| 4×128 | 25 | 1200／1200／0／0 | 39.22ms | 300／0／0 |
| 4×128 | 100 | 4800／3070／1730／0 | 577.43ms | 300／0／0 |
| 16×64 | 25 | 4800／4597／0／203 | 905.09ms | 291／1／8 |
| 16×64 | 100 | 19200／3566／300／15334 | 1581.74ms | 72／0／228 |

最终四档实际接收分别为 153600、392960、294208、228224 次，均与已提交消息的目标数相等。高档中约八成已发出的热点写被拒绝，普通写 228/300 也被拒绝；这档需求明确没有满足。

前两轮 4×128／25 的接收 P95=40.35／40.60ms，也没有输入缺口。4×128／100 只完成 3033／2994 次热点写，另有 1767／1806 次未发出，接收 P95=628.75／606.59ms。16×64／25 在前两轮全部输入成功、接收 P95=446.20／429.17ms，最终复核却有 203 次热点 503，不能把这一档判成稳定容量。16×64／100 前两轮热点 503=15135／15313，普通写 503=248／246，接收 P95=1576.87／1521.47ms；超载结论重复出现。

三轮计量总计：108000 次计划需求，101729 次实际发出，55014 次成功、46715 次容量 503，另有 6271 次需求未发出。数据库实际提交 40614 条消息，另有 14400 次成功历史读取；3228288 次目标订阅投递全部匹配，未发现载荷／事件身份冲突、重复或乱序。所有场景排空后 outbox 为零。这些完整性结果不抵消失败的输入需求。

## 暴露的限制与后续判断

1. **按流隔离还不是全局公平调度。** 多个热流仍能占满共享的 256 个接纳位置和全局预算，普通帖没有独立保证；最终 16×64／100 的普通写只成功 72 次。
2. **不能只怪单帖行锁或 Outbox。** 最终高档 API 池采样可到 16 个连接；取得事务前 P50 约 906ms，事务内 P50 约 20ms，采样 outbox 峰值 14、最终排空。该时长包含身份／资源查询、局部与全局排队、取连接；源码显示容量拒绝前仍会做身份及权限查询。证据支持优先检查共享准入／取连接压力，不能据这些聚合数据精确拆分 CPU、Docker 往返和每个队列的成本。
3. **每帖热点与广播成本需要一起看。** 4×128／100 即使没有 503，也有约 36% 的需求未发出，不能记成扛住每帖 100 条／秒。1024 个连接和同机回调校验也消耗资源，当前数字不能作为独立生产服务端的极限。
4. 下一轮应优先评估按流有界等待／公平接纳和被拒绝请求的池成本，保留私有资源拒绝边界及事务内重新鉴权。扩大连接池、加缓存、分区或通知唤醒都要有对应对照，不能为“全部算法都做完”强行采用。

P3 对即时式帖子与固定频道分别补业务实现、权限、历史／引用及混合负载；贴吧式的热帖翻页／楼层分组读取、慢读者、重连和长时间稳定性继续单列验证。P6 仍需在约定硬件、真实磁盘／网络与负载目标下验收，不能用短场景得出三万活跃在线结论。

## 复用、运行与验证

本轮复用现有 RS256／JWKS 夹具、有界到达调度器、pgx tracer、官方 Centrifugo 原生消费者／SDK 及聚合积压视图。首次采样误用业务角色读取 outbox，被数据库权限拒绝；修正为已有只读观察账号后再测，API 权限未扩大。修复清理逻辑时同步补注释，旧场景在关闭后丢弃回调并释放映射。没有添加运行依赖、手写发布 worker 或生产诊断接口。
