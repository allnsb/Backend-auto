# 当前代码本地性能基线

日期：2026-10-29。P2 后端完成后的首次量化性能基线，API 契约仍为 0.4.0。结论：本机分散读写在 32 并发下达到约 1244–1395 个 HTTPS 请求／秒；同一热点帖写入约 218 次／秒，P95 约 244ms。热点写入与连接池等待是当前应优先研究的方向，三万活跃在线容量尚无验收结论。

后续已修改回复持久化路径；本文保留首次测量的历史数字与当时调用分析，不再代表当前实现。最新六轮对照、收益与 P50 退步见 [热点写入优化与对照](热点写入优化与对照-2026-10-29.md)。

## 已检查的热路径

**分页没有随当前位置明显变慢。** 当前 ListMessages 使用 position > after、ORDER BY position、limit+1；HTTP 每次固定执行本地用户、资源授权与页面三个查询，没有逐条网络查库。超过 19000 条后的实际 EXPLAIN ANALYZE 使用 messages_stream_id_position_key 范围索引，取 51 行；再按 forum_entries 主键关联。该次 SQL 执行 0.336ms、167 个共享缓存命中、零共享块读取，是缓存热状态，不能当成全链路延迟。

topics 和 forum_members 在本数据集很小，计划选了顺序扫描；不能因此对大表预判全表扫描。SQL 计划中的索引 Nested Loop 仍是一次数据库请求内的关联，不是应用逐条发起 N+1 请求。计划读取方法按 [PostgreSQL EXPLAIN 文档](https://www.postgresql.org/docs/18/using-explain.html)核对。

**单帖写入会串行排队。** Reply 的 FOR UPDATE OF s 在事务中锁同一消息流，持有到提交，保证严格序号和幂等一致性。不同帖可以使用不同序号行并行。当前无引用回复按代码路径约有九次数据库往返（含用户读取、BEGIN／COMMIT），这些不是九次连接获取；事务会持续占用一个池连接。热点结果与这条持锁路径相符，但本轮没有独立采集锁等待／CPU profile，不能把全部尾延迟都归到一种原因。行锁行为依据 [PostgreSQL 锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)，没有通过移除排序锁换取吞吐。

**32 并发时池等待明显。** 默认池上限为本机逻辑 CPU 数 16。32 并发历史首页的计量期间有 5983 次空池获取，累计等待约 19.20 秒；分散写入累计约 6.20 秒，热点写入约 41.75 秒。这些是多个请求重叠的等待总和，不是场景墙钟耗时。需要明确每实例／数据库总连接预算，再比较不同池上限；只增大池不能解除同一行的写入串行化。

**实时与积压还有独立成本。** 当前模板只有一个 outbox 分区，轮询间隔 20ms，业务提交之后仍需消费、broker 和 WSS 发送。本轮未计时这段链路。realtime-status 的精确 count／min 聚合会遍历待消费记录，适合作为低频诊断；大积压下的查询成本和告警抓取频率也需后测。

## 下一步性能工作

先保留此基线，针对热点事务测量锁等待和数据库往返，评估缩短持锁区间、合并可安全批量执行的语句；保持顺序、引用授权、幂等和正文／outbox 原子性。随后按总连接预算比较连接池配置，再测混合读写、多用户权限、大历史量、真实磁盘及跨主机环境。

WSS 另按在线人数、发消息频率、每消息订阅人数、重连频率和故障恢复负载测量吞吐、P95／P99、错误率、CPU／内存和积压。三万连接的空闲维持、普通 HTTP RPS 和三万用户活跃广播是不同指标，不能互相换算。CPU 优化前使用 [Go profiling](https://go.dev/blog/pprof) 获取证据，不凭语言或框架名称估计性能。

## 重跑与边界

在 backend 目录运行：

```powershell
pwsh -File deploy/postgres/test.ps1 -GoExecutable go -TestTags 'integration,performance'
```

该标签只选择 TestPerformanceBaseline，功能／故障验收仍使用对应的 integration／realtime／cluster／acceptance 命令。原始结果写入忽略且受限的 runtime/backend-postgres/performance.json；脚本完成后移除专用测试容器和网络。夹具没有变更业务实现或依赖，相关源码见 [性能场景](../backend/internal/postgres/forum_performance_test.go)。

这是固定在途并发的单轮短测试，不控制外部到达速率，不涵盖外部排队；600 次写入的 P99 尾部样本较少。客户端与服务端竞争同一 CPU，数据库位于临时内存文件系统、数据与权限集较小且缓存热，生产磁盘、数据规模和真实网络均会改变结果。它用于比较后续改动，不能直接作为容量上限或线上 SLA。

最初一轮预热因 httptest 的 HTTP/2 ALPN 配置不一致失败，未产生计量数据；根据当前 Go 标准库实现修正了基准夹具，未改业务服务。上表只记录修正后完整成功的一轮。性能标签编译、默认回归与全标签静态检查通过。
