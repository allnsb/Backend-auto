# 同类社区优化策略与本轮取舍

> 历史时点记录：当前 0.4.5 已移除逐条通知并改每流单活动写者，最新独立进程／磁盘对照见 [通知锁修复](独立进程压测与通知锁修复-2026-10-29.md)。本报告原始结果与失败需求保留。

日期：2026-10-29（Asia/Taipei）。当前 HTTP 契约 **0.4.4**，依赖版本与六项迁移不变。本轮按用户要求调研相近论坛／聊天系统，再逐步实现和实测。

**最终保留：同批发送两条独立的流锁／幂等查询、重试结果一次读取、引用校验只取元数据。借用等待名额与动态份额两个候选没有保留，准入已恢复原策略。** 确认的是减少驱动调用和不必要的数据读取；当前同机测量有显著漂移，不能承诺稳定的吞吐增幅或生产容量。

全部八轮多人 WSS、六轮短 API、预热、失败需求、源码和冻结二进制指纹见 [聚合快照](性能基线/2026-10-29-peer-optimization.json)。第一方来源、日期、许可证与采用边界见 [来源索引](../../research/peer-community-optimization-2026-10-29.sources.json)。此前 [0.4.3 缓存与分区](缓存分区与准入修复-2026-10-29.md)保留历史时点。

另参考 [Kubernetes APF](https://kubernetes.io/docs/concepts/cluster-administration/flow-control/) 的有界队列／借用思路做接纳实验。它是基础设施参照，不是类似社区产品；本轮没有采用完整 APF、分布式公平调度或用户业务配额。

## 实际保留的代码

变化集中于 [PostgreSQL 适配](../backend/internal/postgres/forum.go)：

1. 流锁和幂等读取放在一个 pgx.Batch 内，仍是顺序执行的两条独立 SQL。锁后读取使用新的 READ COMMITTED 语句快照；没有合并成同条 CTE。
2. 幂等命中时，同一次查询取得原完整消息与请求摘要，核对内容后复用结果。
3. 同帖引用校验继续最多一次集合查询，只读取消息 ID 与根楼归属，不为验证存在性读取正文、作者和时间。

批次关闭并传播错误后才继续；业务正文、楼层、位置和 Outbox 的事务原子性保持，入队前权限检查与事务内重新授权保留。参考 [pgx Batch API](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.11.0#Conn.SendBatch) 与 [PostgreSQL 快照语义](https://www.postgresql.org/docs/18/transaction-iso.html)，并新增真实数据库实验：先观察跟随事务实际等待行锁，再让另一事务插入并提交，验证同批第二条语句确实读到新提交。当前 SQL 性质实验共五项。

串行探针的调用计数如下。它们是驱动调用分类，不是物理网络包数量；每类各 16 个计量样本，另有 1 次预热。

| 回复类型 | 原版 Query／Batch | 保留版 Query／Batch | SQL 语句总数 |
|---|---:|---:|---:|
| 无引用 | 6／1 | 4／2 | 均为 8 |
| 有引用 | 7／1 | 5／2 | 均为 9 |

也就是总调用组数分别从 7→6、8→7；不能称作 SQL 语句数量减半。保持查询的独立快照比追求表面上的“一条 SQL”更重要。

## 为什么没有保留借用与动态份额

原准入对每计数器最多接纳 12 个活动／等待命令，短突发容易快速被拒绝。第一个候选保留 256 总上限、192 共享区及给新／低占用计数器的余量，允许单计数器最多借到 64；第二个候选再按当前有请求的计数器数计算临时份额，竞争增大时只收紧新接纳，已有请求自然完成。

候选通过了边界、取消和状态清理验证，也把单帖 32 并发的 600 次无退避突发从原版仅 30 次成功改善到 600 次成功。但在固定到达率的持续输入中，出现了以下代价：

| 候选／两轮 | 4 帖各 100/s：客户端未发出／接收 P95 | 16 帖各 100/s：接收 P95 | 普通写计划完成情况 |
|---|---|---|---|
| 借用 | 901／435ms；976／444ms | 943／935ms | 两轮各档均 300/300 |
| 动态份额 | 1002／477ms；1283／549ms | 633／808ms | 最高档第二轮 299/300，另 1 次未发出 |

原版起始回测在 4 帖高档无客户端未发出、接收 P95 为 208ms，在 16 帖高档为 675ms。更长队列能吸收突发，却不能增加持续处理能力；客户端工作者被占用后，未发出的需求仍是未完成需求。动态份额第二轮的 1 次缺口是**客户端未发出**，不是服务器返回一个 503。

同时，本轮后段存在明显测量漂移，不能把候选所有退步都归因于策略本身。因此结论是“缺乏可控、稳定的净收益，暂不采用”，而不是证明借用或公平排队普遍无效。候选实现、二进制与原始结果保存在忽略的 runtime 审计目录；生产准入源码已经与本轮起始 0.4.3 文件逐字节核对相同。

当前仍是每计数器 2 个活动写者、12 个活动／等待命令；池 16 对应全局 12 个活动写事务，总活动／等待 256，两段等待共用 2 秒。容量 503 write_capacity_exceeded／Retry-After: 1 不变，重试复用原幂等键。这是单实例工程预算，仍不保证任意流数或多实例公平性。

## 测量条件与漂移核查

每轮相同的四档负载：4／16 个热帖，各 128／64 个不同身份的 WSS 订阅者，总连接数 512／1024；每帖输入 25／100 次每秒。普通读固定 100/s、32 个工作者；普通写固定 25/s、8 个工作者。每帖 32 个发送工作者，不自动重试；预热 3 秒，计量发起窗口 12 秒，再等待 HTTP 结果并核对数据库、以最多 30 秒排空投递。

48 个 threaded 帖子、12384 条 1KiB 种子消息、1025 个不同 RS256 subject；实际发送主楼、引用主楼的子回复和引用子回复的子回复。API／压测器／SDK 共用 Windows Go 进程，原生 Centrifugo 在同机，PostgreSQL 为 Docker Linux 临时内存存储。Ryzen 7 6800H，8 核／16 逻辑处理器，约 15.19GiB 物理内存，API 池 16；版本为 Go 1.27.3、Centrifugo 6.10.2、SDK 0.13.0、PostgreSQL 18.6。

运行次序为：原版 → 仅 SQL → 借用两轮 → 动态份额两轮 → 恢复原准入后的最终 SQL 版 → 同一个原版二进制末尾回测。原版二进制与测量代码在实现前冻结，输入及客户端数不变；流 UUID 和四个数据分区的碰撞分布没有固定。这不是随机交错或独立硬件上的容量试验。

短 API 档另使用 28225 条种子消息，真实 HTTP/2／TLS 1.3、RS256 和 PostgreSQL TLS；此档不启动消费者。所有下表写入行均为 600/600 成功，吞吐只计算成功响应，P95 只计算成功请求。

| 短 API 场景 | 起始原版 | 仅 SQL 首轮 | 最终 SQL 复核 | 末尾同一原版 |
|---|---:|---:|---:|---:|
| 32 帖分散写／32 并发，成功每秒 | 1509.7 | 1658.4 | 1164.8 | 1006.4 |
| 对应成功 P95 ms | 26.74 | 21.65 | 34.66 | 40.16 |
| 单帖写／8 并发，成功每秒 | 333.0 | 410.5 | 294.1 | 267.6 |
| 对应成功 P95 ms | 26.31 | 21.85 | 33.10 | 32.99 |

首轮有局部改善，最终绝对吞吐却下降；同一旧二进制在末尾也明显变慢，分散写下降约 33%。这支持“测量条件随时点变化”，但尚未定位具体原因，不能未经测量就归咎于温度、CPU、内存或某个进程。两段邻近对照也不足以给出稳定百分比收益；当前保留的是减少调用和数据读取的确定变化，吞吐收益仍待隔离环境验证。

这四个时点的上述热点输入均已发出，没有客户端热点未发出；借用／份额候选的未发出数量另在前表和 JSON 中保留。最终保留版每档普通写均为 300/300，普通读均为 1200/1200，4／16 帖低档热点输入均成功；最高档热点仍约 77.8% 被拒绝。末尾原版的普通写最高档仅 298/300，另 2 次未发出；其 16 帖低档也有 177 次热点容量拒绝。不能据本轮宣称稳定容量提高。

最终短 API 的单帖 32 并发仍只有 34/600 成功、566 次容量拒绝；原版起始为 30/600、570 次拒绝。因此，**这轮没有解决单热点无退避突发接纳问题**，也没有把恢复原准入包装成突发优化。

八轮计量共计划 288000 次需求，实际发出 283743 次，成功 159957 次、容量 503 共 123786 次，另有 4257 次未发出。成功包含 38400 次历史读取和 121557 条已提交消息；9601792 次目标订阅投递全部匹配，无缺失、载荷／事件身份冲突、重复或乱序，各阶段最终 Outbox 为零。正确性验证成立，不抵消失败的输入需求，也不构成生产容量验收。

## 验证与未定位记录

最终采用组合的 integration,realtime,cluster,acceptance,algorithms 完整回归通过，PostgreSQL 包 **88.525 秒**：覆盖五项 SQL 性质、真实 65 秒消费中断／缓存过期、双节点恢复与撤权、分区阻塞隔离、幂等、授权、分页补读与事件合并。默认测试、全标签 go vet、模块校验、格式检查和六个 Linux／amd64 命令交叉构建通过；Go 产物未在 Linux 执行。govulncheck v1.9.0 对全标签含测试调用图未发现已知漏洞，官方库更新时间为 2026-10-27 21:16:18 UTC。

动态份额候选期间有一次完整测试进程仅以状态 1 退出，没有断言或栈信息；保留了原始日志。同源码逐项日志重跑通过，最终恢复原准入后的完整回归也通过。**该次退出的根因仍未确认，不能声称已修复。** 后续隔离测试需要保留进程退出、系统资源和测试阶段证据。

测试容器、专用网络和原生实时进程已核对清理。注释、OpenAPI 版本、运行说明、需求／接续文档和算法采用表已同步；历史报告不回写为当前收益。

## 下一步优先级

1. 分离客户端、API、实时服务与数据库测量，记录各进程 CPU／RSS、GC、数据库等待和分区积压；以交错次序比较原／新版本，补真实磁盘、尾页／冷页、慢读者、刷新／重连与长时间负载。先取得稳定证据，再宣称容量提升。
2. 明确突发成功率、等待上限与持续延迟目标，再比较有界公平调度或客户端按 Retry-After 退避并加抖动。不要仅增大等待队列；前端重试复用原键，未确认的本地回显不能当成持久化成功。
3. 若隔离测量确认同流事务仍为主要瓶颈，再评估跨请求小批处理；需验证每个请求的授权、幂等、取消与失败边界。本轮没有引入跨请求事务批次或改变强顺序。
4. P3 即时式帖子与产品固定频道、编辑／删除的版本化缓存失效、变更日志和周期授权复核仍按各自业务阶段实现。P2 后端保持完成，P6 生产容量、高可用和正式 SLA 尚未验收。

本轮最终业务改动只在 PostgreSQL 适配与既有契约版本；没有给业务类型增加框架依赖。替换数据库主要改适配，替换实时服务仍主要改事件适配；移除本轮读批次可恢复原逐次查询而不改变 API 或持久化模型。没有为优化新增服务层、按表接口或后台调度器。
