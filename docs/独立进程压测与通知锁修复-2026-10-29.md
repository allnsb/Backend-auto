# 独立进程压测与通知锁修复

日期：2026-10-29（Asia/Taipei）。HTTP 开发契约 0.4.5；依赖版本不变，新增第七项迁移。P2 后端仍已完成；P3 即时式帖子／产品固定频道与 P6 正式容量仍未验收。

本轮延续 [0.4.4 同类社区策略评估](同类社区策略与优化-2026-10-29.md)，先修正测量边界，再用实际数据库等待定位跨帖瓶颈。代码取舍按同条件输入、成功、拒绝、未发出需求及实际投递共同判断，不以更长队列冒充吞吐。

完整输入、预热与计量阶段、进程资源、各候选和失败记录见 [聚合数据](性能基线/2026-10-29-process-optimization.json)；第一方源码／文档、版本、许可与复用边界见 [来源索引](../../research/process-isolation-optimization-2026-10-29.sources.json)。本轮最终保留引用读批次、移除通知和单活动写者的组合；未采用只去通知却保留两个活动写者的中间组合。

## 根因：不同帖子的提交被通知锁串行化

旧第六项迁移为每条 Outbox 插入执行 `pg_notify`。PostgreSQL 18.6 的 [PreCommit_Notify 源码](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/commands/async.c)会取得 `LockSharedObject(DatabaseRelationId, InvalidOid, 0, AccessExclusiveLock)`，直到事务提交或回滚后才释放。通知按数据库隔离，使用的 database-0 对象锁却是全局共享的；把 scope 分到四个消费分区不会拆开这把提交锁。

本轮实际抓到同一个对象标签：`locktype=object,database=0,classid=pg_database,objid=0,objsubid=0,mode=AccessExclusiveLock`。七个 API 后端未获锁，另一个已获锁的后端正在等 `LWLock/WALWrite`。这与原版 16 帖负载中大量 `Lock/object` 采样、持锁后较长耗时相互印证。采样次数是多个时点的等待者数量之和，不是独立事务数量，也不是等待秒数。

这是已定位的一项跨帖瓶颈，不表示解释了全部延迟。Windows pprof 中阻塞控制管道／系统调用的样本与 OS CPU 时间不一致，本轮只把这些堆栈当辅助，不按其百分比断言业务 CPU 热点。OS CPU／RSS 与 API GC、堆和连接池分别保存。

## 实际修改与代价

1. **第七项迁移移除逐条通知触发器及函数**，保留同事务正文／引用关系／Outbox、相同 scope 路由和 0 控制＋1–4 数据分区。原生消费者继续使用已有 20ms 轮询，不新增通知服务或另一套投递链路。更新的配置不再设置 `partition_notification_channel`。这遵循 [Centrifugo 原生消费配置](https://centrifugal.dev/docs/server/consumers#postgresql-outbox-consumer)中通知可选、轮询独立的边界。
2. **每计数器活动写者由 2 改为 1**。一个流在同一 API 实例只持有一个事务连接；另一个等待同一行锁的写者留在本地准入队列。数据库仍维护跨实例权威顺序。每计数器共 12、全局共 256、共享 2 秒及池 16 对应全局 12 写者的其他预算保持，权限仍在入队前检查并在事务内复查。它不是硬隔离的读连接池，也不保证任意流数下公平。
3. **引用元数据加入锁后的读批次**，仍为独立 READ COMMITTED 语句。带引用的新回复由 5 Query＋2 Batch 变为 4 Query＋2 Batch，总驱动调用组 7→6，仍是九条 SQL；无引用回复仍为 4＋2／八条 SQL。它们不是网络包计数。相同 root／quote ID 只传一次。幂等重试仍优先返回原记录或冲突；带引用的重试会额外执行一次最多两项的元数据读取，当前取舍优先减少常规回复的持锁交互。

低负载下通知原本能立即唤醒，改轮询会增加等待。20ms 是轮询配置，不是端到端 SLA；实际延迟还包括提交、消费、网络和客户端处理。保留低负载退步和高档失败需求，不能只报告 16 帖中档的收益。

## 测量方式与对照

API 改为独立测试子进程；生成器与真实 SDK 客户端在父进程；Centrifugo 是另一个原生进程；PostgreSQL 18.6 在 Docker Desktop Linux 容器内。它们仍共享同一台 Windows 机器和物理资源，**不是四台独立机器或生产拓扑**。测试控制走继承的本地管道，生产 API 没有新增诊断端点。

使用每轮新建并清理的 Docker 磁盘卷，实际核对 fsync、synchronous_commit、full_page_writes 均为 on。不复用业务数据，不把内存盘的既有成绩直接作为本轮对照；磁盘卷仍受宿主／虚拟机缓存和本机磁盘影响，也未验证生产加密磁盘。

其余条件保持：Ryzen 7 6800H／16 逻辑处理器，Go 1.27.3，API 池 16，Centrifugo 6.10.2／SDK 0.13.0；48 个 threaded 帖、12384 条 1KiB 种子消息、1025 个不同 RS256 subject。4 个热帖各 128 读者或 16 个各 64 读者，每帖 25／100 次输入每秒、32 个工作者；普通读 100/s／32 工作者，普通写 25/s／8 工作者。每档预热 3 秒、计量发起 12 秒，无自动重试，再核对数据库和以最多 30 秒排空投递。根楼／引用主楼／引用子回复的子回复真实轮换；WSS 核对每个目标接收者的载荷、事件 ID 和消息顺序。

原版 API／生成器在改业务代码前冻结。对照次序为 A1 原版 → B1 仅引用读批次 → C1 加去通知（两活动写者） → A2 同一原版 → D1 单活动写者候选 → A3 同一原版 → D2 候选复核。A 使用六项迁移和旧消费配置；C／D 用第七项迁移和轮询配置，B 仍使用通知。API 生产差异有独立来源指纹。初始剖析轮启用 pprof 且用内存盘，收尾失败，保留但不混入这些比较。

这是逐步与交错对照，非随机化因子试验；每轮 scope UUID／分区碰撞不同。能检验本机已发现瓶颈与实际代价，不能给出普遍适用的固定收益百分比或三万在线结论。

三轮同一原版在 16 帖各 25/s 的热点成功数为 3250–3415/4800，接收 P95 为 759–932ms；最终两轮都完成 4800/4800，P95 为 73–87ms。最终每档普通写均 300/300、普通读均 1200/1200，热点与普通需求均没有客户端未发出。

最高档最终热点仅 3870／3781 次成功，仍有 15330／15419 次容量 503（约 80%）；接收 P95 为 1014／938ms。普通写成功 P95 为 198／192ms，虽然全部完成，仍不能称作普通写已完全隔离。不得把这些容量拒绝删掉，也不能把成功事件全部投递当作全部输入成功。

只去通知的 C1 曾提高 4 帖高档热点成功数到 4068，却有 195 次热点及 8 次普通写未发出，接收 P95 327ms；最高档另有 77 次热点与 8 次普通写未发出。因此该组合没有作为最终版。单活动写者两轮的 4 帖高档成功数较它少，但需求全部发出、普通流量完成且接收 P95 为 226／247ms，取舍明确保留。

A2 最高档还有 22 次热点、7 次普通写未发出；A1 最高档另有 2 次普通写未发出。完整 JSON 也保留各轮普通读未发出的需求。排队时没能发出的输入与服务器返回 503 分别统计。

**低档代价**：4 帖各 25/s，各版均 1200/1200 热点成功；原版三轮接收 P95 为 29.4／30.1／30.5ms，最终两轮为 38.2／39.7ms，增加约 8–10ms。不是所有场景都变快。

七轮计量合计计划 252000 次需求，发出 251642，成功 122953，容量 503 共 128689，另有 358 次未发出。共提交 89392 条消息，7147456 次目标投递全部匹配，无缺失、重复、载荷／事件身份冲突或乱序；各阶段最终 Outbox 为零。预热独立保存，不混入这些计量合计。

最终最高档 OS 采样中 API 的 CPU 秒／墙钟秒约 1.59–1.66，生成器约 2.65–2.75、Centrifugo 约 1.39–1.46；API 的采样 RSS 峰值约 60–61MiB，生成器约 311–314MiB。它们不是进程内存上限，1 秒级采样也可能错过瞬时峰值。PostgreSQL 本轮采集等待事件、配置与积压，没有单独归因其 CPU／磁盘时延。分离进程已能辨别开销归属，共用物理资源的限制仍在，后续应外移负载端再谈容量。

## 测试工具修复与验证

- 首次独立进程剖析的八个阶段均写出数据，收尾却失败：父测试的 `defer cancel()` 早于测试 Cleanup，提前终止了健康 API 子进程。改为按 Cleanup 顺序先停子进程、再取消其上下文；后续对照保留真实退出状态和独立日志。该问题与前轮尚未定位的候选进程异常退出分别记录，不把它当成前轮根因。
- 单活动写者切换暴露了测试夹具写死两个占位者的假设。占位器按实际局部预算取得名额，另用互不相同的计数器填满剩余全局预算；等待上限、取消释放、资源清理、陌生成员拒绝和排队后撤权的断言不放宽。中间失败日志保留。
- 新的实际数据库用例先写入尚未提交的根楼，观察跟随事务确实等待行锁，再提交前者；跟随引用必须读到新根楼。随后验证同键返回原结果、改成不存在引用时仍先报幂等冲突、失败后连接可继续使用。
- 第七项迁移在带积压的事务内先回退、再升级，验证原队列 ID／分区／载荷保留，触发器和函数确实移除；原生投递、恢复和控制撤权仍由实时及集群测试验证。

最终 integration,realtime,cluster,acceptance,algorithms 完整回归通过，PostgreSQL 包 89.774 秒；实际消费中断 67.15 秒，241 条积压发布及一条断连恢复、七页合并通过。分区隔离、双节点和单节点已有连接撤权仍通过，实测撤权不作为生产 SLA。默认测试、全标签 go vet、模块校验、Go 格式检查、六个 Linux/amd64 命令交叉构建和全标签含测试的 govulncheck v1.9.0 均通过，未发现已知漏洞；Linux 产物未执行。资源与文档一致性在最终聚合文件一并记录。

## 单帖突发与串行探针

另外用同一新磁盘夹具补原／新各一轮短 API 档，API 与客户端仍同进程、无 WSS 消费；它不与上面的独立进程多人扇出混算。完整结果包括首页／深分页及全部并发档，单轮短测不能证明稳定收益。

| 场景 | 原版 | 最终版 |
|---|---:|---:|
| 32 帖分散写、32 并发：600 次成功吞吐 | 475.3/s | 1107.7/s |
| 单帖 8 并发：600 次成功吞吐／成功 P95 | 166.4/s／49.9ms | 161.6/s／54.8ms |
| 单帖 32 并发、600 次无退避：成功／容量 503 | 28／572 | 23／577 |
| 该突发的成功 P95 | 101.0ms | 123.9ms |

分散写在该轮改善，单帖 8 并发及无退避突发略退步。**本轮没有解决单热点突发接纳问题**，不通过扩大队列掩盖这一点。后续若设计客户端重试，应遵守 Retry-After、加入抖动并复用原幂等键，还需测重试总量、最终成功率和总等待，不能直接将本地回显记作提交。

实际串行探针每类 16 个计量样本、另一次预热：无引用均为 4 Query＋2 Batch／8 SQL；引用从 5 Query＋2 Batch／9 SQL 变为 4 Query＋2 Batch／9 SQL。引用回复总时长中位数 8.16→7.93ms、观察到的锁后至提交中位数 5.79→5.25ms；无引用总时长 8.02→7.99ms。样本很短，仅确认调用分类与当前探针，不据此给生产收益承诺。

## 升级边界与下一步

从六项迁移升级到七项时，先确认全部原生消费者已经轮询且仍为五个相同逻辑分区／同名消费组，再在短维护窗口执行显式迁移。第七项不改路由也不丢积压，无需为了这一步排空；DDL 取锁超过 5 秒会失败并回滚，可避开长事务后重试。旧配置仍监听通知也会继续轮询，可先迁移再移除该可选配置。回退第七项会恢复通知提交锁；要恢复唤醒还须恢复消费者通知配置。

从五项及更早升级，**第六项原有停写、排空、同步切换所有消费者的要求仍然成立**，不能被第七项无需排空替代。步骤统一见 [实时运行手册](../backend/deploy/realtime/README.md)。

最高档的拒绝、未发出需求及突发行为仍须按结果评估。后续目标是独立硬件／真实网络和更长负载，随后按明确的成功率与延迟目标再决定预算、退避或其他算法。消息物理分区、跨请求事务批处理、换数据库与扩大队列都没有因本轮发现而自动采用。

本轮生产实现仍只改 PostgreSQL 适配内的读批次／局部预算、一个迁移及消费者配置，不给通用论坛／消息类型增加框架依赖。替换数据库主要改适配，替换实时服务仍经事件边界；不依赖诊断夹具运行生产服务。移除测试夹具不影响业务包构建。
