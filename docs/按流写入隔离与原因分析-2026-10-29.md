# 普通写入排队原因与按流隔离

日期：2026-10-29（Asia/Taipei）。当前 HTTP 契约 0.4.2。用户要求查明前轮普通写入有 23%–29% 计划请求未发出的原因并继续改进。本轮定位到全局写名额被同一热点流的行锁等待占用；采用按计数器准入，再取得全局名额。保持普通流量速率、客户端工作者数与热点压力，改进版三轮的普通写入全部发出并成功。额外权限预检查带来一次查询和串行开销，本文同时记录。

本文保留单热点＋普通帖的测量范围；随后 [多个热帖与实际 WSS 扇出](多热帖与实时扇出压测-2026-10-29.md)验证了贴吧式回复／引用及多人接收，也暴露高档总容量耗尽时普通写仍被拒绝。这里的 7.5–8.3ms 不能推广到多个帖子都很热或大规模广播的场景。

前轮 [0.4.1 全局预算记录](混合负载与写入准入-2026-10-29.md)保留历史时点；本轮 [全部计量与指纹](性能基线/2026-10-29-scoped-write.json)包含五轮混合、两轮短基线、预热结果、请求失败、未发出需求、分段时间和数据库采样。[业务补丁](性能基线/2026-10-29-scoped-write.patch)只覆盖两个 PostgreSQL 适配文件，不作为运行时策略开关。

## 原因与证据

0.4.1 先取得全局写名额，再开始事务并等待论坛／消息流计数器的 PostgreSQL 行锁。池上限 16、全局写预算 12 时，同一热点帖的 12 个事务占满写名额，约 11 个只在等待相同计数器。其他帖子即使没有锁竞争，也只能在全局队列中等待。给查询留出连接解决了普通读取问题，但没有保护普通写入。

本轮给合成 HTTPS 写请求增加测试专用边界标记：处理器开始、驱动发起 BEGIN、驱动收到 COMMIT／ROLLBACK 结果。128 路热点下，旧版两轮普通写入的结果为：

| 指标 | 旧版第 1 轮 | 旧版第 2 轮 |
|---|---:|---:|
| 处理器全程 P50 | 372.85ms | 370.26ms |
| 开始处理至 BEGIN 的 P50 | 367.94ms | 365.75ms |
| BEGIN 至事务结束的 P50 | 4.29ms | 4.29ms |
| 整个阶段连接池累计等待 | 516.34ms | 605.72ms |
| 数据库 Lock 等待者平均／峰值 | 10.37／11 | 10.38／11 |

事务前时长包含身份、查询、准入和取连接，不能直接称为纯排队时间。结合旧版调用顺序、很小的普通写事务时长及全阶段池等待，可以将主要延迟定位到全局写队列，而不是普通写 SQL 本身。另用真实行锁阻塞测试确认：改进后普通读写均能在热流锁释放前完成。

未发出的请求是压测客户端的需求缺口。普通写固定 25 次／秒、只有 8 个工作者；平均占用超过 8÷25＝320ms 时，客户端无法持续发出全部到达请求。实际延迟约四百毫秒，因此工作者都忙时，相应计划到达被记为 dropped。它们没有发送到服务器，不是数据库接收后丢失。已发送请求的状态、消息／论坛条目／事件数量、事件 ID 与顺序／时间映射均另行检查。

## 实现与授权边界

[writeAdmission](../backend/internal/postgres/forum_write_admission.go)仍使用已锁定的 x/sync v0.24.0 Weighted，不增加依赖、数据库池、后台 worker、配置变量或迁移：

1. 开帖／回复先校验输入，再查询当前成员权限。开帖使用论坛计数器；回复使用消息流计数器，键取数据库返回的规范 UUID，两种命名空间分开。
2. 总接纳容量仍为 256 个活动／等待命令。每个计数器最多 2 条命令进入全局准入／事务段；先等待局部名额，再申请全局写名额。热流的其他等待者不占全局名额，也不取得事务连接。
3. 全局写上限仍按池上限计算：max(1, P−max(1, floor(P/4)))，本机 P=16 对应 12。两个阶段共用同一个最长 2 秒等待 context，并尊重调用方更短时限；不是每段各等 2 秒，也不是整个请求的完成期限。
4. 完成、取消或失败均归还相应名额；注册表用引用计数追踪活动／等待者，最后一个调用退出就删除。注册项不超过总接纳数，不引入定期清理或无限增长的 UUID 缓存。
5. [事务路径](../backend/internal/postgres/forum.go)继续重新检查当前成员权限、锁住权威计数器，再做独立的幂等查询、引用检查及正文／事件原子提交。局部信号量允许小流水线，跨实例顺序仍由数据库锁和唯一约束保证。

预检查防止非成员因私有流正忙而进入该流队列，将原来的 404 变成容量超时；它不取代事务授权。新增开帖／回复回归实际覆盖：热队列中非成员仍获拒绝、大小写 UUID 汇入同一计数器、成员在排队期间被撤权后写入仍失败且不产生新内容。已经通过事务授权的在途操作保留原快照语义，不因此宣称撤权能中止所有在途提交。

HTTP 契约升为 0.4.2，补充入队前／事务内权限说明；成功字段、实时信封、503 write_capacity_exceeded 和 Retry-After: 1 保持原定义。客户端继续以原正文／幂等键做有总时限和抖动的重试，详见 [OpenAPI](../backend/internal/httpapi/openapi.json)。

## 同条件混合对照

Go 1.27.3、GOMAXPROCS=16、PostgreSQL 18.6、API 池 16、观察池 1。33 帖、28225 条 1KiB 合成消息，真实 HTTP/2／TLS 1.3、RS256、PostgreSQL TLS。普通读 100 次／秒、32 个工作者；普通写 25 次／秒、8 个工作者。热点用 32／128 个闭环工作者。每组合预热 3 秒、计量 20 秒，等待窗口内发起请求完成；97ms 聚合采样。客户端与 API 同 Windows 进程，数据库为 Docker Linux 临时内存存储，没有 WSS 扇出负载。

先冻结旧版／改进版测试二进制，按旧→新→新→旧运行，避免反复修改业务源码。四轮共用初版边界计时夹具；随后只收敛测试计时逻辑，再运行当前实现一轮，普通到达率、工作者、超时与业务代码均未调整。

|---|---:|---:|---:|---:|---:|

| 2，改进版 0.4.2 | 500／0 | 5.80／7.53／8.88ms | 4.26ms | 335.60 | 1 |

全部普通读取均发出并成功，已发送请求均没有服务器错误、容量 503 或客户端错误。五轮所有阶段合计 147616 次已发送计量请求成功，另外完整报告旧版的 215 次未发出需求；预热另列，不混入计量吞吐。当前夹具的逐请求计时区间检查全部通过。

最终夹具的普通写事务前 P50=1.57ms，事务内 P50=4.30ms，说明普通写不再跟随热点排长队。热点本身仍然串行；128 路热点的 P95 三轮约 410／412／466ms。32 路混合阶段，普通写旧版 P95=76／90ms、改进版约 7.0／7.6／8.7ms；热点窗口吞吐则为旧版 315.55／305.70、改进版 329.35／330.00／291.75 次／秒。最后一轮热点吞吐有退步，不能据此宣传所有流量都加速。纯热点、普通前后控制及全部尾部结果保存在快照中。

初版曾额外累加 SQL 时长、推导残余等待并计量锁查询，回调配对缺少充分校验，这些派生指标没有用于上述归因，并从公开归一化快照中明确排除。四轮的 HTTP 结果、独立边界标记和池采样完整保留。最终 tracer 使用提交查询独立 context 标记，并逐请求检查区间非负、事务结束不晚于处理器结束；JSON 输出 clock_samples／invalid_clocks，非法区间使测试失败。分位数不能互相相减来求另一阶段分位数。构建指纹区分两版测试夹具，没有将冻结二进制声称为最终全部文件的构建。

## 成本与判断

额外预检查是明确的权限边界，存在查询成本。独立串行仓储探针显示：普通回复由 5 次独立查询＋1 批（7 条语句）变为 6 次＋1 批（8 条），含引用由 6 次＋1 批（8 条）变为 7 次＋1 批（9 条）。普通回复仓储调用中位数 4.21→4.72ms，锁至提交约 2.65→2.63ms；新增成本主要发生在事务前。

两轮短基线每种实现计量 15600 次请求，均零错误，主要取舍如下；这些短测只有各一轮，包含环境波动，不能据小差异得出稳定增益：

| 场景 | 旧版吞吐→改进版 | P50 旧→新 | P95 旧→新 |
|---|---:|---:|---:|
| 32 帖分散写，1 并发 | 199.18→180.82／秒 | 4.83→5.34ms | 5.83→6.32ms |
| 32 帖分散写，8 并发 | 1129.31→981.52／秒 | 6.97→8.00ms | 8.14→9.65ms |
| 32 帖分散写，32 并发 | 1446.70→1460.59／秒 | 21.68→21.44ms | 25.85→25.14ms |
| 单热点，8 并发 | 329.52→351.75／秒 | 9.35→22.61ms | 43.54→24.41ms |
| 首页读取，32 并发 | 1291.17→1136.67／秒 | 24.67→27.73ms | 29.61→35.82ms |
| 深分页读取，32 并发 | 1213.23→1255.32／秒 | 26.07→25.30ms | 32.13→30.70ms |

当前保留隔离方案：它针对已经复现的跨流干扰，收益是普通写在热点下可以继续推进；没有引入分布式调度、额外存储和产品配额。接受一次预检查及低负载退步，同时保留后续按实际延迟／成本目标调整的空间。每计数器 2 是本轮验证的工程默认，不声称它是所有硬件／负载的最优值。

生产业务改动集中在两个 PostgreSQL 适配文件，领域接口、HTTP handler 和实时模块没有增加对应的特殊分支。替换持久化实现时，这里的预算与数据库锁策略随适配层替换，领域代码无需照搬。性能档不启动实时服务器仍能运行论坛读写；删除源码模块仍需处理装配引用，不声称可以任意删包而继续编译。

共享的 256 总接纳容量仍可能被一个流填满，其他流届时也会收到 503；多实例各有局部预算，总连接数和跨实例公平性需另验。预检查发生在写预算外，身份查询、普通查询与维护也共用连接池，理论读取余量不是独占保留池。当前不引入按用户配额、独立连接池或数据库分区来掩盖这些边界。P3 功能、P6 生产负载／高可用／正式 SLA 和生产加密门槛保持原状态。

## 复用来源

- [Go x/sync v0.24.0 Weighted](https://pkg.go.dev/golang.org/x/sync@v0.24.0/semaphore)：BSD-3-Clause，沿用已锁定版本的可取消加权信号量，局部／全局均复用；不复制其内部队列。
- [PostgreSQL 18 锁文档](https://www.postgresql.org/docs/18/explicit-locking.html)：计数器行锁仍是多进程顺序的权威。局部准入减少进入争用区的事务，不用内存顺序替代数据库约束。
- [AWS 多租户公平性实践](https://aws.amazon.com/builders-library/fairness-in-multi-tenant-systems/)：参考共享资源中的热点干扰和分层准入思路；本项目不是按该文实现完整租户配额。
- [ammario/keymutex](https://github.com/ammario/keymutex)：已核对 CC0-1.0 与实现说明；单锁语义、唤醒成本及缺少总接纳边界不直接满足本轮的小流水线＋全局预算，所以没有引入或复制。用已有 semaphore 加小型引用注册表完成当前需求。
