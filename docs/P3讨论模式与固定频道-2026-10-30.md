# P3 讨论模式与固定频道

本文保留 0.5.0 的 P3 验收时点与原始数据。当前 0.5.1 的批次／预算改动、原版回测波动和投递缺口另见 [整体优化对照](整体优化与写预算对照-2026-10-30.md)，不把后续结果覆盖到本轮原始数据中。

日期：2026-10-30（Asia/Taipei）。HTTP 开发契约 0.5.0，共八项迁移。P3 最小后端闭环已完成，真实功能／故障回归通过，三种形态混合测量完成；高档过载和 P6 未验收继续保留。

## 确认与实现边界

用户已批准先完成 P3 最小闭环、开发时补分段计量，再统一验证三种讨论形态。固定频道首版归属独立论坛、继承论坛成员权限；作品在 P5 通过关联接入，不为频道提前创建占位作品。

- **贴吧式帖子**：mode=threaded；主楼、一层楼中楼、具体消息引用，原有接口和实时事件继续有效。
- **即时式帖子**：mode=chat；创建时选择默认布局，消息顺序、可选根楼归属和引用沿用同一份权威数据。两种帖子形式均实时更新。没有发布后改模式或个人视图偏好接口，Q01／Q02 的这部分仍待定。
- **固定即时频道**：是持久产品资源，有元数据、消息历史、引用和独立实时订阅。频道没有帖子标题正文／开篇消息，也没有楼层 root_id；HTTP 明确拒绝 root_id 和伪造作者字段。频道创建后为空，首条消息 position=1。
- 当前显式成员切片允许论坛成员创建帖子和频道、收发与读取该论坛下的讨论；这是本轮工程范围，不代表完整生产创建／管理角色已完成。完整身份组、平台覆盖与运营管理仍按 P5 落实。

正文只存 messages 一份，forum_entries 只存楼层关系，channels 只存频道元数据。数据库 stream kind 和组合外键避免一个流兼为帖子和频道。论坛创建事件共用计数器，topic／channel 列表位置允许缺口。频道复用同一写入准入、缓存、事务 Outbox 和恢复机制，没有叠加一套全局池额度。

## HTTPS 与 WSS 接口

| 接口 | 用途 |
|---|---|
| POST /v1/forums/{forum_id}/topics | mode 可选 threaded／chat；其余幂等、作者和授权规则保持。 |
| GET /v1/topics/{topic_id}/messages | 两种帖子布局共用的有序消息历史。 |
| GET／POST /v1/forums/{forum_id}/channels | 当前成员的频道分页／幂等创建；创建只需要 title。 |
| GET /v1/channels/{channel_id} | 当前成员可见的频道元数据。 |
| GET／POST /v1/channels/{channel_id}/messages | 当前成员的有序历史／持久化发送，正文和可选同频道 quote_id。 |
| POST /v1/channels/{channel_id}/subscription | 无正文，返回 channel:<UUID> 描述符，不是权限凭据。 |

创建／发送使用原 UUID Idempotency-Key。作用域分别为作者＋论坛＋创建资源种类，或作者＋消息流；相同输入返回原结果，输入改变为 409。频道页游标与 channel_messages 游标分别绑定集合和资源，不能拿帖子游标或其他频道的游标复用。成员之外访问仍返回 404。

新增事件为 forum.channel.created（forum:<论坛 UUID>）和 channel.message.created（channel:<频道 UUID>）。现有 forum.topic.created／forum.message.created 和 v1 事件信封不变。data 的频道消息没有 root_id。事件 ID 跨重投保持；position 是业务序号，Centrifugo offset／epoch 是另一个有限恢复位置，不能互换。

当前成员检查在入队前和事务内分别执行。缓存只复用追加型正文，命中前仍查询当前成员与流位置；撤销论坛成员同时影响旗下所有帖子和频道。现有成员移除命令的审计与 user-wide disconnect 同事务提交，覆盖该用户的频道连接；提交响应本身不确认客户端已离开。持续刷新连接在控制面故障时的正式撤权上限仍未验收。

## 分段计量

API 内存中保留固定大小的直方图与计数器：token_verification、identity_lookup、access_check、scope_wait、global_wait、pool_acquire、transaction_begin、stream_lock_observed、idempotency_and_references、message_write、relation_and_outbox、transaction_commit。内部拒绝原因区分全局／局部队列满、局部／全局等待超时和请求取消；对外仍是原 503／Retry-After 契约，不向非成员泄漏私密队列状态。

identity_lookup／access_check 包括各自查询的池等待和数据库往返；pool_acquire 仅测写事务的连接取得。stream_lock_observed 与后续读取是驱动回调观察区间，含网络／调度，不等于数据库内部锁耗时；relation_and_outbox 包括帖子关系及事件批次。直方图分位数是桶上界，不能当精确 P95。在线快照存在并发读取近似，停止写入后的计数可核对；查询快照不会清空计数器。

当前通过进程内 Snapshot 和测试的私有控制管道读取聚合，没有新增公网诊断接口。生产监控后端的导出／告警在 P6 接入。数据没有资源 ID 标签、令牌、正文或 SQL 参数；内存成本不随帖子／频道数量增长。

## 升级与回退

1. 暂停 API 写入，维护窗口内将全部原生消费者的配置加入 channel 命名空间，开启相同的 subscribe_proxy_enabled、history／recovery；API 私有代理按当前论坛成员检查 channel:<UUID>。
2. 显式运行第八项迁移，给运行角色增加 SELECT、INSERT ON odysseia.channels；旧的 messages／message_streams／forums／Outbox 最小授权继续需要。API 启动不执行迁移或修改授权。
3. 部署 0.5.0 API 和匹配的契约；启动并检查所有消费者后恢复写入。必须先让消费者认识新命名空间，再允许新频道事件产生；不能依靠消费者自动重试未知命名空间。
4. 第八项不变更五分区路由，也不要求为它丢弃／重排原有积压；第六项从旧路由升级的停写排空屏障仍然有效。DDL 等锁超过 5 秒失败回滚，大库结构变更耗时尚未单独验收。
5. 如果已有 chat 帖子、频道或待消费的频道事件，Down 明确失败。不会自动改模式、删频道或丢消息；实际回退前需单独设计数据迁移。

## 验证与容量状态

已通过真实 PostgreSQL／HTTPS：两种模式、两实例并发创建／发送幂等、同频道引用、跨流拒绝、作用域游标、伪造字段拒绝、缓存撤权、排队后撤权、Outbox 故障后的正文／计数器／事件回滚，以及第八项保留积压的往返和带 P3 数据的回退拒绝。

真实双节点 WSS 已覆盖两种帖子模式和固定频道，验证同一频道跨节点投递、从另一节点按 epoch／offset 恢复同一事件 ID、继承成员撤权和其他成员继续收发。原有完整标签回归通过（PostgreSQL 包 86.032 秒），包含 P2 真实长中断；这一数字不是 P3 生产故障 SLA。

三种形态混合 profile：48 个种子流（每种 16 个），15 个热点（每种 5 个）、每热点 64 个真实 WSS 客户端，共 960 个；另 32 个普通流轮换读写，剩余 1 个流仅作种子。1025 个不同 RS256 身份已准备，不把它们全算成在线客户端。各档预热 3 秒、计量 60 秒，无自动重试。普通写 25/s、普通历史读 100/s 保持；热点依次每流 10／25／50 次输入每秒。API 与生成器分进程、API 池 16／全局 12 活动写事务，数据库为本轮新建磁盘卷；进程仍共享同一物理机。Go 1.27.3、Centrifugo 6.10.2／SDK 0.13.0、PostgreSQL 18.6 及 fsync／synchronous_commit／full_page_writes 均沿用已核对夹具。

## 混合测量结果

[完整原始数据](性能基线/2026-10-30-discussions.json)保留三个预热阶段、三个计量阶段、每流输入／成功／拒绝／未发出、成功和拒绝延迟、池采样、缓存、分段直方图和 SDK 刷新。以下只汇总计量阶段；接收 P95 仅针对已提交且收到的事件，请求／投递排空时间另存，不能视为严格窗口内吞吐。

各档普通历史读取均 6000/6000、普通写入均 1500/1500，无传输／协议／其他 HTTP 错误。最高档热点成功 21856/45000，约 51.4% 热点需求被拒绝；热点窗口内成功产出约 360.7/s，中档约 374.7/s，继续显示过载退化，不能据同轮成功投递宣称所有输入通过。最高档普通读 P95 111.3ms、普通写 P95 189.5ms，中档分别 26.8／60.4ms，隔离仍不完全。

三档计量共提交 57856 条，3414784 次目标投递全部匹配，无缺失、重复、乱序或载荷／事件 ID 不一致，最终 Outbox 均为 0。每档发生 960 次 HTTPS 连接 token 刷新，刷新失败、传输重连和订阅错误均为 0。该轮是三档各一次的 60 秒测量，不是小时级稳态、独立压力机或三万在线验证。

最高档的 23144 次容量拒绝与内部 scope_queue_full 完全一致，全局队列满、两类等待超时和请求取消均为 0。接纳请求的局部等待均值约 407.9ms，全局等待约 10.8ms，写事务取连接约 6.4ms；当前身份查询和成员预检查均值约 14.8／15.0ms，提交约 9.3ms。池采样平均占用 15.34/16，峰值 16。以上有各自样本数，不可相加为某个请求的完整分位数，也不能把预检查耗时全部归因到 SQL、池或 CPU。

这说明本轮高压下，局部等待队列是直接拒绝点；共享池、前置查询、全局预算和持久化时间仍相互影响。没有证据仅凭加长局部队列就会提高持续吞吐，也没有据此自动扩池或改变用户配额。后续先做相同总连接数下的身份／读与写预算对照，再评估其他已研究的候选。当前只能确认这档 400/s 混合写入负载在本轮完成，不能把 400/s 写成全站上限。
