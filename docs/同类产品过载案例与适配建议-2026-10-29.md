# 同类产品过载案例与适配建议

日期：2026-10-29（Asia/Taipei）。针对用户追问“为什么多并发会失败，成熟产品遇到后怎样解决”。本轮重新阅读当前源码、复核 0.4.5 原始数据并调查第一方事故复盘／实现；不是新一轮压测，也未采用下面的架构候选。HTTP 0.4.5、七项迁移与依赖版本保持。

**结论：确实有相同和相近案例；当前问题是负载超过有效处理能力后，排队和共享资源竞争进一步降低了有效产出。限流保护了已提交数据与普通流量，但最高档约 80% 的输入被拒绝仍是未满足的容量要求，不能当成优化完成。** 不以语言、单线程或“成熟产品也限流”为借口。

来源和版本边界见 [来源索引](../../research/overload-case-study-2026-10-29.sources.json)。项目数据来自 [0.4.5 完整原始结果](性能基线/2026-10-29-process-optimization.json)，本轮提取的指标与原文件 SHA-256 见 [复核数据](../../research/overload-case-study-2026-10-29.local.json)。

## 我们的失败具体是什么

约 300 条／秒不能被转述成“整个论坛最多只能每秒写 300 条”。同一版本中档的热点 400 条／秒两轮均成功，另外的单轮短 API 分散写约 1108 条／秒（600/600，无 WSS 扇出）；这证明当前高档结果包含过载退化，不建立任何生产上限或容量承诺。16 个池连接／12 个活动写事务只是本地实验预算，生产选值须用资源和负载对照标定；共享池也不表示所有帖子只在一个线程上串行处理。

两轮最终组合 D1／D2，均为 16 个热帖、1024 个真实 WSS 订阅者，普通读 100/s、普通写 25/s 继续输入：

| 指标 | 每帖 25/s | 每帖 100/s |
|---|---:|---:|
| 热点总输入 | 400/s | 1600/s |
| 12 秒发起窗口的热点需求 | 4800 | 19200 |
| 最终确认热点成功，D1／D2 | 4800／4800 | 3870／3781 |
| 热点容量 503，D1／D2 | 0／0 | 15330／15419 |
| 热点客户端未发出 | 两轮均 0 | 两轮均 0 |
| 事务开始前 P95，D1／D2 | 26.2／22.2ms | 959.3／875.9ms |
| 事务全程 P95，D1／D2 | 25.5／21.8ms | 27.2／28.4ms |
| 连接池已取连接采样均值／上限 | 约 9.2–9.5／16 | 约 15.5／16 |

两轮最高档被拒绝的请求均未进入业务事务；已提交消息的目标投递验证没有发现缺失、重复或乱序。拒绝仍是用户发送失败，不能把它从分母删除。

输入提高四倍后，发起窗口内成功响应率从约 399–400/s 下降到约 298–305/s。若把窗口发起、排空后才完成的成功也除以 12 秒，则是约 315–323/s；后一个数字不能叫严格的窗口内吞吐或机器的稳定容量上限。这种“加压后成功产出反而下降”的现象符合过载争用的表现，不能仅用“1600 比 400 大”解释全部退步。

**已经确认的调用路径**：`httpapi.authenticated` 先验签、查本地用户；`Forums.Reply` 再查当前成员／帖子，之后才进入局部和全局写准入。身份查询、权限预检查、历史读和写事务目前共用同一 pgxpool。每流 1 个活动写者、全局 12 个活动写者，并不等于池中另有 4 条连接只允许身份／读取使用；预算外的预检查还会彼此争用池。容量拒绝之前也已经发生了数据库工作。

**还不能确认的归因**：`before_begin_ms` 混合了验签、两次前置查询、本地／全局准入和取连接，不能全部命名为队列等待。现有统计也没有分别计数局部满额、全局满额和两段超时。WALWrite／WalSync 等数据库等待仍出现；累计 pool_wait 是多个调用的等待总和，不是单条消息的延迟。物理机器上还同时运行负载端和实时服务。因此“共享池／准入前竞争是优先验证的原因”是有证据的判断，尚非对全部耗时的完整分解。

## 成熟产品确实遇到过什么

### Recall.ai：与上一轮完全对应的通知提交锁

[2025 年事故记录，2026 年更新](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale)描述多个实时写入者使 COMMIT 卡在 `database=0,class=1262,object=0` 排他锁上，最后移除了关键路径的 LISTEN/NOTIFY，改由应用层处理。它不是论坛产品，但故障机制与我们第七项迁移解决的问题直接对应；不能再把它当作当前剩余约 80% 拒绝的原因。

**交叉核实**：文章更新称某个核心提交已解决瓶颈；实际打开其链接的 [282b1cde 提交](https://github.com/postgres/postgres/commit/282b1cde9dedf456ecf02eb27caf086023a7bb71)，主要改善无关监听者的唤醒，[提交后的代码](https://github.com/postgres/postgres/blob/282b1cde9dedf456ecf02eb27caf086023a7bb71/src/backend/commands/async.c#L1300)仍保留全局对象锁，提交说明也没有承诺所有监听者都读取同一通知时改善。当前 [REL_18_6](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/commands/async.c#L921)同样保留该锁。因此不能从博客更新推断升级就能消除本项目的通知提交串行，也不据此恢复触发器。

### Discord 消息存储：热频道影响其他查询

[2023 年官方消息存储文章](https://discord.com/blog/how-discord-stores-trillions-of-messages)记录热分区的无界并发拖累其他请求。其数据服务限制并发、合并同一数据的重复读取，并按频道稳定路由提高合并效果；后续还改变存储系统。文章明确这些流量优化没有一次消灭所有热点。

对我们的适配：缓存和 singleflight 已覆盖部分正文读；不同发帖命令不能作为重复读取合并。Outbox 的四个数据消费分区也不等于 API 写入容量已分片。暂没有证据支持照搬 Rust／ScyllaDB 或照抄完整服务群。

### Discord 2026 语音事故：共享连接管理阻塞了控制流量

[2026-03-25 事故复盘](https://discord.com/blog/behind-the-scenes-of-the-3-25-26-voice-outage)记录连接创建和取用都经过少数 supervisor；邮箱积压连健康注册也阻塞，局部重启后又被故障转移流量压垮。处置包括限制输入、增加容量；后续把连接池监督职责拆到多个独立 supervisor，并改进流控和监测。

这是语音控制面案例，不是文字消息容量证明。适合借鉴的是找到隐藏共享队列并隔离关键流量，不能把“增加业务 goroutine／进程”直接等同于共享池已经能并行服务。

### Slack：入口过载与失败重试会放大数据库压力

[2022-02-22 事故](https://slack.engineering/slacks-incident-on-2-22-22/)中，客户端启动请求耗尽数据库资源，影响已在线用户。Slack 先限制启动请求使系统恢复，放开过快又再次过载，再逐步恢复。这是保护与恢复手段，不代表被限制的用户已经成功接入。

[2022 年另一组事故的 2023 年复盘](https://slack.engineering/the-query-strikes-again/)还记录批量用户清理产生大量重复工作和级联故障。后续缩小查询范围、把逐频道的任务合并成合适的业务任务，并结合限流、熔断和指数退避。这里是批处理／重试放大的类比，不是宣称 Slack 的聊天写入与我们使用相同 SQL。

对我们的适配：先减少重复数据库工作并给关键读／写路径明确预算；重试总量也要受限。不能去掉当前成员复查，不能照搬异步业务清理的合并方式处理多个不同用户的消息命令。

### Matrix/Synapse：每房间单写者，按房间分工并合并合适的持久化任务

[2020 年官方扩展说明](https://matrix.org/blog/2020/11/03/how-we-fixed-synapse-s-scalability/)介绍按房间 ID 分配 event persister；同一房间仍由一个写入者处理，而不同房间可并行，避免跨写入者的全局顺序成为瓶颈。[当前 workers 文档](https://element-hq.github.io/synapse/latest/workers.html#the-events-stream)继续记录这种分工，并明确多 event writer 的实验性质和调整时的协调要求。

本轮还实际阅读 [persist_events.py](https://github.com/element-hq/synapse/blob/develop/synapse/storage/controllers/persist_events.py#L200)，blob 为 `22cc946a6473f0eccdfdd01bee915a9bb0eb21ce`：按房间排队，仅允许一个并发持久化事务，合并兼容的待处理任务，再按 100 个事件分块处理。它支持“每帖有序、不同帖并行、考虑小批持久化”的方向；数字 100 和源码都不直接移植。该文件为 AGPL-3.0-or-later，本轮未复制代码、未接入 Synapse。

### Mattermost：增加进程可能把数据库连接数乘大

[2022 年官方工程记录](https://mattermost.com/blog/how-we-use-rpc-to-share-database-connections/)描述各插件进程独立开池，导致数据库超过连接上限；其方案通过 RPC 共用服务端连接池，云环境也使用数据库代理。对应的教训是跨进程／节点计算总连接预算，而不是把每个进程的池都调大。我们现在没有它的插件架构，不需要照抄 RPC 驱动。

## 对我们的判断与下一步

优先级是工程建议，不是已采用的技术决策：

| 顺序 | 候选工作 | 要验证什么 | 不能混淆的边界 |
|---|---|---|---|
| 1 | 分段记录身份查询、成员预检查、局部准入、全局准入、取连接、持锁／写入／提交；容量拒绝按原因计数。 | 明确高档新增的等待和拒绝分别发生在哪里。 | 内部只存有界聚合，不暴露私有流的队列活动，不记录正文、令牌或 SQL 参数；不能只给 `before_begin` 换个名字。 |
| 2 | 同一个总连接预算下比较共享池与身份／读取、写事务的独立预算，先固定总数 16，再做必要的扫描。 | 高档能否减少预检查竞争并提高成功产出，同时保住普通流量和撤权。 | 16→两个各 16 的池会把资源条件翻倍；只加连接不是同条件隔离。当前成员检查仍访问主库，不能转到可能落后的副本。 |
| 3 | 在明确为瞬时突发的场景，验证有限重试、退避抖动、Retry-After 下限和原幂等键复用。 | 600 个逻辑命令的最终成功、总等待、重试请求放大量及取消；原无重试基线保留。 | 一次逻辑命令的多次网络请求分别记账；202／本地待发送不算 201 持久化成功；持续输入超过能力时重试不能创造吞吐。 |
| 4 | 若分段结果确认提交／持久化仍占主要成本，实验每帖单写者的小批持久化，比较多种小上限／等待窗口。 | 是否减少每消息的提交与持锁开销，改善热帖突发而不恶化中低档。 | 当前 pgx.Batch 是一个请求内的 SQL 批次，不是跨请求批处理；必须分别处理授权、幂等、取消、非法引用、迟到错误和原子提交，不能让一个错误拖垮整个批次。 |
| 5 | 当单实例证据指向需要扩展时，再比较按帖稳定归属、多 API 实例与独立物理机器。 | 不同热帖能否利用更多实际资源；跨节点顺序、撤权和恢复仍正确。 | 同一房间多个进程争同一行锁不等于扩容；必须计算集群连接预算及归属切换，不只是多启动几个进程。 |

隔离机器／真实网络和长时间负载贯穿上述验证。当前数据中的已提交投递完整性仍成立，P2 后端保持完成；P3 即时式帖子／产品固定频道尚未实现，P6 容量与正式故障 SLA 仍未验收。

成熟产品的共同经验是减少共享争用、按合理作用域组织工作、用受控排队与退避处理突发，并在持续不足时增加实际处理能力。扩大等待队列、取消授权／持久性或把失败藏进后台队列，都不能替代这些验证。本轮不引入新数据库、消息中间件、产品配额或新依赖。
