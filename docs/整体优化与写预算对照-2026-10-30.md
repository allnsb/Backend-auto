# P3 后整体优化：写批次与事务预算

日期：2026-10-30（Asia/Taipei）。覆盖 threaded、chat 和固定频道的当前最小后端。P2、P3 最小后端已完成，P6 容量／生产门槛未通过；本报告不定义用户配额或全站容量上限。

## 实现与约束

0.5.1 沿用同一个 PostgreSQL 池、八项迁移和精确锁定依赖。没有新增数据库、代理或消息队列。

- 流锁查询读取最新计数器和数据库事务时间；锁后的幂等／引用仍是独立 READ COMMITTED 语句，避免把等待锁前的快照带到引用校验。
- 使用既有 Go 事件编码器提前生成信封，将计数器／消息、可选论坛关系及 Outbox 放入同一 pgx.Batch。RETURNING 必须符合已锁定的下一序号和数据库事务时间；Close 收齐错误后外层事务才允许提交。晚期失败仍整体回滚。
- 每条请求独立提交，没有跨请求微批、应用时钟、提前响应或降低持久性。正文与事件不变成两个权威来源。
- 全局写事务自动预算留下约三分之一连接余量：`max(1, pool_max_conns - ceil(pool_max_conns/3))`，池 16 对应 10。它为身份／读取留出调度空间，不是物理预留池；其他查询仍可占满池。一连接池没有余量。
- `ODYSSEIA_MAX_WRITE_TRANSACTIONS=0` 或未设置采用自动值；正整数显式覆盖，必须不超过该 API 池上限。负数、格式错误、溢出或超池上限导致启动失败；错误不回显输入。所有实例、消费者和运维连接要合计，不能把每实例设置当全站总预算。
- 每流 1 个活动写者、12 个活动／等待命令、全局 256 命令及两段共用 2 秒等待保持。入队前检查当前成员，事务内重新授权；既有 503／Retry-After: 1 与幂等重试契约保持。

自动预算是本轮局部实验支持的初始工程值，不是所有硬件／负载的最优算法。生产应按实际 SQL、磁盘提交延迟和活跃流分布逐步校准。

## 调研与取舍

详见[成熟实现复核](../../research/whole-forum-optimization-2026-10-30.md)及[来源、许可与固定源码指纹](../../research/whole-forum-optimization-2026-10-30.sources.json)。实际核对 Mattermost 跨进程连接预算、Discord 热键治理和磁盘延迟、Slack 查询放大、Synapse 房间持久化队列、Zulip 事务批写、Nakama 频道落库／路由及 Centrifugo 投递／恢复边界。

固定总 16 连接的 4 读／12 写、8 读／8 写分池均未采用。前者会卡住所有请求都需要的身份／权限检查；后者也存在中档接收延迟和高档热点接纳退步。只合并批次而仍开 12 个写事务的候选也未单独作为默认：热点接纳提高，但普通流量和客户端未发出数变差。没有为复用而照搬整个产品，或把不同持久化保证的吞吐当成对照。

## 测量条件

同一 Windows Ryzen 7 6800H 机器，8 物理核／16 逻辑处理器。Go 1.27.3，API、压测端／官方 Go SDK、Centrifugo 6.10.2 是独立进程；PostgreSQL 18.6 位于 Docker Desktop Linux 的每轮新磁盘卷。fsync、synchronous_commit、full_page_writes 开启。API 总池预算固定 16，未以扩池换吞吐。

48 个合成消息流：每种形态 16 个；其中三种各 5 个热点，共 15 热流，每流 64 个独立用户 WSS 连接，合计 960。另有 32 个普通流循环处理普通读 100/s、写 25/s。每个热点依次计划 10、25、50 条/s，即全站计划写入 175、400、775 条/s；每档先热身 3 秒，再测量 20 或 60 秒，排空最多 30 秒，自动重试关闭。1KiB 正文，覆盖主楼、引用主楼及引用子回复；频道不允许根楼。

20 秒每档计划写入 3500／8000／15500，另有读取 2000；60 秒分别 10500／24000／46500，另有读取 6000。表中的写入不含 GET；计划、发出、成功、503 和未发出分开。普通流 P95 只统计成功 HTTP；接收 P95 只统计实际收到的目标投递，两者都不能掩盖缺口或拒绝。

## 当前验证记录

原版 A3 的最高档有 25 次目标投递在 30 秒排空内未匹配，Outbox 已为零，数据库与 HTTP 成功写入一致。该轮被测试判为失败，保留完整原始报告；原接收器只统计一种重连原因，不能据其“零重连”排除所有断线／恢复。已补不含正文、用户或令牌的有界缺口样本及连接／订阅生命周期诊断，复测不改变缺口验收标准。

E2、A4 和 E3 的全部目标投递均匹配，但没有复现不等于 A3 原因已定位或修复；该项仍是后续容量／投递诊断问题。原 A3 计量报告保留缺失 25／1529216 次目标投递及测试失败，未通过补读、延长排空或重跑覆盖原失败。接收器当前还补齐所有非初始重连原因与 unrecovered 标志；冻结诊断父程序使用较早的计数版本，不能据缺失字段推断其值为零。

## 驱动探针与可以确认的收益

使用原版和最终冻结二进制，各运行既有真实 PostgreSQL 顺序探针 32 次，回复／引用回复分别 16 次。两版原生测试通过（35.33／37.42 秒），每个样本的调用结构一致：

| 路径 | 原版 Query＋Batch | 最终 Query＋Batch | 逻辑 SQL 原版／最终 |
|---|---:|---:|---:|
| 普通回复 | 4＋2＝6 组 | 3＋2＝5 组 | 8／8 |
| 引用回复 | 4＋2＝6 组 | 3＋2＝5 组 | 9／9 |

这是驱动调用组减少，不是 SQL 条数、网络包数或数据库事务数减少；lock_to_commit 也是客户端观察区间，不能当服务端锁持有的精确时长。微基线的全部读写与较差结果同样保留在证据 JSON 的 driver_probes 中，不用于替代多人 WSS 容量。

补充探针的审计包装脚本最初误把输出名写成 performance-baseline.json；两次原生测试已通过，但后续复制报错。实际文件为 performance.json，已在下一次替换前保留原版，再核对最终输出；每份 JSON 的 12 项 HTTP 结果与各自原生日志、4／3 Query 签名一致，修正了脚本路径。没有重跑掩盖测试错误或替换原始数据，恢复说明保留在 JSON。

## 对结果的评估

保留的是更少的驱动调用、同一事务保证以及可以按部署调节的预算，不能宣称稳定吞吐增加了某个百分比。E3 高档提交数比 A4 增加约 12.6%，但 E2 比 A3 略低；同一原版 A3／A4 的中档接收 P95 从 486.4ms 变为 82.6ms、容量拒绝从 253 变为零，说明环境／运行状态的波动足以影响结论。20 秒与 60 秒的数字不能混算成一个稳定增幅。

最终高档也存在明确代价：E3 普通读／写成功 P95 为 124.0／171.7ms，劣于 A4 的 92.3／149.3ms，未发出从 9 增至 15。原版 A3 更差、短候选 E1 更好，这些结果全部保留；尚未获得全面隔离或任意负载下的公平性。共享池中身份和入队前成员查询仍在写预算之外，热点接纳提高也会增加扇出与客户端工作量。

客户端“未发出”的直接含义由 runScheduledLane 实现确认：计划到达时，无缓冲 jobs 通道没有可立即接收的工作者，计为 dropped。慢请求占用工作者或本机调度错时都可能触发；这不等于服务端返回 503，也不直接证明磁盘或 CPU 是唯一原因。普通读／写固定为 32／8 个工作者，各阶段的调度延迟和成功延迟分开保存，不通过无限排队或扩大工作者后抹掉旧结果。

本轮第一阶段实现、候选对照和功能回归已完成；未定位的 A3 投递缺口、过载普通流量和稳定增幅仍有工作，P6 不能关闭。

## 部署与后续改进

更合适的服务器、持久化磁盘及独立压力机可能增加余量，但不是固定倍数保证。A3 高档三个原生进程平均 CPU 核当量约为压测端 3.16、API 1.24、Centrifugo 1.67，尚未统计数据库虚拟机及其他进程；这只能证明同机压力端开销显著，不能独立归因全部瓶颈。网络盘提交延迟也可能高于本地 SSD。

后续优先用分机 Linux 环境、相同总连接预算与持久性做长时阶梯测试，分别记录在线数、活跃写入、读取和目标投递。若证据仍指向持锁成本，再评估跨请求小批及按流稳定写归属，并验证取消、撤权、冲突和故障接管；不能先按 API 实例数线性外推容量。物理表分区、分片、读副本和更换语言／数据库仍须独立证据。

数据库批次与并发预算的改动局限于 PostgreSQL 适配层、启动配置及有界观测；业务类型、处理器权限和实时发布组件无需新增耦合。关闭正文缓存仍可从数据库工作，移除实时组件不改变已提交的论坛正文；跨请求合并或新存储后续若被采用，也应保持这些边界。
