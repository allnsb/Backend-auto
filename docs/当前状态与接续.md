## 接续时不能漏掉的产品要求

容量口径澄清：约 300 条／秒是特定高档过载场景下的成功产出，不是论坛、Go 或 PostgreSQL 的容量上限。同一 0.4.5 的 16 帖中档两轮均完成热点 400 条／秒；不含 WSS 的单轮短 API 分散写约 1108 条／秒，这些场景不能直接互换。此前池 16／全局 12 写者是本机实验预算；当前 0.5.1 自动预算为池 16／10 写事务，并提供显式配置，尚未标定为生产配置。日活、同时在线、持久化写入率与扇出投递率分别计量；原超过 3 万同时在线目标没有验收通过，不能以主动拒绝比例较高的结果替代容量达标。

- **只做后端**，前端由其他同事负责；需提供清楚的 API／SDK 接入和实时事件契约。
- **通用社区可独立作为普通论坛使用**；卡／资源是可关联应用形态，论坛、帖子和消息不强制依赖作品。扩展性、低耦合、安全、性能和清楚代码是默认持续标准。
- 每张卡同时有**介绍与资源下载、即时聊天频道、帖子论坛**，三个区域并存。
- 发帖者创建每个帖子时选择**贴吧式或聊天式**；两种形式的新回复都即时出现。聊天频道固定即时式。
- 贴吧式只有一层楼中楼；主楼归属与具体引用目标分别表达。所有讨论需要 DC 式消息引用，不能只用“回复 @某人”代替。
- 不同读者各自切换视图是期望增强，是否首发尚未决定；发布后改模式也待定。
- 私聊与群聊在范围内；完整聊天能力要单独核对，实时广播不等于完整 IM。
- 身份组可单独配置，作者的作品管理权限可被平台覆盖；分类用于内容组织，不建立逐级独立管理体系。精确权限算法仍待定。
- R18 用单站开关控制，关闭后相关作品在发现入口完全不出现。服务端可处理消息，公网 HTTPS／WSS、存储和备份加密，严格限制访问、保留期限和管理员权限；当前不要求端到端加密。
- 几十万注册、高峰超过三万同时在线、至少运营三年，可能只有一名稳定后端开发者；重视安全、性能、兼容、扩展、自定义和简洁维护。

这些是便于接续的要点；完整边界和未决定细节以需求基线为准。

## 建议如何继续

2026-10-30 接续优先级（工程建议）：P2／P3 最小后端及 0.5.1 首轮整体优化已有交付，下一轮以 [整体对照与未决问题](整体优化与写预算对照-2026-10-30.md)为依据。固定总连接预算的分池候选已经试过并未采用，不再把它列作尚未开始的优化。

1. **先排查投递可靠性。** 原版 A3 的 25 次目标投递缺口尚未定位，不等于已证实丢失 25 条数据库消息。使用当前接收器的完整连接／订阅／恢复诊断，把消息 ID、事件 ID、业务序号和 SDK epoch／offset 对应起来，区分提交／Outbox 处理、实时接收、恢复及排空统计。诊断只保留必要元数据，不记录正文或令牌。结合定向故障注入验证诊断和补读合并；复现的问题修复后增加针对性回归，未复现则继续保留证据与未决状态，不能用后续成功覆盖旧失败。[官方恢复规则](https://centrifugal.dev/docs/server/history_and_recovery)是排查依据之一，不是 A3 的已知原因。
2. **准备可搬到服务器的分机／多实例测试。** 分离压力端、API 和数据库的部署配置及采样，先在相同总数据库连接和活动写事务预算下比较 1／2／4 个 API 实例，并明确各实例队列上限的合计与影响；再单独测试增加资源后的变化。继续覆盖 threaded／chat／固定频道，分别记录计划、发出、成功、拒绝、投递、普通流量和恢复。脚本与观测可先准备，服务器实测及正式阈值须有实际环境和 Q08 依据，不先承诺扩容倍数。
3. **P4 文字、图片／语音和约 7 天附件清扫已经落地。** 接下来在带 Centrifugo 的环境确认 `inbox` namespace 的订阅和短历史恢复，并用真实 R2 复验上传、302 和 `DeleteObject`。把 `attachment-sweep` 排进定时任务后，再打开桶上 `conversations/` 的 8 天生命周期。编辑／删除、病毒扫描，以及 Q05 里仍开放的其它保留期限和管理员访问还没做。不要把这几刀写成完整 IM 或 P6 容量通过。

按 [当前实施计划](后端边界与首个里程碑.md)推进，阶段状态集中维护，本文只保留接续重点：

1. P2 当前范围已关闭，按交接文档重跑验收；真实 IdP 和私密数据使用前的加密门槛继续落实，不记成已接入。
2. 按 [P3 接入与升级](P3讨论模式与固定频道-2026-10-30.md)对接前端并继续三形态的同条件性能对照；即时式帖子和产品频道已经有实现，不再把它们记作待开始。作品关联、个人视图和完整身份组按 P5／对应需求处理。
3. Q01–Q09 按实施计划中的决策时点逐步处理，不擅自采用上游默认值，也不因此停下不依赖这些规则的基础工作。
4. P2 已完成，逐项工时尚未可靠记录，原预算继续保留为估算；后续记录业务实现、联调和故障验证成本，不按代码行数编造日历。加密、权限和故障验证贯穿各阶段。
5. 按用户最新要求，在每个功能动手前及遇到难点时持续联网查找复用机会；保存采用与不采用的原因，和实现同步推进。
