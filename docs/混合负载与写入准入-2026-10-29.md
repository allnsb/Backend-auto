# 混合持续负载与有界写入准入

日期：2026-10-29（Asia/Taipei）。本文保留 HTTP 0.4.1 的实现与测量时点；当前 0.4.2 的原因分析、局部准入与权限预检查见 [后续记录](按流写入隔离与原因分析-2026-10-29.md)。结论：保留短事务，并在数据库事务开始前加入有界写入预算，为同池查询留下连接余量。本机 128 路热点压力下，普通读取 P95 从约 842ms 降到两轮约 4.8–5.2ms，2000 次计划读取均发出并成功。普通写入仍受热点影响，且部分写入 P50 上升，尚未实现按流隔离或生产容量验收。

本记录接续 [首轮短事务优化](热点写入优化与对照-2026-10-29.md)。全部候选、较差结果和采样修正保留在 [合成遥测快照](性能基线/2026-10-29-mixed-admission.json)，不使用只统计成功请求的方式隐藏失败需求。

## 实际改动及边界

[Forums](../backend/internal/postgres/forum.go) 的开帖／回复完成输入校验后、取得数据库事务连接前，进入 [writeAdmission](../backend/internal/postgres/forum_write_admission.go)：

- 使用已经锁定的 x/sync v0.24.0 Weighted semaphore；数据库池上限 P 时，给查询预留 max(1, floor(P/4)) 的理论连接余量，写事务上限为 max(1, P−余量)。本机池 16，对应最多 12 个写事务。池仅 1 个连接时仍允许 1 个写事务，没有读取余量。
- 每个 Forums 实例最多接纳 256 个命令，包含活动与排队中的命令；满额立即返回 ErrBusy。等待写名额最多 2 秒，同时受调用方更短的 context 时限约束。
- 客户端取消或排队超时归还接纳容量；事务提交／回滚退出后归还写名额。排队发生在池外，始终执行原命令，不合并不同请求，也不自行重试。
- 取得名额后继续现有事务权限检查、流锁、独立幂等查询、引用规则、CTE／Batch 和正文／事件原子提交。排队不缓存授权；已完成权限检查的在途事务仍沿用原快照语义。

这是单个后端实例的资源预算。标准 API 装配共享一个 Forums；同一池若创建多个独立 Forums，各自预算会叠加。多个进程仍各有连接池与预算，需要单独确定数据库总连接数。其他查询／维护操作也会占连接，不能将理论余量宣称为独占保留池或全部负载下的读取 SLA。当前没有新增环境变量、第二套数据库池、分布式限流或按用户业务配额；上述数值是当前工程默认，修改时应同步验证与文档。

原有事务计数器仍提供跨实例消息顺序。准入不规定端到端提交 FIFO，不取代数据库锁或数据库约束。成员移除维护命令不排在这条开帖／回复队列里，其事务审计与异步断连保持现有路径。

## 前端需要处理的 503

接纳容量满或等待名额耗尽时返回：

```http
HTTP/2 503
Content-Type: application/problem+json
Retry-After: 1
Cache-Control: no-store

{"type":"about:blank","title":"Service Unavailable","status":503,"code":"write_capacity_exceeded"}
```

Retry-After 是重试提示，不表示一秒后保证可用。客户端保留原请求正文及 Idempotency-Key，在提示时间之后加入非负随机抖动，并限制次数与总时限。不要为同一个命令换新键。此拒绝发生在该次事务开始前；如果此前同键请求已经提交，重试仍按原幂等及当前权限规则处理。

HTTP 身份验证和本地账号查询仍先执行。写预算是全实例范围，对合法格式的目标不检查是否存在后再区别拒绝，因此临时容量错误不披露某个私有资源的存在或活跃程度。进入事务后照常按成员授权返回结果。预期容量拒绝不逐条记录为数据库故障；其他异常仍在原边界记录。

新错误码及可选 Retry-After 已写入 [OpenAPI](../backend/internal/httpapi/openapi.json)，info.version 为 0.4.1；成功字段、实时信封 version=1、五项迁移和消息恢复规则均保持现状。

客户端应核对新增错误码的处理，使用封闭枚举生成客户端时同步更新契约；不能仅凭成功字段保持原状就推定所有旧错误处理均兼容。

## 测量设计与复用

继续复用原有真实 HTTPS／JWT／TLS／数据库夹具，将公共准备集中为 [performanceFixture](../backend/internal/postgres/forum_performance_fixture_test.go)，原基线与 [混合场景](../backend/internal/postgres/forum_mixed_performance_test.go)使用同一数据和授权。没有加入另一套压测运行依赖。

Go 1.27.3、GOMAXPROCS=16、PostgreSQL 18.6、API 池上限 16；一名合成成员、33 帖、28225 条预置 1KiB 消息。服务端与客户端同 Windows 测试进程，数据库为 Docker Linux 临时内存存储。每个场景先预热 3 秒，再计量 20 秒发起窗口，等待窗口内发起的请求完成；每请求时限 5 秒，实际 API 仍使用现有 10 秒认证／处理 context。没有 WSS 消费器参加性能测量。

| 流量 | 方法 |
|---|---|
| 普通读取 | 固定 100 次／秒，轮转其他 32 帖、每页 50 条；最多 32 个客户端工作者。 |
| 普通写入 | 固定 25 次／秒，轮转其他 32 帖；最多 8 个客户端工作者。 |
| 热点写入 | 同一独立热点帖、32 或 128 个固定工作者闭环发送，用作压力源；不是已确认的生产消息速率。 |
| 场景顺序 | 普通负载 → 仅 32 路热点 → 普通＋32 路热点 → 普通＋128 路热点 → 压力解除后的普通负载。 |

普通流量按独立时间表调度，工作者忙满时记为 **dropped：客户端未发出的计划请求**，不排入无界客户端队列。另记已发起、成功、各类失败、HTTP 全程延迟、从计划到达时刻起的延迟，以及客户端调度滞后。所有已发起请求均进入延迟统计；本次已发出请求没有 HTTP／传输失败，但未发出的需求仍不能计为成功。

窗口 RPS 仅计窗口结束前完成的成功请求；延迟采用窗口内发起的完整请求队列，包括结束后排空者。普通流量调度 P99 滞后约在毫秒量级，完整值保留在快照。实验不自动重试任何失败请求。

数据库观测使用同一运行角色的独立单连接采样池，只查询当前测试库／应用名的 pg_stat_activity 聚合计数，不读取正文或输出 SQL 文本，亦不授予额外监控特权。此连接与预置／校验维护连接不计入 API 的 16 个连接。

最初 A1／B1 的固定 100ms 采样与普通请求的 10ms／40ms 节拍重合，曾反复漏掉短暂占用；这两轮保留为试跑，普通池占用均值不用于结论。A2 起采用 97ms，避免相同相位重复，20 秒各有约 206 个样本。离散快照仍不是连续精确持锁或时间加权计量。方法参考 [开放／闭环模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)、[pgxpool Stat](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.11.0/pgxpool#Stat) 与 [PostgreSQL 活动统计](https://www.postgresql.org/docs/18/monitoring-stats.html)。

## 候选及独立取舍

| 标记 | 实现与状态 |
|---|---|
| A1／A2 | 首轮优化前的原事务，作为历史控制；运行后恢复当前源码。 |
| B1／B2 | 小 CTE＋pgx.Batch，未加写预算。 |
| C1 | B＋最多 8 个写事务，给查询留半池；保留试验，不作为最终默认。 |
| D1／D2 | 最终实现：B＋最多 12 个写事务，给查询留四分之一。 |

先测 A1、B1、A2、B2，再测 C1 与分散基线、当前环境的 B 分散控制，最后 D1、D2 及 D 分散基线。每轮重建隔离库；不是随机交错实验。七轮混合计量共 **171188 次已发出请求、零服务端／传输失败**，另有 **5842 次计划请求未发出**。三轮分散基线另计量 46800 次、零错误，总计已发出计量请求 217988 次；预热和串行诊断探针另计。每轮检查实际新增正文、楼层关系和不同消息的序号／时间事件一一匹配，没有消费者删除事件。

## 热点是否拖累其他帖子

下表主要比较采样已修正的 B2 与最终 D1／D2。延迟为已发起请求的 P95，单位 ms；所有计划普通读取每窗 2000 次、普通写入 500 次。D 的范围是两轮实测，不是合并分位数或置信区间。

| 场景／指标 | B2 短事务 | D1／D2 最终预算 |
|---|---:|---:|
| 普通负载读 P95 | 5.67 | 4.99–5.15 |
| 混合 32 路：普通读 P95 | 120.79 | 5.45–5.74 |
| 混合 32 路：普通写 P95 | 84.92 | **97.69–107.41** |
| 混合 32 路：热点写 P50 | 87.64 | **123.01–126.57** |
| 混合 32 路：热点写 P95 | 236.44 | 156.10–167.52 |
| 混合 128 路：普通读 P95 | 841.82 | 4.84–5.24 |
| 混合 128 路：普通读未发出 | 1074／2000（53.7%） | 0／2000 |
| 混合 128 路：普通写 P95 | 526.15 | 439.62–467.12 |
| 混合 128 路：普通写未发出 | 162／500（32.4%） | **116–147／500（23.2%–29.4%）** |
| 混合 128 路：热点写窗口 RPS | 253.60 | 271.25–296.25 |
| 压力解除：普通读 P95 | 5.25 | 4.42–5.13 |

这支持为查询保留余量，但**没有把普通写入与热点写入隔离**。32 路热点时部分写入 P50／P95 变差，128 路时普通写仍达不到 25 次／秒的实验需求。全局同权排队只是限制资源并改变等待分布，不能称为按帖公平调度或全面低延迟。

仅热点的持续负载中，A 两轮窗口吞吐约 194–198／秒，B 约 286–288／秒；B 的持续 P50 约 76–85ms，比 A 的约 101–106ms 低，首轮 600 次短测的 P50 退步没有在该组合复现。最终 D 的 P50 又变为约 115–117ms、P95 约 139–146ms。保留三种分布，不把一个窗口的结果推广到所有负载。

## 等待去了哪里

B2 的 128 路混合场景，平均约 15.97 个 API 连接被占用、13.95 个数据库 Lock 等待者，峰值 15；池等待累计约 3039 秒。D 两轮平均约 10.37 个 Lock 等待者、峰值 11，池等待累计约 0.62–0.81 秒，普通查询能取得余量。

这些累计等待是多个请求重叠后的总和，不是场景墙钟；数据库池等待降低，也不表示总等待消失。Go 写队列的等待包含在 HTTP 请求延迟中，写入仍需串行通过同一数据库流锁。

## 是否牺牲了分散写入

给半池留余量的 C 单轮分散写 32 并发约 1095／秒，临近的 B 控制约 1307／秒；同时首页读取控制约 922 对 1062／秒，存在环境变化，所以不能把全部差额归于预算。该结果提示初版可能偏保守，因此改为 D。

| 32 并发短基线 | B 无写预算 | C 8 写名额 | D 12 写名额 |
|---|---:|---:|---:|
| 分散写吞吐／秒 | 1306.9 | 1095.5 | 1324.9 |
| 分散写 P95 ms | 30.96 | 31.85 | 29.75 |
| 历史首页吞吐／秒 | 1061.7 | 922.2 | 1200.6 |
| 深分页吞吐／秒 | 1083.8 | 1083.1 | 990.8 |

D 在这次分散短测未显示明显写吞吐损失，读取控制仍有波动，不能声称稳定提升 1.4% 或任意生产增益。D 的 8 并发热点短测 P99 约 591ms，B 同类约 408ms；该并发没有触及 12 写名额，短尾样本和调度影响仍在。快照保留全部 12 个基线场景及串行探针，没有只摘取好看的数据。

## 正确性、来源与维护

采用已在模块缓存的 golang.org/x/sync v0.24.0（BSD-3-Clause）Weighted 实现等权等待与取消；[官方 tags](https://go.googlesource.com/sync/+refs)在本轮核对时顶部为 v0.24.0，[API](https://pkg.go.dev/golang.org/x/sync@v0.24.0/semaphore)及固定源码、LICENSE 已读。go.mod 将它标为直接使用，没有新增模块版本、校验和或复制上游实现。pgx v5.11.0 和 PostgreSQL 镜像保持原锁定。

验证包括接纳上限立即拒绝、2 秒排队耗尽、父 context 取消、容量归还与并发活动上限；HTTP 503／Retry-After／Problem 对照 OpenAPI。真实数据库测试先持有流锁，再实际观察写预算对应的数据库 Lock 等待，确认该锁释放前授权读取仍可完成，取消阻塞者后序号未改变。没有用固定睡眠猜测已进入锁等待。

业务适配涉及 PostgreSQL 的准入与构造／写入口；领域只增加通用 ErrBusy，HTTP 统一映射并补契约。身份、实时消费者、消息类型与数据库迁移没有为预算而改造。替换数据库可在适配中调整预算机制，HTTP 仍接收同一个错误；去掉实时消费者不影响该预算和正文事务。公共性能夹具只用于测试。

完整 integration,realtime,cluster,acceptance,algorithms 回归通过，postgres 包 89.190s，覆盖真实 WSS、双节点撤权、65 秒故障及恢复合并；默认回归、全部标签 go vet、模块校验及 Linux amd64 六个命令交叉构建通过。govulncheck v1.9.0 读取官方 2026-10-27 漏洞库未发现已知漏洞；没有上传源代码。交叉构建未在 Linux 执行 Go 服务，测试容器和网络已清理。

测试仍使用合成身份及消息；三万在线、跨机网络、真实磁盘、小时级持续负载、正式故障 SLA 和存储／备份加密不是这组实验的验收结果。
