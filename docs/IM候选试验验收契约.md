# MongooseIM／Tinode 本地试验验收契约

日期：2026-10-26（Asia/Shanghai）。状态：试验约定，结果由实际执行日志填写。用户已同意同时试用两个 OpenIM 替代，尚未决定最终采用哪个。

需求依据：[产品需求基线](产品需求基线.md)。原始调查：[成熟系统](../../research/openim-alternatives-2026-10-26/mature-chat-review.md)、[Go IM](../../research/openim-alternatives-2026-10-26/go-im-review.md)。

## 1. 本轮边界与现状

本轮保留 BBS-GO 的内容业务和原 OpenIM 源码，比较两个独立 IM 候选。检查开始时，本项目只有上游源码、研究与审查材料；部署目录只有说明，尚无 BBS-GO 与新 IM 的实际账号／频道／权限适配。

因此，直接建立候选原生测试账号，只能证明候选服务和测试客户端可用。完成业务身份映射、作品权限接入后，才可以称为业务联调；测试脚本中的虚拟 card_id 也不能算已经实现作品空间。

本轮目标是找出接入、授权和恢复方面的实际差异。三万以上同时在线、生产 P95/P99、跨节点高可用及全部产品功能不在本轮的通过范围。

## 2. 运行与版本记录

两者分别记录以下信息，缺失项填写 unknown，不能从研究阶段的版本推定本次实际运行版本：

| 项目 | 必填证据 |
|---|---|
| 服务端 | 上游 ref、完整 commit、实际镜像 tag 和 digest；是否有本地补丁 |
| 配置 | 生效配置摘要、启用模块、数据库类型、历史保留与写入方式、认证方法、房间类型和 ACL |
| 客户端 | 官方 SDK 名称／版本，或明确写“手写协议测试客户端”；运行时与所用协议扩展 |
| 运行环境 | Docker/WSL版本、CPU/内存限制、数据库配置、测试顺序、其他容器负载 |
| 连接入口 | WSS/HTTPS URL、TLS信任方式、管理入口绑定、内部端口边界 |
| 数据 | 独立数据目录／数据库／账号、run_id、合成测试账号数量、消息数量和正文UTF-8字节数 |

候选初始目标为 MongooseIM 6.10.0、Tinode 0.25.3。Tinode 此前定点审查的是 master `eb90ef83…`，不能把该分支的行为或行号直接归给 0.25.3；需要在发行版实际运行后确认。

两个候选可以共用新建 PostgreSQL 实例，但使用不同数据库和最小权限账号，不共用表或修改旧项目数据库。所有数据、证书、缓存与日志放在新项目 E 盘 runtime 范围，旧容器和旧数据不参与 reset/init 操作。

本地入口只绑定 loopback。应用客户端实际使用 WSS/HTTPS，并信任本次本地 CA 或证书；不能通过关闭 TLS 校验取得“加密连接通过”。容器内部是否明文、TLS在哪一层终止分别记录。域名、证书 SAN 与客户端实际解析也要一致，不能假设所有系统均自动解析任意 `*.localhost`。

## 3. 共用数据与策略

用同一组业务测试身份建立两套原生映射，不要求候选的原生 ID 相同：

| 身份 | 用途 |
|---|---|
| A | 私聊参与者、私密试验房间拥有者；使用A1、A2两个客户端会话 |
| B | 私聊参与者、初始房间成员；保持一个会话在线供撤权检查 |
| E | 有效普通登录用户，未参加 A/B 的私聊与私密房间 |
| O | 仅测试初始化／受控管理使用的服务凭据，不能交给普通客户端 |

使用两种语义明确的会话：

1. A/B 双人私聊，E 无权读取或操作。
2. 成员制、所有成员可发言的私密房间，初始 A/B 为成员，E 非成员。MongooseIM需注明选的是普通MUC还是MUC Light；Tinode使用普通可写group。

不要拿 Tinode 的无限只读 channel 与 MongooseIM 的可写房间比较。公开作品频道另做探针，记录访问、持久成员、临时在线订阅的区别，不把私密房间测通等同于公开大频道已实现。

撤权用例的试验策略明确设为：撤销 B 对该私密房间的后续读取、发送和订阅权限。它是本次合成场景的断言，不替用户拍板全部产品的离群后历史规则、身份组冲突算法或资源继承规则；A/B私聊和B对其他会话的权限保持独立。

每轮使用唯一 run_id，消息正文带可核验的 client_message_id。客户端墙钟不作为消息全局排序或持久化成功的唯一证据。

## 4. 首轮最小验收矩阵

逐项填写 pass、fail、blocked、not_run。只有实际执行并满足断言才为 pass；依赖或脚本故障是 blocked，不自动判为服务不支持。确认没有对应能力时另填 capability=unsupported，并记入需要自建的工作量。

| 编号 | 场景与动作 | 必须观察到的结果 |
|---|---|---|
| A01 | 可信CA下建立WSS／HTTPS；错误凭据登录 | 正确连接成功；错误身份拒绝；客户端日志显示TLS验证启用 |
| A02 | A正常发言，并尝试在协议允许的字段中声明B为发送者 | 正常消息的权威作者为A；伪造请求被拒绝或发送者被可信入口固定为A；B端和历史中均不能出现伪造作者 |
| A03 | A1↔B私聊，A2同时在线 | B真实收到消息，native message ID、作者、会话归属可核对；A2的同步行为单独记录，不能只凭发送ACK通过 |
| A04 | A/B可写房间正常发言；E尝试发言、读取历史、订阅 | A/B实际接收；E的越界操作拒绝；有会话ID或有效普通token也不能取得正文 |
| A05 | 写入合成消息，分页读取；重建客户端，必要时重启本次候选服务再读 | 已确认接收的持久消息可从原生历史重取；边界分页没有遗漏／重复；重启持久化与客户端重连分别记结果 |
| A06 | B断线期间A继续写入，然后B重连补拉 | 记录断线前游标／序号、断线期消息ID和恢复后的集合；在客户端合并后消息不缺失；发生传输重发时明确去重位置 |
| A07 | B保持现有连接；管理端撤销该房间权限，A在撤权提交后发送唯一消息 | 分别验证B不再收到后续实时消息、不能发言、不能经已有连接／API读新历史；再重连确认无法重新进入；记录撤权窗口和踢线／重订阅机制 |
| A08 | E尝试操作A的消息；普通客户端尝试管理入口 | 对外存在的删／改接口按作者／管理权限拒绝；管理凭据不出现在普通客户端；未暴露的接口按入口隔离验证，不虚构调用成功 |

A07必须观察到**已有连接**的行为。仅让B的新token签发失败，或只验证重新登录失败，不算该项通过。撤权前已经交给客户端的正文不在服务端可撤回范围内；断言针对撤权后的新投递和后续服务端读取。

A05的“重启”只针对新建试验服务；数据库保留。删除数据库重建后重新发送消息，不是持久化恢复测试。若只测到重新订阅历史，就只记该子项通过。

A03中的协议ACK需注明语义：服务接受、持久化、流处理确认和对端客户端收到是不同的观测点。MongooseIM的流确认／回执不能直接与Tinode的ctrl状态码作为同一延迟终点。

## 5. 完整聊天与安全补充项

首轮后按实际能力继续，未执行项不能并入“完整IM通过”：

| 编号 | 验证项目 | 需要区别的边界 |
|---|---|---|
| B01 | 引用具体消息、原消息改删后的状态 | 序列／ID关系、定位与摘要；是否服务端检查被引用内容的可见范围；前端自行渲染与原生支持分别记录 |
| B02 | 编辑、撤回、用户删除、管理物理删除 | 原作者限制、跨会话拒绝、历史与其他设备的最终状态；不能以本地隐藏冒充所有设备删除 |
| B03 | 已读／未读、多端同步、主动登出 | A1/A2游标与未读行为；单设备登出／全账号撤销；权限与个人阅读状态分开 |
| B04 | 附件上传与下载 | E拿到A/B私聊附件URL后仍被拒绝；上传签名、登录检查和会话下载授权不是同一件事；旧签名有效期与撤权窗口记录清楚 |
| B05 | 保留期限与删除 | 使用明确测试配置和真实清理路径；清理后新客户端历史／文件读取符合策略；不凭配置字段存在就记通过 |
| B06 | 搜索 | 如果服务提供用户搜索，验证范围；接口缺失计为需补能力，不使用管理全库查询替代用户搜索 |
| B07 | 公开频道进入／离开 | 可读／可写资格、临时订阅与永久成员关系、在线列表、离线投递、历史范围；原生人数限额与实际处理成本分别记录 |
| B08 | 普通日志与错误路径 | 正确／错误凭据、禁言／撤权时不输出可用token、SASL密码或私聊正文；记录脱敏方式和日志等级 |

MongooseIM的MAM、Stream Management、Carbons、Markers、编辑／引用等协议扩展，要明确服务端启用情况和实际客户端实现情况。手写Node测试客户端验证一个XML流程，不代表选定浏览器SDK已经支持全部XEP。Tinode协议具备字段，也需检查所选JS SDK是否保留并正确合并这些字段。

当前调研已指出两者的默认附件路径都不能直接视为按会话授权完成。若本轮未接入统一私密文件服务，应把B04明确标为未完成，而不是用公开图片URL测通下载后计通过。

## 6. 最小业务适配契约

下面定义的是可对照的语义边界，不要求现在建立一个复杂统一协议网关。普通聊天客户端可以使用候选原生协议直接连接；适配层只承担业务身份、授权、会话映射和必要事件整合。

| 边界 | 输入／权威来源 | 可交付结果与约束 |
|---|---|---|
| 身份映射 | 业务user_id及账号状态 | provider＋native_user_id；ID按不透明字符串保留，不把昵称当主键，不强转JS不安全整数 |
| 连接凭据 | 业务登录身份、设备、当前会话策略 | 普通用户凭据／过期信息／WSS配置；服务管理secret留在可信后台；注明本轮是原生测试账号还是已接业务登录 |
| 作品频道映射 | card_id、channel_id、会话用途 | 原生conversation/room/topic ID与类型；不强制一卡一server，也不把分类改成独立权限租户 |
| 授权决策 | 业务身份组策略与policy_version | 按读取、发言、订阅、管理、下载分别执行；候选原生角色只保存所需投影；撤权返回实际生效证据，不能仅返回任务已接受 |
| 消息身份 | 候选权威存储 | native message ID、会话归属、可信sender、server_time／序号和revision；client_message_id仅用于追踪／幂等，不当作可信作者 |
| 引用 | 明确的原会话／原消息关系 | 实际引用目标与可访问状态；楼层归属留给内容业务，引用不改变论坛嵌套层级 |
| 历史与恢复 | 候选原生游标／序号＋权限 | 分页／补拉、边界和失效策略；原生cursor不互相转换，不靠全量刷新掩盖缺失的恢复能力 |
| 论坛增量事件 | 内容事务的event_id、resource_id、version | 内容API是权威，复用同一套事件适配做候选试验；不复制论坛正文成第二份聊天正文 |
| 能力表 | 服务端＋启用配置＋选定SDK | 原生、需要配置、需要适配、不支持、未验证分开记录；缺失能力计入开发工作量 |

完整的DC身份组冲突、作者管理范围、平台覆盖精确算法仍待产品确认。首轮只用明确的试验读／写／订阅策略检查落点，不能因为候选有owner/member就声称DC身份组已完成。

## 7. 公平比较与结果格式

功能对照保持账号数、成员数、消息正文、数量、持久化要求、收发端位置和TLS校验一致。候选采用各自正常原生协议，不为凑相同线路人为给一方增加正文转发服务。压测前还需核对日志、压缩、推送、数据库同步／批量写、TLS终止和资源限制。

先顺序运行并记录空闲基线；同时运行时明确数据库和宿主资源竞争。共享PostgreSQL需要按数据库区分统计，候选容器内存不含数据库时也不能当成全栈占用。

每个测试结果至少包含：

```json
{
  "case_id": "A07",
  "provider": "mongooseim-or-tinode",
  "run_id": "unique-synthetic-run",
  "status": "pass|fail|blocked|not_run",
  "scope": "native-protocol|selected-sdk|business-adapter",
  "assertions": {
    "existing_connection_stops_new_delivery": "observed-result",
    "existing_connection_cannot_send": "observed-result",
    "history_after_revocation": "observed-result",
    "reconnect_cannot_rejoin": "observed-result"
  },
  "revocation_ms": null,
  "evidence": ["redacted-log-path"],
  "limitations": ["unmeasured-or-unimplemented-items"]
}
```

日志只保存合成消息与必要元数据；输出前清除token、密码、SASL payload和管理secret。检查敏感日志时输出命中与否，避免再次把秘密打印到报告。

测试等待时限只是脚本截止条件，不是产品延迟SLA。零星本地收发时间不用于P95/P99排名；即使功能矩阵全通过，也不能写成三万在线容量验收。报告应给出接入缺口、补丁量、操作步骤、SDK工作量和未完成项，供最终选型使用。
