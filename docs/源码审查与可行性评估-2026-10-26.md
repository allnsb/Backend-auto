# BBS-GO＋OpenIM 源码审查与可行性评估

审查日期：2026-10-26。需求依据：[产品需求基线](产品需求基线.md)。本轮是源码与可行性审查，没有修补或启动两份上游服务。

## 结论

**业务结构有条件可行，当前原版组合不具备直接公开上线的条件。** BBS-GO 的帖子、评论、账号和管理能力有复用价值，OpenIM 能复用聊天协议与同步能力。主要新工程是作品模型、作品范围权限、可靠论坛事件，以及两套身份／成员状态的一致性。

最需要先解决的是 OpenIM 的三条授权路径：WS 内层发送者绑定、消息搜索范围、按序号物理删除权限。下面记录的是固定版本的静态代码证据，未在运行服务中做攻击复现，不作为已公开 CVE 或所有版本均受影响的声明。

这不是把两个服务拼接后只改界面的小工程。可以保留选定路线推进，但应先完成授权修补与最小联调，再投入大量作品功能。三万以上在线的容量仍未验收；语言、配置连接上限和现有单元测试都不能替代实际负载测试。

## 2. 优先处理的授权问题

### S01 · P1：WS 消息的内层发送者未绑定登录连接

证据链：

- [client.go:166](../services/open-im-server/internal/msggateway/client.go#L166) 只验证外层 `Req.SendID == c.UserID`。
- [message_handler.go:151](../services/open-im-server/internal/msggateway/message_handler.go#L151) 解包客户端 `MsgData`，没有将其 `SendID` 与登录身份比较或覆盖，随后调用 `SendMsg`。
- [verify.go:55](../services/open-im-server/internal/rpc/msg/verify.go#L55) 及 96、107、111 行，后续单聊／群聊检查使用内层 `SendID` 判断管理员、群成员和禁言。

客户端可以构造与外层身份不同的内层发送者；该路径存在冒充发送者及命中特权分支的风险。正常 SDK 自动填正确字段不能替代服务端绑定。

最小处理：在可信入口绑定发送者，明确普通客户端可发送的会话与内容类型；RPC 仍须保证业务授权。验证普通用户不能冒充另一个用户、管理员，不能借此绕过群成员或禁言检查。

### S02 · P1：消息搜索没有限制到管理员或当前用户可见会话

证据链：

- [router.go:230](../services/open-im-server/internal/api/router.go#L230) 注册 `/msg/search_msg`；300–327 行通用中间件验证 token、设置操作用户，没有统一要求管理员。
- [api/msg.go:387](../services/open-im-server/internal/api/msg.go#L387) 直接转发；[sync_msg.go:148](../services/open-im-server/internal/rpc/msg/sync_msg.go#L148) 没有调用管理员检查或用户会话授权。
- [mgo/msg.go:324](../services/open-im-server/pkg/common/storage/database/mgo/msg.go#L324) 按请求中的发送者、接收者、类型和时间过滤，401–426 行返回消息，没有绑定操作用户。

若将默认 API 全量暴露，普通 token 可进入缺少资源范围限制的搜索路径，威胁私聊隔离。

最小处理：该管理用途接口先限制为管理员／内部调用；若需要用户搜索，单独按已授权会话检索。公网路由使用明确允许列表，RPC 本身也落实权限，避免仅靠反代隐藏敏感路径。

### S03 · P1：按序号物理删除没有管理员或消息范围授权

证据链：

- [router.go:243](../services/open-im-server/internal/api/router.go#L243) 注册 `/msg/delete_msg_phsical_by_seq`，拼写与源码一致。
- [api/msg.go:148](../services/open-im-server/internal/api/msg.go#L148) 直接转发。
- [delete.go:95](../services/open-im-server/internal/rpc/msg/delete.go#L95) 按请求的 `ConversationID`／`Seqs` 调用删除，缺少授权；同文件 104 行相邻的按时间物理删除明确调用 `CheckAdmin`。
- [controller/msg.go:540](../services/open-im-server/pkg/common/storage/controller/msg.go#L540) 操作 Mongo 和 Redis；[mgo/msg.go:219](../services/open-im-server/pkg/common/storage/database/mgo/msg.go#L219) 实际清空消息字段。

最小处理：将物理删除限制在可信管理路径；用户删除／撤回使用分别定义的语义与授权。用普通 token、跨会话 ID、不同消息序号验证拒绝行为，并确认数据未变化。

### 通用中间件不能补足以上资源授权

已核对固定版本 tools：`a2r/api2rpc.go:25–44` 只解析、执行可选 hook、结构检查和 RPC 调用；`mw/rpc_server_interceptor.go:20–45,71–79` 处理 metadata／操作身份、结构验证和日志；`checker/check.go:9–18` 调用没有登录上下文参数的 `Check()`。这不能替代当前用户对具体消息、会话和发送者的授权。

另核对固定 protocol：`msg/msg.go:16` 的 SendMsgReq.Check 调用 `MsgData.Check()`，`sdkws/sdkws.go:10` 只检查字段非空与通知类型匹配，不比较登录身份；SearchMessageReq 和 DeleteMsgPhysicalBySeqReq 没有额外 Check 方法。网关 `ws_server.go:123–125` 的 Validate 直接返回 nil，也不能补足内层发送者绑定。

### S04 · P1（多实例条件）：BBS-GO 撤权只失效本机缓存

[permission_cache.go:5–43](../services/bbs-go/internal/cache/permission_cache.go#L5) 使用无 TTL 的进程内 map；[permission_service.go:124](../services/bbs-go/internal/services/permission_service.go#L124) 命中后返回。[role_permission_service.go:73](../services/bbs-go/internal/services/role_permission_service.go#L73) 等变更路径只清当前进程缓存。

多副本时，A 撤权而 B 已缓存的授权可能持续有效。单实例没有这个跨节点问题。

最小处理：权限版本／跨节点失效，加有界 TTL；资源权限把作用域加入决策与缓存。验收需要预热两个实例，在 A 撤权后验证 B 的读、写、下载、订阅均被撤销。

### S05 · P2：帖子状态与评论／附件可见性不一致

- [topic_handlers.go:294–310](../services/bbs-go/internal/handlers/api/topic_handlers.go#L294) 拒绝删除帖，并限制审核帖的读取。
- [comment_handlers.go:19–38](../services/bbs-go/internal/handlers/api/comment_handlers.go#L19) 直接读取评论／子回复；[comment_service.go:219](../services/bbs-go/internal/services/comment_service.go#L219) 只过滤评论自身状态，没有相同的父帖校验。删除帖子不会同步屏蔽评论正文。
- [comment_render.go:99](../services/bbs-go/internal/handlers/render/comment_render.go#L99) 取引用时也没有父帖可见性判断。
- [attachment_service.go:159](../services/bbs-go/internal/services/attachment_service.go#L159) 只拒绝删除帖，与审核帖详情规则不一致。

直接被删除的评论在渲染时会显示“内容已删除”；这里缺少的是仍为正常状态的评论／引用所属父帖的可读性检查，以及后续作品范围授权，不是所有已删除引用都会返回原文。

知道 ID 后，可能从其他入口读到详情已拒绝的内容。最小处理是在统一内容服务执行可读性判定，并覆盖正文、引用、列表、搜索、收藏、隐藏内容、sitemap、文件和后续事件。

### S06 · P2；受限文件上线前必须处理：永久静态附件绕过下载入口

[local_uploader.go:16](../services/bbs-go/internal/pkg/uploader/local_uploader.go#L16) 返回永久 `/res/uploads/...`；[router.go:58](../services/bbs-go/internal/server/router.go#L58) 静态提供文件；[attachment_middleware.go:18–49](../services/bbs-go/internal/middleware/attachment_middleware.go#L18) 只设置下载响应头，没有授权或删除状态阻断。

[attachment_handlers.go:111–147](../services/bbs-go/internal/handlers/api/attachment_handlers.go#L111) 的下载 API 虽有登录／积分检查，最后重定向到永久 URL。拿到路径的人可绕过入口，软删除记录也不撤销文件访问。这不是 UUID 可枚举的结论。S3 实现返回长期对象 URL，是否公开还取决于 bucket／CDN 设置。

受限资源应使用私有对象存储，授权后发短期签名 URL，或走受保护代理。下载授权包括作品、资源版本和帖子状态；公开封面与受限文件分开处理。

| 需求 | 可复用部分 | 必须补充的部分 |

| 论坛即时式连续讨论 | 内容 API、排序与引用基础 | 同一权威内容模型的游标读取与事件协议；模式选择规则仍待定 |

| 严格私聊访问与保留策略 | OpenIM 服务端消息处理、撤回、删除、定时清理 | 先修 S01–S03，再落实管理审计、日志脱敏及分类保留策略 |
| 超过三万同时在线／单帖超过千人 | Go 服务、多网关基础、成员缓存 | 真正热房间扇出与恢复压测；不能承诺容量 |

### D01 · P2：上游现存数据约束不足，评论写入未限制目标、第三层和引用有效性

[comment_service.go:110–165](../services/bbs-go/internal/services/comment_service.go#L110) 只检查非空类型、正 ID 和正文，随后复制 `EntityType/EntityId/QuoteId` 并入库。`EntityComment` 分支没有要求父评论必须是主楼层，其他类型没有 default 拒绝；[comment_repository.go:85](../services/bbs-go/internal/repositories/comment_repository.go#L85) 更新父计数不检查 RowsAffected。

应在同一事务里验证合法目标、父层级、引用存在和可读范围。数据关系建议明确 `topic_id/root_comment_id/quote_id`：引用子回复不会把子回复变成新的嵌套容器。跨帖引用是否允许仍由产品决定。

独立 overlay 用例中，合法子回复对照通过；第三层拒绝和不存在引用拒绝两个断言失败，实际成功写入了这些数据。它们成功复现原版的约束缺口，**不是修复通过**；见 [审查材料](../audit/2026-10-26/README.md)。

### D02 · P2：现有内存事件不能充当可靠论坛广播

[event.go:20,38–44](../services/bbs-go/internal/pkg/event/event.go#L20) 使用 4 worker／1000 等待任务的进程内池，提交失败只记录日志。评论事务在 [comment_service.go:165](../services/bbs-go/internal/services/comment_service.go#L165) 完成，174 行才提交事件；当前通知目标主要是作者和被回复人。

进程故障可能造成正文已落库而没有事件，也没有所有看帖者的订阅语义。建议在同一 SQL 事务写 outbox，以 eventID、resourceID、version 幂等重试投递；客户端按游标补拉权威 API。OpenIM 自定义通知可作为候选传递方式，仍需验证实际订阅者规模与离线成本，不能把所有读者自动加成永久群成员。

论坛正文不要再双写为 OpenIM 聊天正文。OpenIM 成功接受消息不等于跨数据库事务成功；发送后内存 hook 不适合作为论坛唯一可靠来源。

## 4. OpenIM 特性核实与更正

1. **发送前回调默认关闭；启用后错误会阻断发送。** `config/webhooks.yml:2,32` 为 `enable:false`；`failedContinue` 仅见配置声明，选定标签没有读取它的执行路径。`pkg/common/webhook/http_client.go:60–83` 返回网络／解析错误，`internal/rpc/msg/send.go:57–58` 返回发送失败。此前研究根据配置字段推断超时放行的说法已更正。回调增加同步调用延迟与可用性耦合，应按实际代码验证超时与拒绝。
2. **原生有引用，也有撤回、物理删除和定时清理。** 不应把这些统称为商业能力。没有在当前消息路由中发现已发消息编辑接口；`BeforeMsgModify` 是发送前改包，不等于编辑已发送消息。
3. **保留策略不是按作品／会话配置完成的。** `config/openim-crontask.yml:2–4` 默认消息 365 天、文件 180 天；本项目各类私聊／群聊／作品内容的保留策略待定。
4. **封禁要处理已有连接。** token 默认有效期 90 天；`internal/rpc/auth/auth.go:194–201` 部分踢线失败只记日志。业务封禁需要停止签发、撤销 token、跨端踢线并重试或对账，不能只禁止重新登录。
5. **默认日志不符合严格隐私目标。** `config/log.yml:8` 为 debug 等级 6；`internal/msggateway/ws_server.go:517`、`internal/rpc/auth/auth.go:210–211` 有 token 日志，webhook 客户端在 Info 记录含消息内容的输入。需要删除／脱敏敏感日志并定义访问和保留规则，仅降低日志等级不能覆盖所有正文日志。
6. **未发现 1000 群成员的统一硬限制，但大群不是无成本。** 创建／加入路径没有该固定上限；`CreateGroup` 仅接受 WorkingGroup，不能把遗留 SuperGroup 分支等同开箱即用的公开观察频道。

## 5. 性能与部署可行性

### 可确认的执行成本

- BBS-GO 评论渲染对每个根楼取 3 条子回复，再逐条读取引用。20 个主楼各 3 条带引用子回复时，这两项会额外约 80 次读取，不计主楼自身引用等查询。它有分页，不是每条消息遍历整帖。
- Comment 主要是单列索引；应按实际查询 EXPLAIN 决定复合索引，并批量取引用／子回复预览。
- `topic_service.go:452` 同步更新浏览计数，热帖可能形成写热点；是否聚合写入应由实际压测决定。
- OpenIM `rpccache/group.go:56–69` 有成员缓存，不能说没有缓存。但 112–117 行每次将成员列表重建 map；推送仍获取群成员、查在线状态，并向网关扇出接收者列表。成本随群规模和网关数增长。
- `onlinepusher.go:63–112` 的并发 3 指网关 RPC，不是只能向 3 个用户发消息。`fullUserCache` 对象是在线用户状态，也不是每个进程缓存全部注册用户资料。
- `client_conn.go:33,89–93` 每连接写队列为 256，满后断连；需测慢客户端、补消息和重连潮。

### 默认配置需要改的地方

| 发现 | 实际含义与处理 |
|---|---|
| 网关 maxConn 为 100000，Mage maxFileDescriptors 为 10000 | Linux／Mage 启动路径设置 soft 和 hard RLIMIT_NOFILE；单网关默认启动不能据此承诺三万连接。直启二进制按 OS／容器限制另查。统一设置 nofile 或明确多网关拓扑 |
| websocketMaxMsgLen 配置为 4096，实际传入常量 51200 | 该配置没有接到 SetReadLimit；实际仍有 50KB 上限，不是无限包长。修字段连接并测边界 |
| BBS-GO 默认构建包含 SPA／Node SSR | 当前纯源码没有 build/spa，默认非 dev 编译依赖前端产物。制作后端独立镜像，沿用 Gin/GORM；本轮测试用 dev tag 避免前端 embed |
| 上游 Compose 使用 latest／浮动构建工具 | 不能保证运行的是审查提交；本项目镜像应从锁定源码构建并记录 digest／工具链 |
| OpenIM 根 Compose 不启动 Go IM 服务 | 主要是依赖、配套前端与监控；仍须规划服务构建与启动，compose 可解析不代表 IM 已运行 |
| etcd 无认证且映射宿主端口，Kafka 有 PLAINTEXT 外部端口 | 是示例部署条件风险，须隔离内网和宿主绑定；不把开发示例直接作为公网配置 |
| 后端默认 HTTP／WS | 公网用 HTTPS／WSS 反代，并禁止绕过反代直连内部端口 |
| PG 默认连接池每副本 idle50／open200 | 副本数量乘以池上限计入数据库连接预算；不是全站合计200 |
| BBS-GO 启动自动迁移 | 多副本升级前明确单独迁移与兼容发布流程 |

### 一人维护的成本

除内容服务和 PostgreSQL，还包括 OpenIM 的 MongoDB、Redis、Kafka、etcd、对象存储及多个 Go 进程。不能按“两份 Go 程序”估算维护量。前期使用明确的单套部署、固定配置、可恢复备份与最少自定义补丁；是否做高可用由目标可用性和预算决定，先不增加新的实时中间件。

三万连接之外，至少要分别测分散小频道、单热点大频道、论坛广播、下载并发、撤权与节点故障。同样 100 条消息／秒，若每条投递 50 人是 5000 次投递／秒，投递 10000 人则是 100 万次，负载完全不同。现阶段没有足够证据承诺硬件配置、P95 或比其他方案更快。

## 6. 建议保留的最小架构

```text
前端 ── HTTPS ── 业务 API（BBS-GO 扩展） ── PostgreSQL
                 │ 作品／身份组／论坛正文／资源元数据
                 ├─ 私有对象存储＋授权下载
                 ├─ 薄适配：用户、token、频道映射、成员／禁言投影
                 └─ SQL outbox → 增量事件 → 当前订阅者

前端 ── WSS ──── 修补后的 OpenIM ── 原生依赖
                 聊天正文／历史／多端同步
```

业务授权在一个权威位置定义，OpenIM 只保存需要执行的投影。避免把每次普通聊天都改成“正文先经过内容服务再转发”，但也不能把自定义角色仅保存在内容库却不约束 IM 发送。优先投影原生可表达的成员／禁言；原生表达不了的动作再评估同步回调及缓存失效。

论坛增量事件的传递可先验证 OpenIM 自定义通知；如果实际观众订阅和扇出成本不合适，再决定是否需要专门通道，不在审查阶段叠加更多组件。

本轮完成以下核对：

- 两份固定版本本地源代码调用链，以及 OpenIM 固定 tools／protocol 依赖源码。

## 8. 进入实现时的顺序

1. 修补 S01–S03 并做普通身份／跨用户／跨会话反例；收紧公网 API、token 和正文日志。权限检查集中在可信边界，不四处添加重复的静默回退。
2. 做一个最小纵向流程：统一账号 → 建卡 → 频道 → 论坛两种读取 → 一层回复与引用 → 增量事件 → 撤权 → 下载拒绝。先提供前端可联调契约。
3. 多副本前解决权限失效、可靠事件和迁移流程；文件受限前改私有存储入口。
4. 在明确消息量、热点观众与硬件预算后，以实际 SDK 和接收端时间测三万以上在线、P95／P99、丢失恢复与故障重连。

**推荐仍是沿用这两份代码做地基，但把“已选型”与“已安全集成、已达容量”严格区分。** 对一人后端而言，收益在复用既有论坛／IM 能力，代价在两套存储与权限生命周期，以及长期合并安全补丁。先通过上述小闭环再扩大改造，能尽早检验这笔成本是否值得。

## 9. 上游复核与推荐程度补充

同日用户追问 OpenIM 是否仍值得选择后，重新核对官方发布页和主分支：

- [官方发布页](https://github.com/openimsdk/open-im-server/releases)当时仍将 `v3.8.3-patch.18` 标为 Latest，所以上述发布版审查结果不能简单归结为拉了旧标签。
- [主分支提交 e3a08b844c2cea4ebcd40baf3f374bb2f659ad9b](https://github.com/openimsdk/open-im-server/commit/e3a08b844c2cea4ebcd40baf3f374bb2f659ad9b)的 [delete.go:95](https://github.com/openimsdk/open-im-server/blob/e3a08b844c2cea4ebcd40baf3f374bb2f659ad9b/internal/rpc/msg/delete.go#L95) 已在 DeleteMsgPhysicalBySeq 开头调用 `authverify.CheckAdmin(ctx)`。这项修补值得参考，但没有改写本地固定发布版，函数检查也不等于该主分支完成运行验证。
- 该提交的 SendMessage／SearchMessage 业务函数没有看到相应身份绑定／范围检查；此次只做定点复核，未重新审完整个主分支的入口、依赖和调用链，因此不把它直接判为与发布版完全相同的风险状态。
- [公开安全公告页](https://github.com/openimsdk/open-im-server/security/advisories)未列出已发布公告；没有公告不是没有漏洞的证据，也不代表维护者已对本次三项发现给出结论。

**推荐程度应收紧：OpenIM 保留为有复用价值、需要先通过安全和业务验证的选择，不能再按“安全省心的默认首选”背书。** 三条授权路径有局部修补的可能，但必须补回归并排查同类入口；更长期的成本是 DC 式角色与原生群角色之间的差异、作品撤权与长连接同步，以及多项基础依赖的一人维护负担。

这次审查没有证明 OpenIM 的性能差，也没有证明未经同标准审查的替代品更安全。产品选型决定保持不变；建议先验证小闭环，再决定是否承担长期深度绑定成本。没有自动切换到 main 或修改业务源码。
