## 新增的真实验证

夹具现在可在同一地址停止并重新启动它创建的原生子进程，每次都有新的进程和内存状态；不是仅调用 SDK Disconnect／Connect。每次停止都等待该子进程退出，再复用端口；日志附加到受限且忽略的诊断文件，配置、证书和 PostgreSQL 保持不变。未重启 PostgreSQL，不能把本轮说成数据库持久化重启验收。

| 场景 | 结果与严格断言 |
|---|---|
| 实时服务停止时提交消息 | 原生进程停止、SDK 检测到传输断开后，HTTPS 提交三条消息；真实 outbox 精确保留三条。 |
| 原生进程同地址重启 | SDK 自动重订阅，stream epoch 与原流不同，WasRecovering=true／Recovered=false；经授权 HTTPS 历史取得全部缺失消息，后续实时消息继续到达。 |
| 消息已投递但未确认时停止 | 暂时撤销消费者 DELETE，确认 WSS 已收到消息且真实删除失败；再停止该进程，未确认命令仍在 outbox。 |
| 去重缓存丢失后的重放 | 重启并先恢复订阅，再恢复消费授权；再次收到相同 event ID、相同消息 ID 及逐字节相同载荷，正文表始终只有一行。不能宣称跨重启只投递一次。 |
| 重放完成后的连续写入 | 待发布记录清空，新的实时消息正常到达。 |
| 事件契约 | 两类真实 WSS 事件均检查规范 UUID、version、type、scope_id、字符串 position；消息体作用域／位置与信封一致，帖子载荷与实际创建响应一致。 |

默认与 integration,realtime 回归、go vet、go mod verify、五个命令的 Linux／amd64 交叉构建通过；未在 Linux 运行这些命令。原有身份、TLS、论坛、分页、引用、事务、主动撤权及过期检查保留通过。测试容器／网络与原生子进程已清理；受限运行文件仍保留在忽略目录。

govulncheck v1.9.0 对含测试的 integration,realtime 调用图扫描未命中当时已知漏洞；它不覆盖原生服务的完整供应链审计。文档 JSON 示例另对照当前 OpenAPI 的 Entry schema 验证，并核对 sequence 与信封 position 一致。

## 当前事件字段

以下是 WSS publication 的 data，不包含供应商自己的 channel／offset 等帧字段。字段由实际事件适配器生成，正文的权威来源仍是业务消息表；outbox 是可能含正文的暂存投递载荷，不承担长期历史职责。

| 字段 | 语义 |
|---|---|
| id | 本次业务事件的稳定 UUID，用于识别重复投递；不等同于消息 ID。 |
| version | 当前信封版本 1，不是消息编辑 revision。 |
| type | forum.topic.created、forum.message.created；0.5.0 扩展 forum.channel.created 和 channel.message.created，信封仍为 v1。 |
| scope_id | forum.topic.created／forum.channel.created 对应论坛 ID；消息创建对应帖子／频道消息流 ID。 |
| position | 信封中的十进制 JSON 字符串；分别为论坛开帖位置或帖子消息创建序号。消息体对应字段实际叫 sequence，数值应一致。不是 WSS offset，也不是未来编辑／删除的变更游标。 |
| data | topic.created 为 Topic 元数据；message.created 为 Entry，含消息正文、同帖引用和可选 root_id。开帖正文通过消息历史读取，不在帖子列表事件中重复存一份。 |

合成示例（可选 quote_id、root_id 未出现）：

```json
{
  "id": "10000000-0000-4000-8000-000000000001",
  "version": 1,
  "type": "forum.message.created",
  "scope_id": "20000000-0000-4000-8000-000000000001",
  "position": "12",
  "data": {
    "id": "30000000-0000-4000-8000-000000000001",
    "stream_id": "20000000-0000-4000-8000-000000000001",
    "sequence": "12",
    "author_id": "40000000-0000-4000-8000-000000000001",
    "body": "hello",
    "created_at": "2026-10-28T16:00:00Z"
  }
}
```

## 前端合并与恢复顺序

1. 先通过现有 HTTPS 获取连接凭据与 channel 描述，按 [实时运行说明](../backend/deploy/realtime/README.md)无频道 JWT 订阅；等订阅成功后开始加载所需 HTTPS 历史页，加载期间缓冲实时事件，避免先读取、后订阅的空隙。
2. 合并历史与缓冲事件时，以消息 ID 保持一份正文；按 event ID 识别重复事件，以同一作用域的业务 position 排序。保留字符串／BigInt 精度，不将 WSS offset 当成业务分页游标。
3. 短断线时由 SDK 携带 epoch／offset 尝试恢复；WasRecovering 只表示尝试，只有 Recovered=true 才证明缓存连续。
4. Recovered=false 或首次加载时，从当前有权的 HTTPS 页面补读，必要时沿服务端 next 游标翻页，再合并缓冲事件。当前测试数据在单个 100 条页面内，不把它当成大型热点历史的性能验收。
5. 断连码 4001 后重新授权目标频道；权限拒绝停止该频道读取，依赖失败保持失败状态，不把 503 解释为消息已删除。重连时复核当前成员，不用旧 channel 描述当授权。
6. 当前只有创建事件；后续编辑／删除必须新增相应变更同步契约，不能只按新消息创建序号补拉。未知版本／类型不按现有结构强解，日志不记录令牌或正文。

这是交接协议与测试证据，尚未宣称同事的前端已经实现缓冲、去重和回退。临时幂等缓存不能提供永久的“仅一次投递”；本轮已实际复现跨重启的重复载荷，业务消费者需要容忍它。
