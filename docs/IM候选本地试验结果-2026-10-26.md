# MongooseIM／Tinode 本地试验结果

日期：2026-10-26（Asia/Shanghai）。两套候选均已实际启动，原生 WSS 核心功能、已有连接撤权和服务重启后的历史恢复通过。本轮确认两者可以继续做业务接入验证，尚未确定最终 IM；没有完成 BBS-GO 集成或三万在线验收。

用户决定：保留 BBS-GO 内容业务，替换 OpenIM，同时试用 MongooseIM 与 Tinode。旧 `services/open-im-server` 和相邻 NodeBB 项目保留，本轮没有修改上游服务源码或旧项目数据。

部署与复现：[本地试验入口](../deploy/im-trials/README.md)。语义依据：[共用验收契约](IM候选试验验收契约.md)。可复核的无密钥 JSON：[审查材料](../audit/im-trials-2026-10-26/README.md)。

## 实测结果

客户端是 Node.js 22.16.0 手写原生 WebSocket 协议探针，MongooseIM 使用 XMPP，Tinode 使用自身 JSON 协议。均以普通合成账号连接，发送 ACK 与真实接收分别观察。没有把手写客户端等同于正式浏览器 SDK。

| 场景 | MongooseIM 6.10.0 | Tinode 0.25.3 |
|---|---|---|
| 可信 WSS、错误密码拒绝 | 通过 | 通过 |
| 发送者身份绑定、防伪造 | 通过，伪造 `from` 明确拒绝 | 通过，特权代发拒绝，普通自报作者不成为权威作者 |
| 私聊对端实际收取、A1/A2 多端同步 | 通过，观察到 Carbons | 通过，观察到第二会话实际收取 |
| 可写私密房间、非成员订阅／发言／历史拒绝 | 通过，普通 MUC | 通过，可写 group，非只读 channel |
| 每页 2 条历史、原生游标、重建客户端 | 通过 | 通过 |
| 真实断线后补拉、按原生 ID／序号去重 | 通过 | 通过，记录了 WebSocket close 事件 |
| 保持原连接撤权：停止投递、拒绝发言／历史、重连仍拒绝 | 通过 | 通过 |
| 实际重启应用、保留数据库后恢复既有历史 | 通过，私聊和房间 SQL 历史 | 通过，9 条已确认的合成群消息 |
| 普通用户越权撤回／删除、权限提升、管理路径隔离 | 已执行子项通过；完整 A08 为 partial | 已执行子项通过；完整编辑语义仍未验收 |
| 引用、编辑与显示合并 | 本轮未验证引用与 XEP-0308 编辑授权 | 引用／替换元数据收取存储通过，目标授权和安全编辑合并未完成 |

MongooseIM 主试验有 17 个子检查通过，统一矩阵 A01–A07 为 pass，A08 因缺少完整编辑作者策略验证而固定为 partial。Tinode 脚本 A01–A08 与 B01/B02 的已定义断言通过；B01/B02 的 pass **仅指元数据传输／存储**，不能扩展为完整引用或编辑安全验收。两个服务的专项重启探针均通过；MongooseIM 重启报告通用矩阵中 A05 的 `not_run` 表示未重跑分页，实际重启恢复由该报告 `results` 下两个专项 pass 记录。

撤权观察窗口分别为 MongooseIM 750ms、Tinode 1000ms。它们证明本次撤权后没有观察到后续投递，不是生产最坏撤权时延保证；不能把窗口长度或单次管理响应作为性能排名。

TLS 正对照使用本地 CA，证书验证开启、实际协商 TLS 1.3；空信任链的负对照得到 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`。代理的管理／诊断路径返回 404，没有关闭证书验证。

## 发现的语义差异

**Tinode 的编辑头不能直接作为可信编辑指令。** 实测 B 发布 `replace` 指向 A 的消息时返回 202，事件作者仍为 B，A 的原始消息没有被改写。`native_server_rejects_cross_author_replace_header=false` 表示服务接受了带此元数据的新事件。业务适配与前端在合并编辑事件前必须检查原作者、原消息会话和可见范围，否则客户端可能把 B 的事件错误显示成 A 的修改。引用 `head.reply` 本轮同样只验证传输与存储。

**Tinode 的“硬删除请求成功”不一定表示全体删除。** 没有 D 权限的成员发硬删请求会返回 200，但降为个人软删除；本轮另查拥有者历史，确认原消息仍在。产品 API 必须明确区分个人隐藏、作者撤回和管理删除，不能只按状态码向前端汇报“已为所有人删除”。

**MongooseIM 本轮的原生撤回作者校验通过。** 非成员撤回被拒绝，入房的 B 不能撤回 A 的原文；正对照由 A 本人撤回后，MAM 原文消失并出现对应 tombstone。它没有覆盖全部编辑、物理清理与附件删除语义，不能概括为隐私功能已全部完成。

两者的成员权限都能承接试验里的读、写、订阅和撤权，但不等同于已实现 DC 身份组。作品归属、作者管理范围、平台覆盖规则以及角色组合算法仍由业务层定义。

| 共享依赖 | 独立 PostgreSQL 17 实例、分库分角色；Caddy 终止 TLS；摘要见 [images.lock.json](../deploy/im-trials/images.lock.json) |
| Docker 环境 | Desktop 4.41.2／Engine 28.1.1，WSL2 Linux `6.6.87.1-microsoft-standard-WSL2`，16 CPU，Docker 可见总内存约 9.71 GiB |
| 存储 | Docker VHD 在 `E:\Docker\DockerDesktopWSL\disk\docker_data.vhdx`；本项目 runtime、日志与 Docker 构建缓存位于 E 盘 |
| 资源限制 | MongooseIM 内存 1GiB、2 个 BEAM 调度器；Tinode 内存 512MiB、GOMAXPROCS=2；PostgreSQL 768MiB；Caddy 128MiB。调度器数不是容器 CPU 配额 |
| 试验房间人数配置 | 两者均为 128，仅是功能试验配置，未确定产品人数上限 |

MongooseIM 采用 SCRAM 密码存储、WSS 上的 SASL PLAIN、SQL MAM 同步写、SQL roster/offline、Carbons 和成员制持久 MUC，关闭 s2s。配置需包含 `mod_presence` 才能正确路由 presence；WS ping 为 30000 毫秒。

Tinode 禁用 gRPC、静态网页、调试指标、pprof、推送及 WebRTC，主容器仅使用无超级用户／CREATEDB／CREATEROLE 权限的运行角色。MongooseIM 数据库角色也没有这三项权限。只有一次性 Tinode schema 初始化使用本试验数据库管理凭据，该配置不挂到主容器。

代理只绑定 `127.0.0.1:19443`，后台端口不直接发布，CA 私钥不挂容器。Windows runtime DACL 限于当前用户、SYSTEM 和 Administrators，并实际抽查 `fixture-secrets.json`、CA 私钥、Tinode bootstrap、MongooseIM 账号文件：没有额外 Allow 主体。代理后的隔离容器网络本轮是明文，Origin 白名单未配置；这不是可直接公开的生产部署。

## 复现及下一阶段

`node deploy/im-trials/run.mjs up`、`test`、`restart-test` 均已实际执行成功；启动流程也验证了已有库和密钥复用。MongooseIM 首次从源码构建耗时主要在获取、编译依赖，后续构建命中缓存。最初的 WSS 失败来自 Codex 网络沙盒，使用已授权的本机执行后恢复，不能将其记为候选能力缺失。

当前四个试验容器保持运行，数据没有清理；停止命令为 `node deploy/im-trials/run.mjs stop`。本轮未启动 BBS-GO 或旧 OpenIM/NodeBB。后续应以同一条真实业务链继续比较：业务登录→作品频道→双人收发→身份组撤权→引用/编辑→私密附件。普通聊天保留原生直连，业务层只负责身份、授权、会话映射与内容事件。

对于当前 Go 内容地基和单后端维护的条件，Tinode 的 Go 服务与 JSON 协议值得优先做业务适配验证；代价是引用／编辑、文件授权等产品语义需要补齐。MongooseIM 保留为另一条候选，原生 XMPP/MAM/Carbons/撤回组合本轮可用，但维护和深改需要 Erlang/OTP 与 XMPP 扩展经验。这是基于本地接入复杂度的工程判断，不是吞吐或整体安全性排名。

未完成：正式浏览器 SDK、业务统一登录、完整身份组及作品权限、帖子两种表现和一层回复约束、引用目标授权、安全编辑、附件会话授权、保留期限、用户搜索、公开大频道、账号级会话撤销、多节点及三万在线负载。数据库连接池、压缩和资源限制不同，本轮不报告可比的 P95/P99 或最大连接数。
