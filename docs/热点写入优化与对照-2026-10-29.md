# 热点回复写入优化与对照

日期：2026-10-29（Asia/Taipei）。依据 [算法适配研究](../../research/algorithm-selection-2026-10-29.md)先落地短事务候选。结论：保留“小 CTE＋pgx.Batch”回复路径；本机三轮中位数显示 32 并发单热点吞吐约增加 33%、P95 下降约 46%，但该场景 P50 上升，仍有明显排队和尾延迟。不能据此承诺生产容量或全面延迟改善。

后续 0.4.1 又加入有界写事务预算，持续混合负载与取舍见 [后续记录](混合负载与写入准入-2026-10-29.md)。本文保留首轮 0.4.0 的历史实现、数字与差异；复现旧 A/B 应固定当时快照，不能直接将旧补丁应用到当前准入代码。

## 这次采用什么

仅调整 PostgreSQL 适配的 [回复写入](../backend/internal/postgres/forum.go) 与 [事件编码](../backend/internal/postgres/forum_events.go)：

1. 保留当前权限查询及每流行锁。
2. 加锁后用独立 READ COMMITTED 语句检查幂等，避免并发赢家提交后仍使用旧快照。
3. 小 CTE 更新事务计数器，再从 RETURNING 取得序号并写入正文，返回实际 sequence／created_at。
4. 用数据库返回值编码原事件，然后用 pgx.Batch 写楼层关系和 outbox。必须检查 Close 的错误，成功后才提交外层事务。

引用校验仍在 Go 业务边界，CTE 只组织持久化依赖。开帖主流程、业务规则、权限语义、数据库迁移、运行角色授权与 OpenAPI 0.4.0 契约保持现状；没有新增依赖、缓存、工作进程或配置开关。原有分页、幂等、顺序与事务 Outbox 适配当前需求，继续使用。

本轮复用已经引入的 pgx v5.11.0（MIT），没有复制上游源码。重新查询 [官方最新正式发行](https://github.com/jackc/pgx/releases/latest) 返回 v5.11.0、2026-09-07 发布、非预发行；固定记录见 [v5.11.0](https://github.com/jackc/pgx/releases/tag/v5.11.0)。本次无需为 Batch 升级模块；这不表示其他全部依赖均已重新核对到最新。

方法依据 [pgx Batch 文档](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.11.0#Batch)、固定版本 batch.go 的 Close 错误处理，以及 [PG WITH／RETURNING](https://www.postgresql.org/docs/18/queries-with.html) 和 [READ COMMITTED](https://www.postgresql.org/docs/18/transaction-iso.html)。同条语句里的数据依赖通过 RETURNING 传递；不把幂等检查与取得锁硬合成一条语句。已有四项 SQL 性质实验继续回归。

## 测量方式

沿用 [首次基线](本地性能基线-2026-10-29.md)的实际 HTTPS API 工作负载：Go 1.27.3、HTTP/2／TLS 1.3、每请求 RS256 验签与用户查询、PostgreSQL 18.6／TLS、MaxConns=16、GOMAXPROCS=16。每轮新建隔离数据库、33 帖、28225 条预置 1KiB 消息，读取每场景 2000 次、写入 600 次，各以 1／8／32 在途并发执行，计时前各预热 64 次。没有 WSS 消费者参与性能测量。

按 A1、A2、A3、B1、B2、B3 顺序运行，A 是原路径，B 是候选。每轮计量 15600 次，共 **93600 次、零错误**。性能运行期间没有同时运行编译检查或其他压测。客户端与服务端仍共享本机 CPU，数据库使用临时内存存储；没有随机交错、独占主机、开放到达率或置信区间，因此不能排除环境随时间变化的影响。

另在每轮负载完成后，用独立单连接池跑无引用／带引用两个串行探针：各预热 1 次、记录 16 次。探针不经过 HTTPS／JWT，不计入上面的吞吐；每轮另有 34 次写入。它记录驱动调用次数，以及“收到流锁查询成功响应 → 收到提交确认”的客户端观察时间，**不是数据库服务端的精确持锁计量**。每轮 outbox_pending=4017 是探针前的快照；探针后还会增加 34 条事件。

全部分轮结果、192 个探针及原／新代码 SHA-256 见 [JSON 快照](性能基线/2026-10-29-write-optimization.json)。保留 [实现差异](性能基线/2026-10-29-write-optimization.patch)便于在隔离副本恢复 A 路径；不把旧路径作为生产开关长期维护。原始含执行计划的运行结果留在忽略的 runtime/audit/algorithm-improvement/，公开快照不含 DSN、密钥、正文、用户或测试作用域 ID。

## 三轮对照结果

以下每个指标分别取三轮中位数，**不是合并原始请求后重新计算的分位数**。吞吐单位为请求／秒，延迟为毫秒；“原 → 新”对应 A／B。

| 场景 | 并发 | 吞吐原 → 新 | 变化 | P50 原 → 新 | P95 原 → 新 | P99 原 → 新 |
|---|---:|---:|---:|---:|---:|---:|
| 历史首页 50 条 | 1 | 275.9 → 255.3 | -7.5% | 3.66 → 3.72 | 4.48 → 4.89 | 6.07 → 6.37 |
| 历史首页 50 条 | 8 | 1083.9 → 1038.0 | -4.2% | 7.11 → 7.45 | 10.12 → 10.70 | 11.69 → 12.09 |
| 历史首页 50 条 | 32 | 1361.4 → 1326.5 | -2.6% | 23.20 → 24.03 | 29.30 → 29.05 | 32.84 → 31.72 |
| 第 19000 条后 50 条 | 1 | 308.7 → 292.9 | -5.1% | 3.16 → 3.22 | 4.16 → 4.27 | 5.14 → 5.34 |
| 第 19000 条后 50 条 | 8 | 1063.8 → 1080.6 | +1.6% | 7.18 → 7.09 | 10.58 → 10.25 | 11.90 → 12.02 |
| 第 19000 条后 50 条 | 32 | 1263.4 → 1308.4 | +3.6% | 24.88 → 24.08 | 32.46 → 30.53 | 37.30 → 33.20 |

| 同一热点帖 | 8 | 238.9 → 327.9 | +37.3% | 12.66 → 9.27 | 46.95 → 41.26 | 577.13 → 407.01 |

32 并发热点吞吐的三轮范围由 243.9–254.2 变为 270.4–334.4；P95 由 239.62–399.16ms 变为 139.31–164.25ms。分散写三轮范围重叠明显（1213.1–1623.4 与 1126.6–1792.0），所以 +15.1% 只能表述为本次中位数变化，不能当成稳定容量增益。

**不能省略的退步：热点 32 并发 P50 的三轮中位数上升约 38%。** 三轮候选 P50 分别约 67、110、130ms，原路径约 78–80ms；8 并发的 P99 仍有约 407ms。当前没有锁调度／CPU profile，不能断言这些尾部全由行锁或公平性造成，也没有证据声称平均用户体验在所有负载下均改善。

读取路径没有修改，测得 -7.5% 到 +3.6% 的变化说明环境和短样本漂移仍存在；不能把它直接归因到回复代码，也不隐去较差结果。后续混合／持续负载需要确认写入收益是否能重复、热点是否拖累其他流。

## 调用与锁区间探针

| 场景 | 驱动执行组原 → 新 | 顶层语句原 → 新 | 锁成功响应至提交确认中位数 |
|---|---:|---:|---:|
| 无引用回复 | 8 次单查询 → 5 次单查询＋1 批次 | 8 → 7 | 3.737 → 3.145ms |
| 带引用回复 | 9 次单查询 → 6 次单查询＋1 批次 | 9 → 8 | 4.735 → 3.760ms |

每项每阶段有 48 个串行样本。均包含 BEGIN／COMMIT，不含 HTTPS 用户查询。批次含两个 SQL；CTE 内部仍需更新与插入，不能将顶层语句减少误称为少执行了一项业务持久化。执行组是驱动观测，不是逐包抓取的实际网络往返数，冷预编译也可能增加通信。

32 并发热点的池等待累计值中位数约 37.28 → 27.97 秒；这些是重叠请求等待的总和，仍有约 1173–1176 次空池获取。此次没有调整池上限，有界准入与连接预算仍值得后测。

## 正确性验证与维护评估

新增／强化的真实数据库回归覆盖：批次第一项楼层关系失败、第二项 outbox 失败，均返回原 CHECK 错误并回滚正文、关系、事件和计数器；修复后同一个请求键可成功重试。另核对返回值／数据库序号与时间／事件载荷一致，及撤权后重试已有回复仍被拒绝。

完整 integration,realtime,cluster,acceptance,algorithms 回归通过，postgres 包用时 83.062s；包括并发幂等、引用／层级／越权、真实 WSS、跨节点撤权、消费者失败重试、65 秒中断、缓存过期、重放与七页补读合并。默认回归、全标签 go vet、模块校验和 Linux amd64 六个命令交叉构建结果一并核实。交叉构建不等于在 Linux 执行 Go 服务，故障回归使用 Windows 原生实时进程＋Linux 容器依赖。专用测试容器和网络已清理。

业务实现只涉及两个 PostgreSQL 适配文件；外部协议和业务类型不依赖 Batch 或 CTE。更换存储需要重做适配与事务保证，无需为此修改 HTTP／论坛规则；移除实时消费者仍能保存正文与 outbox，实际推送自然需要对应消费者。本轮没有为测量添加生产监控路径或运行配置。

## 对需求与后续方案的独立判断

| 要求或候选 | 本轮判断 |
|---|---|
| 通用论坛独立于作品、明确边界、简洁代码 | 合理且已有真实扩展理由；继续按具体业务关联扩展，不预建庞大插件体系。 |
| 安全与隐私加密 | 是持续边界；保留权限／幂等／原子性验证。生产存储、备份加密及管理员审计仍有独立门槛，性能数字不能替代它们。 |
| 最新潮技术栈 | 适合作为现代稳定发行的偏好；依赖和组件必须有具体收益、兼容性与维护验证，不因新名字就替换现有实现。 |
| 本次短事务候选 | 有重复出现的热点收益且改动局限，保留为当前路径；同时公开 P50 退步和样本局限，不承诺全部延迟改善。 |
| 三万以上在线、完整聊天、一名长期维护者 | 可作目标，尚不足以推导硬件或容量；需消息到达速率、热点订阅人数、扇出、恢复和延迟指标，并按阶段交付。 |
| 缓存、UUIDv7、通知、流分区、单写者、CDC | 暂无新增实测证据要求本轮采用，继续保留为候选；不把研究清单机械变成实施清单。 |

下一步先用热点写入＋普通帖读写的混合持续负载核实排队影响，再决定有界准入、连接预算与拒绝／重试契约；它们可能改变成功率与等待策略，需一起比较，不能只挑成功请求的低延迟。另行测提交到 WSS 可见及扇出。P3 功能和 P6 正式容量／故障 SLA 保持各自验收边界。
