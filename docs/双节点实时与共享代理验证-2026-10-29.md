## 复用依据与固定版本

[Centrifugo engine 文档](https://centrifugal.dev/docs/server/engines)区分单进程 memory engine 与可供多节点使用的 Redis／Valkey engine；固定版本的 [engine 配置](https://github.com/centrifugal/centrifugo/blob/v6.10.2/internal/configtypes/engine.go)及 [Redis 配置](https://github.com/centrifugal/centrifugo/blob/v6.10.2/internal/configtypes/redis.go)用于核对地址、用户、密码、共享 prefix 和自定义 CA。没有添加上游不存在的配置项，也没有修改上游源码。

沿用已校验的 Centrifugo 6.10.2、Go SDK 0.13.0、Go 1.27.3 和 PostgreSQL 18.6。新增夹具采用当日官方最新稳定版 [Valkey 9.1.3](https://github.com/valkey-io/valkey/releases/tag/9.1.3)，2026-10-26 发布。[官方镜像仓库](https://github.com/valkey-io/valkey-container)列有 GHCR；Docker Hub 直连超时后从官方 GHCR 下载同一版本，未替换成第三方镜像。linux/amd64 的平台摘要与本地 image ID 已核对，运行时实际输出版本 9.1.3，详见 [镜像锁定](../backend/deploy/realtime/images.lock.json)。

Valkey 项目主许可证为 BSD-3-Clause；已阅读固定版本 [COPYING](https://github.com/valkey-io/valkey/blob/9.1.3/COPYING)及其捆绑组件声明。沿用 Centrifugo Apache-2.0、SDK MIT；这不等于完成镜像全部依赖的供应链审计。来源与采用边界另见 [复用记录](../../research/realtime-cluster-reuse-2026-10-29.md)。

## 实际拓扑与职责

```text
合成身份 → HTTPS API／私有订阅代理 → PostgreSQL TLS
                   ↑                         ↓ 事务 outbox
              Centrifugo A ← shared Valkey → Centrifugo B
                   ↑ WSS                       ↑ WSS
                 Alice                      Alice、Bob
```

两个实时进程使用各自的本机端口、相同身份签名密钥、代理凭据、共享 broker prefix，以及相同消费者名称 odysseia_outbox 和单分区配置。官方消费者按名称和分区使用数据库 advisory lock 协调；不按节点发明不同 consumer name。两个进程均只用消费角色读取／删除 outbox，正文写入仍由 API 运行角色完成。

共享 Valkey 负责跨节点广播、恢复流和短期发布幂等状态，不是业务正文权威来源。完整业务历史仍从当前有权的 HTTPS 接口读取；没有把缓存变成第二套数据库。

集成测试位于 [双节点测试](../backend/internal/postgres/realtime_cluster_integration_test.go)，安全断言位于 [broker 测试](../backend/internal/postgres/realtime_broker_test.go)。复用现有 HTTPS 服务装配、数据库角色授权、真实进程启停与协议断言，未复制整套单节点场景。

## 通过的真实场景

| 场景 | 断言与结果 |
|---|---|
| 共享服务传输和认证 | 实际协商 TLS 1.3；不可信 CA、错误主机名、仅 TLS 1.2 客户端均拒绝。匿名 PING、错误密码拒绝；正确账号可 PING。 |
| 隔离授权 | 关闭 default 用户；应用用户的键和 Pub/Sub 频道限定本次随机 prefix。实际拒绝读取其他 prefix 的键、拒绝 CONFIG GET dir。未执行清库或修改管理配置。 |
| 两节点有序投递 | 六条数据库提交消息由连接在 A／B 的三个 SDK 客户端收到；逐条核对正文、消息 ID、业务位置及相同的有序事件 ID。 |
| 两消费者真实重试 | 撤销消费角色 DELETE 后，发布已成功但 outbox 精确保留一条；两个原生进程日志各实际出现本次确认权限错误，证明均尝试消费。恢复授权后队列排空，后续屏障消息验证没有重复广播。 |
| 节点停止时继续服务 | 实际停止 A，连接观察到传输断开；提交两条消息，存活的 B 继续消费和投递。 |
| 切换节点恢复 | 将客户端在 A 的最后 epoch／offset 交给 B 的新 SDK 连接；WasRecovering=true、Recovered=true、epoch 不变，两条遗漏消息及事件 ID 完整一致。 |
| 原地址重启恢复 | 再启动 A，原 SDK 自动重连；共享 broker 保留历史，恢复成功且 epoch 不变，缺失消息 ID 与 B 一致。 |
| 跨节点主动撤权 | 维护事务移除 Alice 后，A、B 及换节点后的三个连接都收到 4001／permissions changed。旧身份 JWT 在 A 和 B 新订阅均被代理以 103 拒绝，持久历史读取也被拒绝。 |
| 定向断连 | Bob 的现有连接继续收到新消息，没有传输中断或撤权事件；Alice 三个客户端未收到撤权后的消息。 |

测试缓存只保留两条，本轮节点停止期间恰好补两条，特意验证有效窗口内的连续恢复。SDK 通过 GetState 返回测试预存的 stream position 完成显式换节点；没有假设已存在自动负载均衡，也没有实现前端的完整状态加载。

本轮双节点故障恢复与此前 [memory engine 重启验证](实时服务重启与事件接入契约-2026-10-29.md)结论不同：共享状态仍在时可保留 epoch 并恢复；memory engine 重启会失去状态，需要 HTTPS 补读。共享状态丢失、缓存过期和幂等窗口结束仍允许重复，客户端继续按稳定事件 ID 去重，不承诺永久仅投递一次。

## 运行与检查

在 backend 目录使用已校验的原生 Centrifugo 程序执行：

```powershell
pwsh -File deploy/postgres/test.ps1 -GoExecutable go -TestTags 'integration,realtime,cluster' -CentrifugoExecutable '<已校验的centrifugo.exe路径>'
```

全标签集成测试、默认测试、包含全标签的 go vet、go mod verify 及五个命令的 Linux／amd64 交叉构建通过。Go 测试和原生 Centrifugo 实际运行于 Windows，PostgreSQL／Valkey 实际运行于 Docker Linux；没有声称 Go 命令已在 Linux 执行。运行资源已清理，受限且忽略的凭据／诊断文件保留于 runtime。

govulncheck v1.9.0 对包含 integration,realtime,cluster 测试的 Go 调用图未命中当时已知漏洞；公开漏洞数据库更新时间为 2026-10-27。这项结果不覆盖原生 Centrifugo 和 Valkey 容器的完整供应链审计。

## 仍待验收

- Valkey 当前只有一个临时实例，关闭持久化；本轮停止的是实时进程，没有验证 Valkey 故障切换、复制、持久化恢复、数据库重启或跨主机网络分区。
- 短期重试去重不保证永久仅一次投递；长时积压、坏命令隔离／告警、顺序与热点分区、正式撤权 P95／P99 及三万活跃连接容量仍待验证。
- 前端完整联调、真实 IdP、完整身份组、作品和完整 IM 继续按产品基线推进。
- Go API／PostgreSQL 客户端和本轮 Valkey 链路要求 TLS 1.3；原生 Centrifugo 的 TLS 最低仍为 1.2，严格生产入口待落实。存储／备份加密、生产密钥管理和完整管理员审计尚未验收。

当前仍处于 P2 收尾；基础双节点投递／恢复／撤权已有证据，不等同于生产多节点高可用验收。
