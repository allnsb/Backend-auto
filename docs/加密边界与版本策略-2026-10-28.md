# 加密边界与版本策略

日期：2026-10-28（Asia/Taipei）。产品要求以 [产品需求基线](产品需求基线.md) 为准。

本次用户重申公网必须 HTTPS、隐私数据需要加密，并希望采用最新潮的技术栈与版本。随后明确选择：**保留服务端处理消息；HTTPS／WSS＋存储和备份加密，严格控制管理员访问。**

以下将已确认要求与工程做法分开记录。本次只改文档，没有配置服务、升级依赖或验证实际加密效果。版本证据见 [来源索引](../../research/encryption-and-version-policy-2026-10-28.sources.json)。

后续实施状态见 [Go 实施里程碑](后端边界与首个里程碑.md)：HTTPS 工程地基已开始验证，不代表本文中的存储、备份、内部链路和管理员权限均已实施。

## 1. 传输层的明确含义

此前技术栈表中的“HTTP”是接口／路由层名称，net/http、chi 或 Axum 均不意味着要公开明文业务端口。对外表述统一改为“HTTPS API”，实时连接明确为 WSS。

| 链路 | 规划要求 |
|---|---|
| 浏览器／客户端 → 公网 API、登录、下载 | HTTPS，正确验证证书；不通过明文连接提交身份、令牌或业务数据。 |
| 浏览器／客户端 → 实时服务 | WSS，订阅仍需业务授权；加密不代替会话成员／身份组判定。 |
| 反向代理 → 业务／实时服务 | 网络连接采用 TLS 并验证上游证书，避免只加密到代理这一段。 |
| 应用 → PostgreSQL | TLS 并验证服务器身份；采用驱动中等效于 verify-full 的设置，配合服务端强制规则。 |
| 应用／实时服务 → Valkey | TLS，验证证书；不因处于内网就默认为可信。 |
| 应用 → 身份服务、对象存储、备份目的地 | HTTPS／对应 TLS 协议，采用受限服务身份。 |

优先协商 TLS 1.3；最低兼容范围在目标客户端与部署配置中明确，不关闭证书验证、不静默降级。Caddy 的 [TLS 文档](https://caddyserver.com/docs/caddyfile/directives/tls)说明其当前默认范围为 TLS 1.2–1.3；如收紧最低版本，应列入兼容验证。

HTTPS API 可以启用 HTTP/3，并保留 HTTP/2 等客户端兼容路径；[Caddy 支持相应协议](https://caddyserver.com/docs/caddyfile/options)。HTTP/3 是请求传输选择，不能代替消息历史、权限、引用和多端同步，也不表示必须改用实验性的实时协议。

PostgreSQL 的 [TLS 支持](https://www.postgresql.org/docs/current/ssl-tcp.html)、[证书验证模式](https://www.postgresql.org/docs/current/libpq-ssl.html)和 [Valkey TLS](https://valkey.io/topics/tls/)均需显式核对实际配置；仅安装组件不等于已经开启。

## 2. 存储、备份和管理访问

已确认需要存储和备份加密。以下是覆盖范围与实现建议，具体供应商和密钥服务待定：

- **数据库**：持久卷／文件系统加密覆盖数据库数据、WAL、临时文件及落盘副本，逻辑导出和备份也单独加密。不把 PostgreSQL 安装本身描述为自动拥有全库透明加密。
- **附件与资源**：使用私有对象存储，启用受验证的静态加密能力；下载前执行归属与可见性检查。封面、资源和私聊附件的授权场景分别定义。
- **缓存和中间数据**：若 Valkey RDB／AOF、outbox、搜索索引、临时上传、导出或故障转储持有隐私数据，纳入加密覆盖、访问限制和保留清理；不只保护最终消息表。
- **备份**：备份产物和传输都加密，备份身份与生产写入身份分开；恢复演练同时验证密钥可用、权限和历史清除规则。
- **密钥**：使用成熟的密钥管理／加密能力；密钥与密文分开授权管理，记录 key ID／轮换与恢复方案，不写进源码、镜像、日志或同一份普通数据备份。
- **管理员**：区分运营管理、基础设施运维和应用服务身份；私密正文访问按明确目的、授权和审计处理，具体规则仍待需求基线 Q05 决定。管理员角色不自动获得全部私聊读取权限。
- **日志**：令牌、Cookie、私聊正文、敏感附件链接和密钥不进入普通日志；日志自身也有访问、留存和加密边界。

参考：[PostgreSQL 加密选项](https://www.postgresql.org/docs/current/encryption-options.html)、[S3 加密方式](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html)。AWS S3 的默认加密不能推广为所有 S3 兼容服务的默认行为。

服务端仍可按授权解密并处理消息。磁盘／对象加密保护落盘数据，不能单独阻止已经获得在线数据库或应用权限的人读取；需要与权限隔离和审计一起落实。当前没有选择端到端加密，也不宣称后台或服务进程在任何情况下都无法接触正文。

敏感字段是否增加应用层信封加密，应结合所选存储、检索、事件投递和密钥方案确定，不未经设计就把它叠到所有字段上。使用成熟库／服务，不自行发明密码算法或协议。

## 3. 版本策略

**用户已确认的偏好**：技术栈要现代，优先近期活跃发展的方案和最新版本，避免无依据沿用旧教程／旧版本。

**建议的生产执行方式**：

1. 默认从最新稳定正式发行选择，不把“最新潮”自动解释为用户接受 RC、beta 或 nightly。
2. 以实现／发布时重新查询的结果为准；下表仅为本次检查快照。
3. 锁定精确工具链、依赖和镜像摘要；不在生产配置中使用漂移的 latest 标签。
4. 升级通过构建、接口、权限、恢复和相关负载回归；安全补丁优先安排。存在兼容问题时记录证据与升级路径，不静默退回老版本。
5. 最新发行不自动证明全套兼容、没有安全问题或容量达标；维护范围、版本生命周期和实际复用收益仍纳入选择。

## 4. 技术路线对照与最终 Go 语言决定

Go／Rust 对照后，2026-10-28 用户明确“嘛还是用go吧”，因此业务主语言已选 Go。框架、数据库和其他配套仍为工程建议；现代性、当前版本、加密和简洁编码要求继续适用。下表保留比较依据。

| 方向 | 具体候选 | 收益与代价 |
|---|---|---|
| Go 路线：语言已确认 | Go 1.27.3＋chi 5.5.0＋pgx 5.11.0／sqlc 1.31.1，具体配套仍为建议 | 与已找到的 Go 业务代码同语言，便于局部移植；使用显式错误与事务流程。实施时重新复核并锁定当前稳定版本。 |
| Rust 路线：历史对照 | Rust 1.99.1＋Axum 0.8.9＋Tokio 1.54.1＋SQLx 0.9.0 | 适合重视类型表达、编译期约束与 async 生态的取向；此前仅作对照，当前不作为业务主栈。 |

两条路线原本可使用同样的 PostgreSQL、Centrifugo、Valkey、OIDC、私有对象存储和 HTTPS／WSS 契约；当前沿 Go 路线推进，不同时引入两套业务主栈。

[Axum](https://docs.rs/axum/latest/axum/)与 Tokio／Tower 生态协作，[SQLx](https://docs.rs/sqlx/latest/sqlx/)提供异步 SQL 和 TLS 配置能力；这些描述不构成整套兼容或安全验收。

本轮比较后用户亲自选定 Go。首个小闭环仍用于验证模型、权限、恢复及维护成本；没有创建第二套后端，也没有据此锁定全部配套、预算或首发范围。
