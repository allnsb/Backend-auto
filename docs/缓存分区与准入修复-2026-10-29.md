# 缓存、Outbox 分区与准入修复

> 历史时点记录：当前 0.4.5 已移除逐条通知并改每流单活动写者，最新独立进程／磁盘对照见 [通知锁修复](独立进程压测与通知锁修复-2026-10-29.md)。本报告原始结果与失败需求保留。

日期：2026-10-29（Asia/Taipei）。本报告记录 OpenAPI info.version **0.4.3** 时点，六项迁移。用户授权先采用缓存和分区等候选，再复测、修复并指出剩余问题。本轮采用正文页缓存／singleflight、Outbox 逻辑消费分区与事务通知；复测后修复单流等待者挤占共享接纳容量。**普通写在当前 16 热帖场景得到保护，但最高档热点仍大量拒绝，生产容量没有通过。**

后续 0.4.4 的同批读取与有保留空间的突发接纳见 [最新记录](同类社区策略与优化-2026-10-29.md)；本文数字和当时 12 名额规则保留，不回写历史。

全部旧版、仅候选、修复后两轮、短 API 对照、预热和源码／二进制指纹见 [聚合快照](性能基线/2026-10-29-cache-partition.json)。此前 [0.4.2 多热帖结果](多热帖与实时扇出压测-2026-10-29.md)原样保留，本轮基线为另一次实际重跑，不替换历史中的较差结果。复用来源、精确版本、许可和不采用原因见 [来源索引](../../research/cache-partition-reuse-2026-10-29.sources.json)。

## 采用的位置与边界

| 候选 | 当前实现与判断 |
|---|---|
| 有界正文页缓存 | 采用 Ristretto v2.4.2（Apache-2.0），估计成本预算 64MiB、TTL 5 分钟。缓存追加型正文页，不缓存身份、成员关系或拒绝结果；64MiB 不是进程 RSS 上限。 |
| 相同内容查询合并 | 复用已锁定的 x/sync v0.24.0 singleflight，只合并相同内容键的在途加载。等待者独立取消；首个加载者取消可能使共享加载失败，错误不缓存。 |
| Outbox 逻辑分区 | 采用原生消费者的 5 个分区：0 为 disconnect 控制，1–4 为 publish 数据；数据库根据 scope UUID 最后一个字节稳定取模。相同作用域保持同分区，不同作用域可能碰撞，无跨分区全局顺序保证。 |
| 通知唤醒 | 同事务 INSERT 触发 NOTIFY，只携带分区号；消费者启用 partition_notification_channel，并保留 20ms 轮询补偿。继续复用原生消费者，没有新增自写发布 worker。 |
| 消息表物理分区、UUIDv7 | 本轮不采用。当前几万条合成数据的索引与深分页未显示必须拆表，已定位的问题是接纳、计数器串行和消费隔离。物理分区不能消除这些等待，还会增加迁移和运维成本；后续按真实数据／磁盘／保留需求重新评估。 |

缓存位于 PostgreSQL 适配内部，API 入口显式创建并在 HTTP 停机后关闭；维护命令仍可使用无缓存构造器。forum／message 业务类型与 HTTP 路由不依赖缓存库。没有将缓存耦合到现有 Valkey engine。

每次消息分页仍查询当前成员与流末位置，再确定该次内容快照的上界。完整前缀不会被后续追加改变；未满页在其他实例追加后取得新上界和缓存键。返回值及入缓存值分别复制，且校验完整内容键，避免调用者修改或哈希碰撞返回错误页面。新请求被撤权后先返回 404，不能从热缓存读取；已经通过检查的在途读取仍可按该次快照完成，不能将 5 分钟 TTL 解释为权限缓存时间。

当前只有追加操作；**实现编辑／删除前必须引入版本或失效机制**。删除缓存不会删除权威正文，也不会改变幂等、序号或 Outbox；历史 HTTP 响应仍是 no-store。缓存命中仍有身份及当前成员／流位置数据库查询。

第六项迁移将 partition 变为数据库生成列、增加 `(partition,id)` 索引和通知触发器，生产者继续只插入 method／payload。不合法命令仍由约束拒绝，不能由调用者指定数据分区。升级屏障和实际步骤见 [实时运行说明](../backend/deploy/realtime/README.md)：**暂停全部写入者 → 旧消费者排空 → 停止全部消费者 → 迁移 → 全部同步配置为 5 分区及通知通道 → 启动并恢复写入**。队列非空时迁移明确失败；不得混用旧 1 分区与新 5 分区消费者，也不自动改派积压。

## 复测条件

- Ryzen 7 6800H，8 核／16 逻辑处理器，物理内存约 15.19GiB；API 池 16。Go 1.27.3、Centrifugo 6.10.2、SDK 0.13.0、PostgreSQL 18.6 的既有版本保持。
- 每轮独立新建隔离夹具；48 个 threaded 帖子、12384 条种子消息、1KiB 正文、1025 个不同 RS256 subject。实际发送主楼、引用主楼的子回复和引用子回复的子回复。
- 4 帖各 128 人订阅（512 条 WSS）或 16 帖各 64 人（1024 条）；每帖输入分别 25／100 条每秒、每帖 32 个客户端工作者。普通读取固定 100／秒、32 个工作者；普通写固定 25／秒、8 个工作者，分散到 32 个普通帖。
- 每档热身 3 秒、计量发起窗口 12 秒，不自动重试。停止发起后等待 HTTPS 结果，核对数据库，再以最多 30 秒等待排空；最终等待不计作窗口吞吐。
- API／压测器／SDK 同一个 Windows Go 进程，原生实时服务也在本机；数据库在 Docker Linux 临时内存存储。未分离服务端与客户端 CPU，没有正式磁盘／网络、慢读者、刷新风暴或长时间稳定性结论。
- 旧版二进制在实现前冻结，内含五项迁移、单消费分区、无正文缓存；候选和最终二进制内含第六项迁移及 5 分区。流 UUID 在每轮不同，4 个数据分区的碰撞分布没有固定。这是组合对照，不能把全部收益归因于某一个组件。

## 首轮结果与实际修复

仅增加缓存、分区和通知后，4 帖低档接收 P95 从 40.8ms 到 20.1ms，16 帖低档从 154.9ms 到 46.0ms；但最高档普通写仍只成功 **74/300**。这说明候选有收益，却没有解决共享等待容量被占满。

原因是原来每流虽仅有 2 个活动写者，等待者仍可填满全局 256 个活动／等待名额；16 个热帖同时持续输入时，普通帖会在入队前收到容量拒绝。现将每计数器的活动加等待上限设为 **12**，全局 256／活动写 12／每计数器活动写 2／共用 2 秒等待期限保持。16 个热流最多占 192 个等待和活动名额，给当前普通流量留下空间。容量错误继续使用 503 write_capacity_exceeded 与 Retry-After: 1，幂等重试复用原键。

这是单实例有界等待策略，**不是任意流数或多实例公平调度**；超过 21 个满额计数器仍可能占满总量。满额立即拒绝也会降低单热点短突发的接纳率，实测代价见下节，没有将其隐藏。

测试还发现并修复两处夹具问题：缓存撤权测试改用专属合成账号，避免影响原有审计计数；更快的消费唤醒暴露出重放测试把“客户端收到”误当成“消费者已确认删除”的竞态。现在下一次 DELETE 故障注入前明确等待 Outbox 排空，原事件 ID／消息 ID／字节一致断言保留，没有放宽重放正确性要求。

## 正确性与验证

默认测试覆盖单键加载合并、等待者取消不影响加载者、错误不缓存；数据库集成覆盖跨成员内容共享、返回值修改隔离、其他实例追加刷新未满页、闭合页复用和热缓存撤权拒绝。队列测试覆盖局部满额不泄漏全局名额、普通流继续进入、取消清理；既有并发幂等和授权回归保留。

真实原生分区隔离测试锁住一条 Outbox 的 DELETE 确认，先观察消费者实际处于 Lock 等待，再验证另一个数据分区继续投递、控制分区的 4001 撤权在释放数据锁前到达；被阻塞流的下一条消息只在释放后投递。另验证迁移非空屏障、非法信封和生成分区不可覆盖。这里只证明该合成故障下的隔离，不是正式故障撤权 SLA。

integration,realtime,cluster,acceptance,algorithms 全套通过，PostgreSQL 包 87.702 秒，包含真实 65 秒中断、历史过期、双节点恢复／撤权、补读合并及算法性质。随后只改性能报告、等价 SQL 常量抽取及默认缓存测试；短 API 实测执行了新的 SQL 常量。最终默认回归、全标签 go vet、go mod verify 与六个 Linux／amd64 命令交叉构建通过；Go 产物未在 Linux 执行。govulncheck v1.9.0 对全标签含测试调用图未发现已知漏洞，官方库更新于 2026-10-27 21:16:18 UTC；不代替原生二进制／镜像审计。

## 仍可改进的地方

1. **先改测量部署。** 分离压测器、API、实时服务与数据库，使用真实磁盘／网络，增加冷页／尾页、慢客户端、重连／凭据刷新和长时间负载；记录进程 CPU／RSS、缓存成本与命中、分区积压、数据库连接和成功延迟。这比继续在同机短测上宣称容量更有价值。
2. **再评估接纳公平与突发体验。** 当前每流 12 是简单工程默认，16 流保护不等于任意流数保证；需测试更多流、偏斜流量和多实例。可比较有界按流轮转调度、少量借用空闲预算或客户端按 Retry-After 退避并加抖动，明确成功率、等待和复杂度取舍；前端重试必须复用原幂等键。未替用户决定业务令牌桶／身份组配额。
3. **热点持续吞吐仍有空间。** 保留事务计数器顺序，按真实瓶颈评估每流小批写入，度量批内错误、幂等、取消及提交等待；不能仅靠扩大连接池或增加分区消除同流行锁串行。4 个数据分区仍可能碰撞，是否增加需结合连接／消费成本验证，不能在线随意改取模。
4. **随业务完善失效和同步。** 编辑／删除需要正文 revision／缓存失效、独立变更游标；读进度需要 watermark。当前创建序号及 5 分钟 TTL 不能代替这些机制。周期授权复核和正式故障撤权时效仍待设计与验收。
5. **继续 P3 与上线门槛。** 当前测试仍为 threaded 贴吧式主楼／楼中楼／引用；即时式帖子与产品固定频道尚未实现。P2 后端保持完成，P6 的生产容量／高可用、真实 IdP、存储／备份加密与管理审计仍单独推进。

本轮业务变化局限于 PostgreSQL 适配、入口缓存生命周期、迁移／消费者配置和相关验证；文档与注释同步。替换缓存只调整适配与生命周期，替换数据库／实时组件仍主要影响对应适配；移除缓存不改变业务契约，身份与令牌模块仍能独立验证。没有增加按表机械接口或新的业务框架。
